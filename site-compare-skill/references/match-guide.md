# タスクの対応の進め方（工程 5）

行（業務種別）ごとに、各拠点の作業の箱を、拠点をまたいで「同じ作業」のタスクにまとめる。決まりは `references/compare-rules.md` の 4 章。
機械が並び・区分・差の種類・粒度・複雑性を決めるので、LLM が書くのは「どの箱が同じ作業か」と「記載なしの根拠」と「内容の差」だけ。

## 親（進行役）のやること

1. 行ごとに下書き: `python3 scripts/sc_match.py draft -w <CMP> --row <行>`（基準の拠点の作業の箱を、1 つずつタスクにしたもの）。
2. 行ごとに 1 体のサブエージェントを起こして、下の指示文を渡す（同時に 4〜6 体）。サブエージェントを起こせない環境で、行の材料が小さい（合わせて数千字）ときは、親が指示文のとおりに書いてよい（照合は、別の担当が行う。verify-prompt.md）。同じフローを分け合う行（`sc_match.py material` の末尾に出る）は、まとめて 1 体に。
   材料が 4 万字を超える行（`sc_axis.py plan` の★）は、先に子の行に分ける。
3. そろったら `python3 scripts/sc_check.py -w <CMP> --stage rows --fast` → `python3 scripts/sc_compute.py -w <CMP>`（または `sc_run.py`）。FAIL は、その行の担当に直させる。
4. 親は材料・拠点の写しを開かない。見るのは `reports/match_<行>.json` と点検の出力だけ。

## 指示文の `{…}` に入れるもの

`{CMP}`＝比較の作業フォルダの絶対パス、`{SKILL}`＝このスキルのフォルダ、`{ROW}`・`{ROW_NAME}`＝行の ID と名前（まとめて渡すときは並べる）。

## サブエージェントへの指示文（ここからコピー。`{…}` を置き換える）

あなたは、拠点ごとの業務フローの箱を見比べて、拠点をまたいで「同じ作業」をタスクにまとめる担当です。書くのは JSON（タスクの対応）だけで、並び・区分・差の種類・複雑性は機械が決めます。
**同じタスクにするのは、同じ作業のときだけです。** 名前が似ていても、何を・何のために・前後に何があるかが違えば、別のタスクにします。違う作業を同じにする誤りは、表では誰も気づけません。

### 担当する行
- 比較の作業フォルダ: `{CMP}`
- 行: `{ROW}`「{ROW_NAME}」
- 書く先: `{CMP}/rows/{ROW}.match.json`（下書きがある。直して書く）

### 最初に読むもの
- `{SKILL}/references/compare-rules.md` の §0・§4
- `{SKILL}/references/schemas.md` の「タスクの対応」（書く形。表に無い項目は使えない）
- 材料: `python3 {SKILL}/scripts/sc_match.py material -w {CMP} --row {ROW}`（拠点ごとの箱: 鍵・種類・担当・名前・補足・札・帳票・分岐の行き先・出典）
- 原文を見たいとき: 拠点の写し `{CMP}/snap/<拠点>.json` の `nodes` の `quotes`（日本語でない拠点は原文）

### 書き方（上から順に）
1. **タスクを決める**: 下書きは基準の拠点の箱 1 つ＝1 タスク。ほかの拠点の箱を、同じ作業のタスクの `members` に入れる。どの拠点の作業の箱（作業・判断・システム処理）も、ちょうど 1 つのタスクに入れる（別のフローへ進む箱・開始・終了は入れない）。
2. **粗い方に合わせる**: ある拠点が 1 つの箱で書いた作業を、ほかの拠点が何個かの箱で書いていれば、詳しい側の箱を 1 つのタスクにまとめる（判断・差し戻しの枝も入れる）。下書きのタスクを統合して、ID は統合したどれか 1 つ（ふつうは小さい番号）を使う。一度計算したタスクの ID（`numbers.json` に番号のあるもの）は、別の作業のタスクに使い回さない。
   **粗い箱に含めてよいのは、その箱の文が名指ししている作業と、名指しした作業と作業の間にある詳しい箱だけ**（「支払データを作成して振込を行う」なら、作成・その間の確認・振込とその中の細目（エラーの判断・再振込））。名指ししていない前か後ろの端の作業（「提出する」の前の「作成する」）は含めず、別のタスクにして、粗い拠点は記載なしにする。
3. **まとめすぎない**: どの拠点も 2 つ以上の箱で書いているタスクは分ける。拠点で分け目が食い違って分けられないときだけ、`joined` に理由を書く。
4. **ほかの拠点にだけある作業**は、新しいタスクを足す（ID は、いちばん大きい番号の次）。
5. **タスクの名前**: 日本語の「目的語＋動詞」。粗く書いた拠点の言葉に近く、短く。
6. **記載なし**: その行にフローを当てた拠点で、タスクに箱が無ければ、`members` は空の並びにし、`python3 {SKILL}/scripts/sc_match.py candidates -w {CMP} --row {ROW}` の候補を全部 `absent.<拠点>.checked` に写し、どれも同じ作業でない理由を `note` に 1 文で書く。候補が同じ作業なら、記載なしにせず、その箱をタスクに入れる（ほかのタスクから移す）。粗く書いた 1 つの箱に含まれていれば、そのタスクにまとめる（2）。
7. **内容の差**（`content`）: やり方（紙とメール・目視とシステム・手での記録と自動の記帳）・値（金額の基準・期日）・対象の違いだけを書く。担当・システム・帳票・判断・順序の差は書かない（機械が出す）。`sites` は差のある拠点（基準ありなら、基準と違う拠点）、`evidence` は差のある拠点と比べた相手の両方の箱。文は日本語で、拠点の名前で書く（拠点 ID・箱の鍵を書かない）。
8. **確認事項**: 同じ作業か決められない・記載なしの作業を行っているかで区分が変わる、のときだけ `questions` に書く（`effect` は 対応／区分／差の種類／複雑性。名前だけ・値だけの問いは書かない）。いちばん確からしいほうに仮置きして、仮置きを `assumption` に。

### 終わったら
1. 確かめる:
   ```bash
   python3 {SKILL}/scripts/sc_validate.py --file match {CMP}/rows/{ROW}.match.json
   python3 {SKILL}/scripts/sc_check.py -w {CMP} --stage rows --fast
   ```
   この行の FAIL を 0 にする（ほかの行の FAIL は、その担当のもの）。
2. 報告を `{CMP}/reports/match_{ROW}.json` に書き（形は schemas.md の「タスクの対応の報告」）、`python3 {SKILL}/scripts/sc_validate.py --file report_match <そのファイル>` で確かめる。
3. 返事は 1 行だけ: タスクの数・記載なしの数・確認事項の数。JSON の中身は貼らない。

## よくある失敗

| 失敗 | 何が起きるか | どうする |
| --- | --- | --- |
| 名前の一致だけでまとめる | 違う作業が「共通」に見える | 前後の作業・扱う物・担当で確かめる（照合が不支持にする） |
| 粗い拠点に合わせずに、詳しい拠点の箱 1 つずつに粗い拠点の箱を重ねる | 粗い拠点の 1 つの箱が 2 つのタスクに入る（点検が FAIL） | 詳しい側の箱をまとめて 1 つのタスクに（内訳として残る） |
| どの拠点も詳しいのに 1 つにまとめる | 担当・判断の差が内訳に隠れる | 分ける（点検が joined を求める） |
| 粗い箱に、文が名指ししていない端の作業を含める | 照合が「原文に無い」と一部支持にする | 端の作業は別のタスクにし、粗い拠点は記載なし |
| 候補を確かめずに記載なしにする | ほかの業務種別に書いてある作業を「無い」と言ってしまう | candidates の候補を全部確かめる（点検が FAIL） |
| 担当・システムの差を content に書く | 差が 2 回出る・機械の差と食い違う | content は、やり方・値・対象だけ |
