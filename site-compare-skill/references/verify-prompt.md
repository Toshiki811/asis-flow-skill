# 対応の照合の指示文（作り方を知らない別のエージェント用）

機械チェックは、箱がタスクに 1 回ずつ入ること・記載なしの候補を確かめたことしか見ない。**その箱の組が本当に同じ作業か、記載なしと言った作業が本当に資料に無いか、
内容の差が原典のとおりか**は、原典の言葉を見た人にしか分からない。作った本人は自分の読みを疑えないので、作り方を知らない別のエージェントに照合させる
（asis-flow-skill の原典照合と同じ考え方）。

## 使い方

1. `python3 scripts/sc_verify.py sheet -w <CMP>` — 行ごとの照合シート `out/対応の照合シート_<行>.md` を作り、照合に出した版を控える（見出しに［V-<n>］）。
2. 下の指示文を、**このスキルの名前・決まり・タスクを決めた理由を一切伝えずに**、別のエージェントに渡す。照合シート 1 つにつき 1 エージェント（主張が 60 を超える行は、親が主張の番号で分けて渡してよい。報告は 1 つの行に 1 本）。

   | 置き換える所 | 入れるもの |
   | --- | --- |
   | `{SHEET}` | `<CMP>/out/対応の照合シート_<行>.md`（差分照合なら `_<行>_V-<n>.md`） |
   | `{OUT}` | `<CMP>/reports/verify_<行>.json`（差分照合なら、sheet の出力に出る `verify_<行>_差分<N>.json`） |

3. `python3 scripts/sc_verify.py draft -w <CMP>` — 報告から採否表 `review/<行>.review.json` の下書き（判定と指摘は機械が写す）。親は、指摘ごとに `decision`（採用／不採用／保留）と `action`（直したこと・採らない理由）だけを書く。
4. 採用した指摘を、タスクの対応（`rows/<行>.match.json`）・比べる行・用語の対応に反映し、`sc_compute.py` をやり直す。
   同意しない指摘（不採用・保留）は、理由を `action` に書き、その主張だけを**別の担当**に差分照合させる（`sc_verify.py sheet --only <行> --claims <主張>` → 新しいエージェントに同じ指示文）。2 人目も支持しなければ、直すか、確認事項にして仮置きのほうに直す（`compare-rules.md` 6.4）。親が自分で照合し直さない。
5. `python3 scripts/sc_check.py -w <CMP> --stage verify` を FAIL 0 に（支持率 95% 以上）。照合のあとに変わった主張は、点検が挙げるコマンドで差分照合する（`sc_verify.py sheet --only <行> --claims <主張>`）。

サブエージェントを起こせない環境では、別のプロセスの Claude に回す（空のフォルダで `claude -p "<指示文>" --allowedTools Read Write --add-dir <CMP>/out --add-dir <CMP>/reports`。それもできなければ、利用者に別のセッションで回してもらう）。親が自分で照合すると、作った人の読みがそのまま「支持」になる。

渡してよいもの: 照合シート。渡さないもの: `compare-rules.md`・このスキルの説明・タスクの対応の JSON・材料（渡すと、作った側と同じ読み方をしてしまう）。
親は、照合シートを開かない（行が多いと文脈があふれる）。受け取るのは、照合の担当が書いたファイルだけ。

## 指示文（ここからコピー）

あなたは、拠点ごとの業務マニュアルから描いた業務フローを、拠点をまたいで突き合わせた結果の検証担当です。照合シートの「主張」が、原典（出典の引用）から見て正しいかを、1 つずつ判定してください。
どう作られたかは知らされません。推測する必要もありません。シートに出ている箱の名前・担当・出典の引用だけで判定します。

### 見るもの
- 照合シート `{SHEET}`（Read で全部を順に見る）。前半に、拠点ごとのこの業務の箱（並び順）、後半に主張。
- 箱の名前は日本語に直してあります。日本語でない拠点は、引用が原文です（訳が原文と合っているかも見てください）。

### やること
1. 主張ごとに判定する:
   - 「〇〇の次の箱は、タスク『…』の作業である」（`t3/TK` の形）: その箱の組が、タスクの名前の作業をしているか。同じタスクにした、ほかの拠点の箱と同じ作業か（何を・何のために・前後に何があるか）。
     違う作業が混ざっている・同じ作業がほかのタスクに分かれている → 一部支持か不支持。
   - 「〇〇に、タスク『…』の作業は書かれていない」（`t3/OS:absent`）: その拠点の箱の一覧（シートの前半）と確かめた候補の中に、同じ作業が無いか。
     ある・粗く書いた 1 つの箱に含まれているように読める → 不支持（どの箱かを書く）。
   - 「〇〇では、タスク『…』の作業は、この拠点の手順ではない」（`t3/OS:absent` の、根拠のある形）: 示した根拠（その拠点が描かなかった資料の項目の引用・同じページの注記・箱の補足）から、この作業をほかの拠点が行う（この拠点の手順ではない）と読めるか。
     読めない → 一部支持か不支持。この拠点の箱（シートの前半）が、この作業をしている → 不支持（どの箱かを書く）。
   - 「内容の差」（`t3/content:1`）: 差の文が、両拠点の引用から読めるか（根拠が、拠点が描かなかった資料の項目のときは、その引用と注記から）。
2. 判定は 支持／一部支持／不支持。一部支持・不支持は、何が違うかを 1 文で書く。
3. 指摘（直し方の提案）は、次の種類で書く: 対応違い（違う作業を同じタスクにしている・同じ作業を分けている）／記載あり（記載なしとしたが、同じ作業がある）／粒度（まとめすぎ・分けすぎ）／内容（内容の差が原典と合わない）／名前（タスクの名前が中身と合わない）／その他。

### 出力形式
`{OUT}` に、次の形の JSON を書く（`sheet` は、シートの見出しの［V-<n>］を写す）:

```json
{"sheet": "V-3", "row": "B03",
 "verdicts": [{"claim": "t1/TK", "verdict": "支持", "evidence": "「経理部は、経費精算システムから承認済みの申請を一覧で出力する」"},
              {"claim": "t1/OS:absent", "verdict": "不支持", "evidence": "大阪支店の「支払データを作成して振込を行う」は、承認済みの申請を対象にしていて、一覧の出力を含むようにも読める"}],
 "findings": [{"kind": "記載あり", "target": "t1/OS:absent", "text": "大阪支店の 1 つの箱に含まれているなら、記載なしではなく粗い記載として扱う"}]}
```

- `verdicts` は、シートに載った主張を全部（1 つも抜かさない）。
- `findings` は、直したほうがよい所だけ（無ければ空）。
- 返事は 1 行だけ: 支持・一部支持・不支持の数と、指摘の数。
