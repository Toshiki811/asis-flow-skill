description: 拠点ごと（インド・ベトナム・シンガポールなどの海外拠点、東京支店・大阪支店などの国内の拠点）の業務マニュアル・手順書・規程類（全社共通の資料に「大阪支店の場合は…」の書き分けがある形も。日本語以外の資料も。大量でも可）から、asis-flow-skill で拠点ごとに as-is の業務フローを根拠つきで作り、拠点をまたいで業務とタスクを突き合わせて、どこが同じでどこが違うかを Excel と draw.io で出すスキル。基準の拠点があれば、その業務一覧にほかの拠点を寄せ、無ければ拠点を横に並べて同じ業務をそろえる（元の業務名が分かるまま）。マニュアルの粒度のずれは、タスクごとに粗い方へそろえ、詳しい拠点の作業は内訳として残し、活かせなかった詳細を活かすための追加の資料を示す。納品物は、① 拠点タスク一覧（タスクごとに、どの拠点に・どんな差があるか）、② 拠点のタスク別業務フロー（業務種別ごとに、拠点のレーンを横に並べ、同じタスクを同じ高さに）、③ 複雑性ヒートマップ（条件分岐の数と、担当のレーンをまたぐ受け渡しの数で大中小）。同じ業務かの判定は、作り方を知らない別のエージェントが原典で照合する。「拠点ごとのマニュアルを比べて」「支店間で業務の差分を出して」「海外拠点と国内の業務を比較して」「拠点間の業務の違いを一覧に」「拠点別の業務フローを並べて」「拠点の業務の複雑さをヒートマップで」のように、2 つ以上の拠点・支店・事業所・工場・子会社の業務を資料から比べる依頼では、draw.io や比較という語が無くても必ずこのスキルを使う。

# 拠点間比較スキル

拠点ごとの業務マニュアルから、拠点をまたいだ業務の差を、根拠つきで Excel と draw.io に出す。核は `references/compare-rules.md`（正典）の 4 点。

- **比べるのは、原典照合を通した拠点ごとの as-is。** 拠点ごとのフローは asis-flow-skill で作り、原典照合（支持率 95% 以上）まで済ませてから写す。拠点の図の読み違いは、そのまま「差」になる。
- **「—」は「業務が無い」ではなく「資料に記載なし」。** 記載なしと言うには、機械が出す候補（その拠点のほかの業務種別の似た作業・フローから外した手順）を全部見たと書く。粗く書いた 1 つの箱の中に含まれていないかも照合で見る。
  資料に「その拠点では行わない」とある業務・作業（業務ごとの対象外・共通の資料が「本部拠点だけ」とする手順・ほかの拠点の担当のレーンの箱）は「対象外」。記載なしと分け、区分と追加の資料の依頼に数えない（ほかの拠点の担当は用語の組の `site`、書き分けの根拠・受け取る側〔ほかの拠点の箱が「本部へ申請する」〕は `absent.not_here`）。`site` の効き目は、箱の組の主張で照合する。
- **粒度は、タスクごとに粗い方へそろえる。** 拠点全体ではそろえない。詳しい拠点の作業は内訳として残し（表に内訳、図は全部描く）、何があれば比べられるようになるかを「追加の資料の依頼」に出す。
- **LLM が書くのは「どれが同じか」だけ。** 並び・区分・記号・差の種類（担当・システム・帳票・判断・順序）・粒度・複雑性・番号は機械が決める。LLM が書くのは、用語の対応・業務種別の対応・タスクの対応（箱の組）・記載なしの根拠・内容の差（やり方・値・対象）だけ。Excel と draw.io は機械が書き出す（XML・セルを手で書かない）。

納品物（日本語のみ。システム名・資料名などの固有名はそのまま。原文の引用は出さない。出典は「資料名 p.N」）: `拠点比較.xlsx`（概要・拠点タスク一覧・拠点別の明細・業務種別の対応・複雑性ヒートマップ・複雑性の明細・追加の資料の依頼・拠点間の用語対応・確認事項一覧）、`拠点比較フロー.drawio`（1 ページ目＝業務種別 × 拠点の複雑性の表、以降＝業務種別ごとに 1 ページ）と PNG、作業の記録（チェック結果・対応の照合シート・採否表・比較の数）。拠点ごとの as-is の納品物（業務フロー・業務マトリクス一覧）も要るなら、拠点ごとに asis-flow-skill の納品の門を通す。

## 手順

比較の作業フォルダ（`<CMP>` = `<出力先>/site-compare-work/`）にすべての中間成果物を置く。拠点ごとの asis の作業フォルダは `<CMP>/asis/<拠点>/`、共通の資料は `<CMP>/asis/shared/`。どの工程も途中からやり直せる（済んだ拠点・行は飛ばす）。

0. **始める**（`references/site-guide.md` §0）: `references/compare-rules.md` を全文読む。入力を `<入力>/<拠点>/…` と `<入力>/共通/…`（全社共通の資料。無くてよい）の形に置き、`python3 scripts/sc_init.py <入力> -w <CMP> [--baseline <拠点のフォルダ名>]`。**利用者と決める: 基準の拠点（無ければ null）・拠点の名前と別名（資料の中の呼び方を全部）・資料の言葉・共通の資料を使わない拠点。** 作業フォルダがすでにあれば `python3 scripts/sc_status.py -w <CMP>` から。**機械の工程は `python3 scripts/sc_run.py -w <CMP>` が順に回す**（LLM・人の仕事を終えるたびに実行する）。
1. **拠点ごとの as-is**（`references/site-guide.md` §1a〜1c）:
   - 1a 共通の資料は、`<CMP>/asis/shared` で 1 回だけ読む（asis の棚卸し・ページ化・読取・`check_extract.py` まで）。拠点の書き分けも、ふつうの手順として読む（条件は `condition` に）。
   - 1b 書き分け: `python3 scripts/sc_applies.py draft -w <CMP>` の候補ごとに、当てはまる拠点（all／only／except）と根拠を `applies.json` に書く。**フロー化の担当ごとに判断させない**（拠点で読みが割れる）。
   - 1c 拠点ごとに、asis の手順（棚卸し → `sc_share.py --site <拠点>` → ページ化 → … → 原典照合）。asis のフロー化の指示文には `sc_site_ops.py` の直しと site-guide の段落を、原典照合の指示文には site-guide の段落を足す。日本語以外の資料は、箱の名前・補足・確認事項を日本語に訳す（引用は原文。asis の決まり 1.27）。拠点は、拠点ごとに別のセッションで進めてよい。
   - 拠点の門: asis の `check_flow.py --stage flow` と `--stage review`（支持率 95% 以上）が FAIL 0、`python3 scripts/sc_check.py -w <CMP> --stage applies` が FAIL 0。
2. **写し**: `python3 scripts/sc_collect.py -w <CMP>`。門の通らない拠点は写さない。拠点のフローをあとで直したら、asis の側で直して照合し直し、`--site <拠点>` で写し直す（番号の振り直しは機械が付け直す）。
3. **用語の対応**（`references/terms-guide.md`）: `python3 scripts/sc_terms.py draft -w <CMP>` → 訳・言い換えで同じ担当・システム・帳票を、理由つきで 1 つの組にまとめる（名前は日本語）→ `sc_check.py --stage terms` を FAIL 0 に。
4. **比べる行**（`references/axis-guide.md`）: `python3 scripts/sc_axis.py draft -w <CMP>` → ほかの拠点のフロー（箱の一部も）を行に当て、基準に無い業務は行を足す（捨てない）→ `sc_axis.py show` → `sc_check.py --stage axis` を FAIL 0 に → `sc_axis.py plan`（4 万字を超える行は子の行に分ける）。**利用者に、比べる行（業務分類 › 業務種別 × 拠点の当て方）を見せる（確認点①）。**
5. **タスクの対応**（`references/match-guide.md`）: 行ごとに `sc_match.py draft`、1 行 1 体のサブエージェント（同時に 4〜6 体）に、拠点の箱をタスクにまとめさせる（サブエージェントを起こせず、材料が小さいときは親が書いてよい）。粗い箱に含めるのは、その箱の文が名指ししている作業と、その間にある詳しい箱だけ（前後の端の作業は別のタスク。compare-rules 4.3）。そろったら `sc_check.py --stage rows` を FAIL 0 に。
6. **計算**: `python3 scripts/sc_compute.py -w <CMP>`（`sc_run.py` が回す）→ `sc_check.py --stage compute`。
7. **対応の照合**（`references/verify-prompt.md`）: `python3 scripts/sc_verify.py sheet -w <CMP>` → 照合シート 1 つにつき、作り方を伝えない別のエージェント 1 体 → `python3 scripts/sc_verify.py draft -w <CMP>` → 採否（採用／不採用／保留＋対応）を書き、採用分をタスクの対応・比べる行・用語の対応に反映して工程 6 から → 照合のあとに変わった主張は、点検が挙げるコマンドで差分照合 → `sc_check.py --stage verify` が FAIL 0（支持率 95% 以上）になるまで。同意しない指摘は、その主張だけを別の担当に照合し直させる（親が自分で照合しない。compare-rules 6.4）。サブエージェントを起こせない環境では、別のプロセスの Claude（`claude -p`）か、利用者の別のセッションで照合する（6.5）。
8. **書き出しと点検**:
   ```bash
   python3 scripts/sc_book.py -w <CMP>                  # out/拠点比較.xlsx（確認事項一覧の回答は、いまのブックから取り込んで戻す）
   python3 scripts/sc_drawio.py -w <CMP>                # out/拠点比較フロー.drawio
   python3 scripts/sc_layout.py -w <CMP>                # 配置の点検 FAIL 0。PNG を out/png/ に（draw.io デスクトップが要る）
   python3 scripts/sc_check.py -w <CMP> --report <CMP>/out/チェック_比較.txt    # 全段 FAIL 0（表と図が、いまのデータのとおりか・納品物に内部の番号が出ていないかも見る）
   ```
   **PNG を全ページ目で見る**（帯のそろい・空き枠・内訳の枠・色・字のはみ出し）。draw.io デスクトップの無い環境では `sc_layout.py --preview` の下見で形だけを確かめ、PNG と目視は利用者の環境で。照合のあとに足したタスクで番号の順が並びと合わなくなったら、はじめて納品する前に限り `sc_compute.py --renumber`（7.6）。行が 10 を超えるときは、数ページずつ別のエージェントに見させて指摘だけを受け取る。**利用者に、拠点タスク一覧と複雑性ヒートマップを見せる（確認点②。大中小の境 `assets/sc_complexity.json` は既定が目安なので、実物で直す）。**
9. **納品の門**: 出力先を利用者に聞き、`python3 scripts/sc_deliver.py -w <CMP> --to <出力先>`。門は書き出しと点検を回し直し（拠点の門も）、全段 FAIL 0・PNG がそろって新しい・照合済み、を確かめてから写す。利用者には次をまとめて渡す。
   - 写した 2 つのフォルダ
   - 数（`比較の数.md`。機械が書く）: 拠点・行・タスクの数、区分ごとの数（共通・差異あり・拠点固有）、記載なし・対象外の数、粒度をそろえたタスクの数、照合の支持率、確認事項の件数
   - 追加の資料の依頼の上位（比べられるようになるタスクの多い順）と、答えで区分が変わる確認事項
   - 受けた指摘は `references/compare-rules.md` の 9 章に 1 行足す

確認事項に答えが返ってきたら、答えで変わる所（`effect`）を直す（記載なしを外す・タスクを移す・用語の組を直す。拠点のフローの読み違いなら asis の側で直して写し直す）。工程 6 からやり直す。タスクと確認事項の番号は引き継がれる。確認事項一覧に書かれた回答・回答者・回答日は、書き出し直すときに機械が取り込んで戻す。

## 大量の入力のとき（1 つのエージェントの文脈に収める）

仕事を、1 つのエージェントが読み切れる大きさに割る。状態は作業フォルダに置き、会話の記憶には頼らない。

| 何を | どう割るか |
| --- | --- |
| 拠点ごとの as-is | asis-flow-skill の割り方のまま（読取の束・フローの材料 4 万字・照合シートの分冊）。1 拠点 1 セッションで回してよい |
| 共通の資料 | 1 回だけ読み、拠点へは機械が写す（`sc_share.py`） |
| 比べる行 | 材料（フローごとの短い要約）が 4 万字までなら 1 体。超えるときは業務分類ごとに 1 体 |
| タスクの対応 | 1 行 1 体。行の材料は 4 万字まで（超える行は、下位フローの切れ目で子の行に分ける。`sc_axis.py plan`・点検が FAIL）。同じフローを分け合う行は、まとめて 1 体 |
| 対応の照合 | 照合シート（行ごと）1 つに 1 体。主張が 60 を超える行は、主張の番号で分けて渡してよい |
| 親（進行役） | 拠点のカード・フロー・材料・照合シートを開かない。見るのは `sc_status.py`・点検の出力・`reports/` だけ |

- **途中で止まったら・文脈が圧縮されたら・別のセッションで続けるときは、`python3 scripts/sc_status.py -w <CMP>` から始める。**
- 拠点を足すとき: `sites.json` に足し、その拠点の as-is を通し、写し → 用語の組に足す → 行に当てる → 行ごとのタスクに足す → 計算 → 変わった主張だけを照合し直す（点検が挙げる）。ほかの拠点の大中小は動かない（境は固定の値）。
- 表と図は、親の行で子の行を足し上げる。図は 5 拠点以上・タスクが 25 を超える行でページを分ける。

## やってはいけないこと

- 原典照合を通していない拠点のフローで比べる（`sc_collect.py --no-gate` は試験と下見だけ）
- 共通の資料を拠点ごとに読む・書き分けをフロー化の担当ごとに判断させる・拠点のフローに「大阪支店か」の判断を残す
- 名前が似ているだけで、同じ業務・同じタスクにする（何を・何のために・前後に何があるか・担当で確かめる）
- 記載なしを、候補を確かめずに書く。記載なしを「その拠点では行っていない」と言い換える
- 粒度を拠点全体で粗い方にそろえる。どの拠点も詳しく書いたタスクを、理由なしに 1 つにまとめる（`joined`）
- 基準に無い業務・作業を捨てる（行かタスクを足す。比べない箱は `not_compared` に理由つき）
- 担当・システム・帳票・判断・順序の差を、LLM が `content` に書く（機械が出す。内容の差は、やり方・値・対象だけ）
- 並び・区分・記号・番号・複雑性の数・大中小を、LLM が決める・`result.json` を手で直す
- 統合の余地・改善案・あるべき姿を混ぜる（as-is の比較だけ）
- 納品物に、拠点 ID・箱の番号・資料 ID・英語の原文を出す（点検が FAIL）
- Excel・draw.io を手で直す（データを直して書き出し直す。人が入れる回答だけは、ブックが正）
- 答えても比較が変わらない問いを確認事項に出す（`effect` を必ず書く）
- スキーマに無い項目を JSON に足す（当てはまる項目が無ければ報告の `for_parent` に書く）
- 納品の門（`sc_deliver.py`）を通さずに、`out/` を手で写して渡す
- 機械チェックが通ったことを、正しいことの証明として報告する（機械は形・数・候補を見ただけ。同じ作業かは、対応の照合と目視までが点検）
