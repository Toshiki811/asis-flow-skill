# site-compare-skill（拠点間比較）

拠点ごと（インド・ベトナム・シンガポールなどの海外拠点、東京支店・大阪支店などの国内の拠点）の業務マニュアルから、拠点をまたいで業務とタスクを突き合わせ、どこが同じでどこが違うかを、Excel と draw.io に根拠つきで出す Claude Code スキル。[asis-flow-skill](../README.md) を拡張する別のスキルで、拠点ごとの as-is の業務フローは asis-flow-skill で作る。

進め方は、拠点の一覧 → 全社共通の資料を 1 回だけ読む → 共通の資料の拠点ごとの書き分けを決める → 拠点ごとの as-is（asis-flow-skill で原典照合まで）→ 拠点の写し → 用語の対応 → 比べる行（業務種別の対応）→ タスクの対応 → 計算 → 対応の照合 → 書き出しと点検 → 納品の門、の順。手順は [SKILL.md](SKILL.md)、決まりは [references/compare-rules.md](references/compare-rules.md) にある。

納品物（日本語のみ）:

- **① 拠点タスク一覧**（`拠点比較.xlsx`）: 1 行＝1 タスク。区分（共通／差異あり／拠点固有）、拠点ごとに記号（○ 差なし・△ 差に関わる・— 記載なし・対象外〔資料に、その拠点では行わない・ほかの拠点が行うとある〕）とその拠点の作業の名前（内訳つき）、差の種類（担当・システム・帳票・判断・順序・内容・記載なし）と差の内容、粒度、確認事項。拠点別の明細（タスク × 拠点）・業務種別の対応・追加の資料の依頼・拠点間の用語対応・確認事項一覧のシートも。
- **② 拠点のタスク別業務フロー**（`拠点比較フロー.drawio`）: 業務種別ごとに 1 ページ。拠点のレーンの塊を横に並べ（基準が左）、同じタスクを同じ高さの帯にそろえる。色は 共通＝緑・差異あり＝橙・拠点固有＝赤、記載なしは点線の空き枠、対象外（受け取る側も）は灰色の枠、ほかの拠点の担当のレーンの箱は灰色の破線、粗く書いた拠点に合わせた詳しい拠点の作業は点線の枠（内訳）。レーンの名前は比べる用語の名前に、拠点の言葉を添える（「出納職員（事務員）」）。
- **③ 複雑性ヒートマップ**（Excel のシートと、draw.io の 1 ページ目）: 業務種別 × 拠点の大中小。点数＝条件分岐の数 × 2 ＋ 担当のレーンをまたぐ受け渡しの数 × 1（重みと境は設定ファイル）。数えた分岐・受け渡しは 1 件ずつ明細に。

## 考え方

- **比べるのは、原典照合を通した拠点ごとの as-is。** 拠点のフローの読み違いは、比べるとそのまま「差」に見える。拠点ごとのフローは asis-flow-skill で作り、作り方を知らない別のエージェントの原典照合（支持率 95% 以上）を通してから写す（拠点の門）。
- **LLM が書くのは「どれが同じか」だけ。** 用語の対応・業務種別の対応・タスクの対応（箱の組）・記載なしの根拠・内容の差（やり方・値・対象）だけを JSON で書く。並び・区分・記号・差の種類・粒度・複雑性・番号は機械が決め、Excel と draw.io は機械が書き出す。
- **同じ作業かは、別のエージェントが原典で確かめる。** 違う作業を「同じ」とする誤りは、表では誰も気づけない。主張（このタスクにこの箱の組が入る／この拠点に記載なし／この内容の差）を 1 つずつ、作り方を知らないエージェントが原典の言葉で照合する。照合のあとに変わった主張は、その主張だけを照合し直させる。

### 依頼の設計から変えた所（理由つき）

| 依頼の設計 | このスキルの形 | 理由 |
| --- | --- | --- |
| 粒度は、荒い方に一度そろえる | **タスクごとに**、いちばん粗く書いた拠点に合わせる。詳しい拠点の作業は内訳として残す（表に内訳、図は全部描く） | 受付は詳しく審査は粗い、という拠点は普通にある。拠点全体を粗い方にそろえると、比べられる所まで捨てる |
| 差分（無い業務） | 「—」は「業務が無い」ではなく**「資料に記載なし」**。記載なしと書くには、機械が出す候補（その拠点のほかの業務の似た作業・フローから外した手順）を全部確かめた記録が要る。資料に「その拠点では行わない・ほかの拠点が行う」とある所だけを「対象外」にする（共通の資料の書き分け・ほかの拠点の担当の箱） | 資料に書いていないだけのことは多い。「行っていない」と言い換えると、誤った結論になる。逆に、資料が「本部だけ」と言う作業を記載なしにすると、作業の差に見え、追加の資料の依頼の上位に出る |
| 大中小は、分岐の数とレーンをまたぐ処置の数 | 大中小は**そろえた粒度**で判定し、原典の粒度の数も明細に出す。受け渡しは「役割」で数える（拠点ごとの呼び方の違いは、用語の対応でそろえる） | 細かく書いた拠点ほど分岐・受け渡しが多く数えられ、書き方の細かさが「複雑さ」に見えてしまう |
| — | 拠点間の**用語の対応**（担当・システム・帳票）を先に作る | 「経理部」「経理担当」「Finance」が同じ役割かを決めないと、担当の差・システムの差・受け渡しの数を比べられない |
| 基準の拠点の業務一覧に寄せる | 基準に無い業務・作業も**捨てない**（「基準に無い業務」の行・タスクを足す）。どの拠点の作業の箱も、ちょうど 1 つの行・タスクに入るか、理由つきで「比べない」 | 落とすと差が見えなくなり、2 回数えるとヒートマップが膨らむ |
| — | 差の種類は「違う」と**「片方だけ記載」**を分ける。片方だけ記載は差に数えない。順序の差は、線でたどれる前後で見る | システム名が書いていないのは「システムを使わない」ではない。並べた順で見ると、並列の枝が差に見える |
| — | **粒度の差は差異に数えない**（別の印） | 書き方の違いで、業務の違いではない |
| — | 大中小の境は**固定の値**（`assets/sc_complexity.json`） | 拠点を足すたびに、ほかの拠点の判定が動かないように（分位で切らない） |
| 全社共通のマニュアルの「大阪支店の場合は…」 | 共通の資料は 1 回だけ読み、拠点の名前が出る所を機械が拾い、どの拠点に当たるかを 1 つのファイル（`applies.json`）で決めてから、拠点ごとのフローに配る | フロー化の担当ごとに判断させると、拠点で読みが割れ、同じ手順が「差」に見える |

統合の余地・改善案は入れない（as-is の比較に徹する）。

## 精度と規模のための仕組み

| ねらい | 仕組み |
| --- | --- |
| 出力が毎回ぶれない | 全部の JSON にスキーマ（`sc_validate.py`。余分な項目は FAIL）。並び・区分・記号・差の種類・複雑性・番号は機械が決める。タスクと確認事項の番号は、行とタスクの ID で引き継ぐ。同じ入力で書き出し直すと、計算・Excel・draw.io が同じ（文字のハッシュの種を変えても同じことを、試験で確かめる） |
| 拠点の読み違いを、差にしない | 拠点の門（asis の点検 `check_flow --stage flow`・`--stage review` が FAIL 0）を通らない拠点は写さない。拠点を直したあとの古い写しは、点検が止める。番号が振り直された箱は、出典の指紋で比較のファイルの鍵を付け直す |
| 共通の資料の書き分けが、拠点で割れない | 共通の資料のカードは共通の作業フォルダでだけ直し、拠点へは機械が写す（拠点の側で直すと FAIL）。ほかの拠点だけの手順がフローに入っている・自分の手順を外している・拠点で分かれる判断が残っている、を FAIL |
| 違う作業を「同じ」にしない | 箱は、ちょうど 1 つの行・タスクに入る（0 回も 2 回も FAIL）。どの拠点も 2 つ以上の箱で書いたタスクを 1 つにまとめるのは、理由（`joined`）があるときだけ。作り方を知らない別のエージェントが主張を 1 つずつ照合し、照合のあとに変わった主張は止める |
| 「記載なし」を軽く書かない | 記載なしの拠点ごとに、機械の候補（かなを除いた字の組で似た作業）を全部確かめた記録が要る（抜ければ FAIL）。粗く書いた 1 つの箱の中に含まれていないかも照合で見る |
| 使えなかった詳細を活かす | 粗く書いた拠点・記載なしの拠点ごとに、活かせていない作業・判断・受け渡し・システム・帳票の数から、依頼する資料（判断 → 規程・基準表、受け渡し → 業務分掌・権限表、システム → 操作の手順書、帳票 → 様式、記載なし → その作業の手順書）を、比べられるようになるタスクの多い順に出す |
| 納品物が日本語だけ | 箱の鍵・資料 ID・決まっていない用語・英語（3 語以上続く英字。資料名と拠点の用語の原文の名前は除く）が Excel・draw.io に出ていれば FAIL |
| 点検が壊れても気づける | LLM・人が書くファイルを見る点検は、どれも、誤りを 1 つ仕込んだ写しで FAIL が出ることを自己点検で確かめる（点検 111 か所のうち 110 か所。残りの 1 か所は理由つきで `evals/untested_checks.md`） |
| 大量の入力 | 拠点ごとの as-is は asis の割り方のまま（1 拠点 1 セッションでよい）。タスクの対応は 1 行 1 体で、行の材料は 4 万字まで（超えれば子の行に分けよと FAIL）。図は 5 拠点以上・タスク 25 超えでページを分ける。点検の出力は同じ種類を 10 件までに畳む（拠点の名前が違っても同じ種類）。状態は作業フォルダにあり、`sc_status.py` で途中から続ける |

## セットアップ

asis-flow-skill と同じものが要る（`pip3 install pymupdf python-pptx openpyxl pillow oletools`・Office 文書に LibreOffice か Microsoft Office・PNG の書き出しに draw.io デスクトップ。Python 3.9 以上）。asis-flow-skill の [セットアップ](../README.md#セットアップ) を見る。

Claude Code のスキルとして使うときは、2 つともシンボリックリンクで入れる（このスキルは、リンクを解いた 1 つ上のフォルダの asis-flow-skill を使う）:

```bash
ln -s <このリポジトリ> ~/.claude/skills/asis-flow-skill
ln -s <このリポジトリ>/site-compare-skill ~/.claude/skills/site-compare-skill
```

asis-flow-skill を別の場所に置くときは、環境変数 `ASIS_FLOW_SKILL` にその場所を書く（探す順: `ASIS_FLOW_SKILL` → 1 つ上のフォルダ → となりの `asis-flow-skill`）。

## 動作確認

```bash
python3 evals/selftest.py                 # 架空の 3 拠点を組み立て、正しいデータで全段 FAIL 0・計算が手で数えた値と同じ・揺れ・表記・基準なし・仕込んだ誤り・部品・納品の門（1〜2 分）
python3 evals/large_test.py               # 6 拠点 × 31 行（タスク 98・図 65 ページ）に複製し、材料の上限・ページの分け方・畳み・再開・Excel の行数・揺れ（30 秒ほど。--reps で行を増やす）
python3 evals/coverage.py                 # 自己点検を回しながら、FAIL を出した点検を控え、発火を確かめていない点検が一覧（untested_checks.md）の外に無いかを数える
python3 evals/fixture_tools.py build /tmp/sc_work   # 架空の 3 拠点の比較の作業フォルダを、期待データで組み立てる（手で触って試すとき。--stage sites なら拠点の as-is まで）
```

架空の 3 拠点（`evals/make_fixture.py` が PDF を作る。期待データは `evals/fixture_expected/`）:

- 全社共通: 経費精算マニュアル（申請・承認・支払処理への回付）。「※ 大阪支店では、課長に代えて支店長が申請を承認する。」の書き分けがある。
- 東京支店（基準）: 共通のマニュアル＋支払処理手順（詳しい。振込の下位フローに振込エラーの判断）。
- 大阪支店: 共通のマニュアル＋支払の手順（1 文。粗い）。
- シンガポール拠点: 英語の手順書（申請と承認が 1 本・GST の税額請求書の確認が固有・Oracle に記帳）。共通のマニュアルは使わない。

`evals/evals.json` のうち、架空データで試せるのは 1・2。3（4 拠点・多言語・大量）・4（工場ごとの読み替えの表）は、入力を各自で用意する。

## カスタマイズ

- いちばん効くのは `references/compare-rules.md` の 9 章への追記。レビュー・照合で受けた指摘を 1 行ずつ足す。
- 複雑性の重み・大中小の境・差の大きさの境は `assets/sc_complexity.json`。既定（小 4 まで・中 10 まで・大 それより上、分岐 × 2 ＋ 受け渡し × 1）は目安なので、実物の拠点で数えてから直す（概要のシートに、いまの値が出る）。判定に使う粒度は `basis`（aligned＝そろえた粒度／raw＝原典の粒度）。
- 納品物の字は Yu Gothic UI（asis の `scripts/common.py` の `OUTPUT_FONT`。図のセル・表のブック・既定のテンプレート）。Mac・Linux では別の書体で表示される。
- Excel の様式は `python3 scripts/sc_book.py default` が既定のテンプレートを作る。お客様の様式は `sc_book.py --template <様式.xlsx>`。
- チェックを足すときは `sc_check.py` に FAIL / WARN を足し、`evals/selftest.py` の `CASES` にその誤りを仕込んだケースを足して、`python3 evals/coverage.py` を通す。
- JSON の項目を足すときは、`assets/schemas/sc_*.schema.json` に説明つきで足し、`python3 scripts/sc_validate.py --doc` で `schemas.md` を作り直す。

## まだ確かめられていないこと

- 実物の拠点のマニュアルでの通し（LLM の工程: 書き分け・用語の対応・比べる行・タスクの対応・照合）。試したのは、架空の 3 拠点と、それを複製した大量の試験だけ。
  架空の 3 拠点では、作り方を知らないエージェントが SKILL.md だけで工程 1b〜9 を通した（照合は別のプロセスの担当。支持率 89% → 指摘を採用して差分照合し 100%）。そこで出た指摘（粗い箱に含める作業の線引き・指摘に同意しないときの進め方・サブエージェントの無い環境・出典の区切り・図のページ名の行の ID・進み具合のコマンドの道 など）は直した。拠点ごとの as-is（工程 1）から通したことは、まだ無い。
- draw.io デスクトップでの PNG の書き出し（作った環境に draw.io が無い。目視は、draw.io と同じ描画エンジンによる下見で行った。納品の門は、draw.io の PNG が無ければ止まる）。
- 複雑性の境と重みが、実物の拠点の「大中小」の感覚と合うか。
- 英語以外の日本語でない資料（ベトナム語・タイ語など）の文の切り方（asis の手入れで足したのは、英文の文末と略語だけ）。
