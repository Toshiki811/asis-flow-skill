# 階層の判定・資料の紐付け・業務分類の決め方（工程3・5）

フローは業務分類ごとに1枚描く。どう分けるか、資料どうしがどうつながるかを先に決め、利用者に見せてからフロー化に入る。ここを後から直すと、フローを全部作り直すことになる。

## 考え方: 業務の木を骨格にし、木で表せない関係だけを決まった種類の紐付けで持つ

- **骨格は業務の木**（業務領域 › 業務 › 手順）。出力（全体構成 → フロー → 下位フロー）も、目次も、人が確かめるときの見方も木になっている。
- **資料は木にならない。** 1つの様式を複数の業務が使う。操作マニュアルを複数の業務マニュアルが参照する。規程が複数のマニュアルの根拠になる。ある資料の業務が、別の資料の業務に続く。資料に親を1つだけ持たせると、これらが落ちる。
- そこで、資料どうしを親子にして終わりにせず、**資料の節を業務の木に結び付ける**（「上位資料のこの節を、この資料が詳しくしている」）。木で表せない関係は、下の決まった種類で持つ。
- 種類や概念を自由に増やさない。語彙が開いていると、実行のたびに形が変わり、人が確かめきれない。別の担当・帳票を同じものとして誤って結ぶと、結ばない場合より害が大きく、気づきにくい。**根拠の文を書けない紐付けは作らない。**

| 何と何 | 種類 | 書く先 | 使いみち |
| --- | --- | --- | --- |
| 資料の節 → 業務 | 書いている（`describes`）／詳しくしている（`details`） | `hierarchy.json` の `tree[].refs` | ページの割当。上位フローと下位フローの分け方 |
| 資料 → 資料 | 上位（`parent_of`）／別紙（`appendix_of`）／根拠（`basis_of`）／参照（`refers_to`）／版違い／同一 | `doc_relations` | 全体構成の図。食い違いの突き合わせ先 |
| 業務 → 業務 | 続く | `sequence` | 資料をまたぐ受け渡し。フローの「別フローへ」のノード |
| 用語 → 出てくるページ | （機械が集計） | `glossary.json` | 同じ帳票・システムを使う業務を見つける。レーン名の統一 |

## 工程3: 階層の事前チェック（`structure/hierarchy.json`）

全ページを読む前に行う。使うのは機械で集めた手がかりと、目次まわりのページの画像だけ。

1. `python3 scripts/detect_structure.py -w <作業フォルダ>` の要約を読む（フォルダ・目次・本文の見出しの候補・資料の役割の見立て・資料どうしの関係の候補）。
   - **本文の見出しの候補**は、本文の中の、番号で始まる短い行（第◯章・1・1.1・（1）・①）。目次が拾えていない資料は、要約に一覧が出る（全部は `structure/signals.json` の `body_headings`）。段は、番号の書き方の入れ子の順（第◯章 → 第◯節 → 1 → 1.1 → （1） → ①）からの見立て。図の箱の題・箇条書きの項目も混じるので、そのページの画像で、見出しかどうかを確かめてから使う。
2. 目次らしいページ（要約に出る）と、各資料の表紙の次の1〜2ページの画像を Read で開く。目次が画像の中にしかない資料は、機械では拾えていない。
3. 次を判定して `hierarchy.json` に書く（形は `schemas.md`）。

| 判定すること | 見るもの | 書く先 |
| --- | --- | --- |
| 階層構造か（あり／一部／なし） | フォルダの深さと番号、目次の段、見出し番号の深さ、本文の見出しの候補、しおり、セクション | `is_hierarchical`・`basis`・`rationale` |
| 業務の木 | 目次の項目、フォルダ名、資料名。目次の無い資料は、本文の見出しの候補（章・節。`source: heading`） | `tree[]`（上から 業務領域 > 業務 > 手順 > 操作） |
| 資料の役割と題名 | 資料名・フォルダ・表紙（機械の見立てを確かめる） | `docs[]`（全資料に `role`。表紙のある資料は、表紙の題名を原文のまま `title` に写す。納品物では、資料をこの題名で書く — 資料ID は出さない） |
| 資料の節と業務の結び付き | 目次の項目とページ、資料名 | `tree[].refs`（この段階で分かる範囲。ページは空でもよい） |
| 資料どうしの関係 | 「別紙」「◯◯参照」「◯◯規程に基づき」、資料名の言及、フォルダの親子、版の表記 | `doc_relations[]`（根拠の文を `evidence`、ページを `sources` に） |
| 目次に業務（業務フロー）の一覧があるか | 目次の項目が「業務・手続き・処理」の名前で並んでいるか | `toc_flow_list`（`page` は目次に刷られた番号のまま） |

### 「目次に業務フローの一覧がある」とは

目次（または業務一覧表・フロー一覧・索引）の項目が、そのまま業務の単位になっている状態。

- ある: 「1. 受注業務　2. 出荷業務　3. 請求業務」「業務フロー一覧: 01 新規契約／02 契約変更／03 解約」
- ある（下位に）: 章は「第1章 総則　第2章 販売管理　第3章 購買管理」で、節に「2.1 受注　2.2 出荷」と業務が並ぶ → 節の段を業務として採る
- ない: 「1. はじめに　2. 画面の説明　3. 操作方法　4. 困ったときは」（システムの機能別・画面別の目次）
- ない: 目次そのものが無い、資料がばらばらの手順書の寄せ集め

迷うとき（項目が業務とも機能とも読める）は、`found: true` にして目次に準拠し、確認事項（種別「分類」）で利用者に確かめる。目次を捨てて分類し直すより、目次に沿って確かめるほうが利用者の認識に近い。

### 食い違いの扱い

フォルダの分け方と目次の章立てが違う、資料 A の目次と資料 B の目次で同じ業務の名前が違う、といった食い違いは、どちらを採ったかを `rationale` に書き、確認事項（種別「階層」）にする。両方をそれぞれ生かして二重の階層を作らない。

4. `python3 scripts/check_flow.py -w <作業フォルダ> --stage hierarchy` で形を確かめる（この段階では、結び付きが決まっていない資料は WARN。工程5で埋める）。
5. **利用者に見せる（確認点①）**: 階層の判定、資料の役割と関係、目次に準拠するかどうか。あわせて、縦軸（業務マトリクスの行）の案を見せる: `python3 scripts/pages.py rows -w <作業フォルダ>`（目次に業務の一覧があれば、階層の判定から組んだ下書きで、大分類・中分類・分類名の根拠と、目次の項目ごとの扱いが出る）。大量の入力のときは、ここで読む範囲と優先順も決める。

## 工程5: 用語・紐付け・業務分類の確定

全ページのカードができてから行う。親はカードを1枚ずつ開かず、次の集計で見渡す。

```bash
python3 scripts/pages.py outline -w <作業フォルダ>     # 資料・章ごとの集計（1行＝1つの章）
python3 scripts/pages.py pagemap -w <作業フォルダ>     # 刷られた番号とファイルの番号の対応。目次の番号 → 実際のページ
python3 scripts/pages.py terms -w <作業フォルダ>       # 担当・システム・帳票の表記と、同じものかもしれない組
python3 scripts/pages.py links -w <作業フォルダ>       # 紐付けの候補（参照の文・共有している帳票・業務どうしの受け渡し・別の業務の名指し）。番号つき
python3 scripts/pages.py links -w <作業フォルダ> --accept R1,S2   # 根拠の文を読んで採る候補の番号だけを渡す。根拠の文とページは、機械が hierarchy.json に写す
```

### 用語の正本（`glossary.json`）

- `terms` の出力から、担当・システム・帳票の名前を1つずつ載せる（原典の表記のまま）。数が多いときは `python3 scripts/pages.py terms -w <作業フォルダ> --draft` が、まだ無い表記を別々の用語として書く（寄せない。すでにある用語には触らない）。寄せるかどうかは、このあと人が決める。
- 「同じものかもしれない組」は、原典で同じと確かめられたものだけ `aliases` に寄せ、根拠を `evidence` に書く（「経理部（以下、経理）」のような定義、同じ文の中の言い換え）。
- 確かめられないもの（「上長」と「課長」）は、別の用語のまま両方を載せ、確認事項（種別「用語」）にする。
- フローのレーン名・帳票名は、ここの `name` しか使えない。フロー化の担当が正本に無い呼び方を見つけたら報告してくるので、原典を確かめて足す。

### 紐付けの確定（`hierarchy.json` を更新）

- `links` の候補を1件ずつ見る。根拠の文を読み、採るものだけを書く（`tree[].refs`・`doc_relations`・`sequence`）。採るものには根拠の文（原文）とページを付ける。
- **上位資料が1行で書いた業務を、下位資料が詳しくしている**ものは、業務の木のその節に、下位資料を `rel: details` で結び付ける。`parent_of` だけ書いて節に結び付けていないと、フローの親子に落とせない（FAIL）。
- 全資料が、どれかの業務に結び付いているか、対象外の理由（`docs[].out_of_scope`）があること。
- ある業務の成果を別の業務が受け取るもの（資料をまたぐものも）は `sequence` に書く。同じ資料の中の章どうし（「◯◯は第8章 購買を参照」）も同じ。`links` が、番号と名前で名指しした参照を候補に出す。
- 決められない紐付けは作らず、確認事項（種別「階層」）にする。

### 業務分類（`taxonomy.json`）: 目次に一覧があるとき（`basis: toc`）

**下書きは機械が書く。** 名称・順序・番号・目次の場所（`toc_ref`）・ページの割当は、判断の要らない写しなので、LLM が書くと実行のたびに揺れる。

```bash
python3 scripts/pages.py taxonomy -w <作業フォルダ> --draft    # taxonomy.json の下書き（すでにあれば、分類には触らない）
python3 scripts/pages.py rows -w <作業フォルダ>                # 縦軸（業務マトリクスの行）と、目次の項目ごとの扱いを見る
python3 scripts/pages.py orphans -w <作業フォルダ>             # どの分類にも入っていない内容ページのまとまりと、結び付きそうな目次の項目の候補
```

下書きのあと、LLM が決めるのは次の4つだけ（下書きの名称・順序・番号は書き換えない）。

| 決めること | 書き方 |
| --- | --- |
| 目次の業務一覧に無い項目（下書きが「フローを描かない」で置いたもの）は、業務か | 業務なら `make_flow: true`。業務でなければ `out_of_scope` に理由（「体制の説明で、手順ではない」）を書き、もう一度 `--draft` を実行する（その項目のページが `unassigned_pages` に理由つきで入る） |
| 次の項目がページの途中から始まる境目（下書きが一覧に出す） | そのページに前の項目の続きが載っていれば両方の分類に残す。載っていなければ前の分類から外す |
| 章をまたぐページ・目次に無い項のページ | カードの見出しを見て、当たる分類の `pages` に足す（2つの分類にまたがるページは両方に） |
| 目次に無い業務（`orphans` に出るまとまり） | 下の「目次に無い業務があるとき」 |

- 目次の項目をそのまま分類にする。**名称・順序・番号を変えない。** まとめない・分けない・言い換えない。
- 各分類に `toc_ref`（目次のどのページのどの文字か）と `hierarchy_id`（業務の木の id）を付ける。
- **ページの割当には、ファイルの番号を書く。目次の番号は刷られた番号なので、そのまま使わない。** `pagemap` の「目次「…」… 13 → M01/p0014」の右を使う。自分で足し引きしない。割り当てたら、分類の先頭のページにその見出しがあることを確かめる（`check_flow.py` が、目次が指すページが割当に入っているか・見出しが隣のページに無いか・見出しがそろってずれていないかを FAIL で見る）。
- 下位資料（手順書・別紙・規程）のページは、業務の木の `refs` に従って、対応する分類に割り当てる。対応が決まらなければ確認事項。
- 目次の上位の見出し（章）は、`make_flow: false` の分類として残す（全体構成の図に階層として出る）。下にフローを描く分類の無い項目（業務でない章）は、`out_of_scope` に理由を書く。

### 目次に無い業務があるとき（`basis: mixed`）

目次のある資料と、目次に無い資料（ばらの手順書・別冊）が混ざっているとき。**目次を正にし、目次に無い業務だけを足す。**

1. 縦軸は、最上位の資料の目次。項目は変えない。
2. `pages.py orphans` で、どの分類にも入っていない内容ページのまとまり（資料 × 見出し）と、結び付きそうな目次の項目の候補を見る。
3. 目次の項目に結び付けるのは、**根拠の文があるとき、または見出しが目次の中で一意に一致するとき**だけ。見出しが一意に一致するものは、`pages.py orphans -w <作業フォルダ> --accept` で機械が結び付ける（業務の木の `refs` と、当たる分類の `pages`）。根拠の文のある候補は、文を読んで、採るものの番号を `--accept C1,C2` で渡す（根拠の文とページは、機械が写す）。目次の資料でない資料は、根拠の文（`tree[].refs` の `evidence`・`sources`）を必ず書く。同じ名前の項目が目次に複数あるときは、見出しだけでは結び付けない。結び付けたら、そのページを当たる分類の `pages` に足す（フローは目次の項目のフローに入る）。
4. 結び付かない業務は、新しい分類として足す: `basis: llm`・`number` は空・`toc_ref` は書かない。名前は原典の見出し・資料名の言葉のままにして、場所を `name_ref` に書く。置き場所は、属する上位の見出しの根拠があればその段の末尾、無ければ最上位の末尾。
5. 足した分類ごとの確認事項（種別「分類」・`flow` にその分類の id）は、機械が決まった形で作る（「目次に無い「備品の貸出」を、1つの業務分類として足しました。このまま 1 つの業務としてよいですか、目次のどれかに含めますか。」）。別の聞き方が要るときだけ、`taxonomy.json` の `questions` に書く（書けば、そちらを使う）。
6. 全体の `basis` を `mixed` にし、`rationale` に、何を足したかを書く。

### 業務分類: 目次に一覧が無いとき（`basis: llm`）

LLM が分類する。次の順で考える。

1. カードの手順を、きっかけ（何が起きたら始まるか）と成果（何ができたら終わるか）でまとめる。「注文を受けてから出荷するまで」「月末に締めてから請求書を送るまで」。
2. 1つの分類は、担当の受け渡しを含んでよい。部門別・資料別・システム別には切らない。
3. 大きさは、1フロー 5〜25 ステップが目安。大きければ、成果物ができる切れ目で分ける。小さすぎる（2〜3 ステップ）ものは、前後の業務に含める。
4. 分類どうしが重ならず（1つの手順は1つの分類に）、漏れない（内容ページがすべてどこかに入る）こと。
5. 名前は、原典の見出し・資料名にある言葉のままにし、その場所を `name_ref` に書く（`heading` 本文の見出し＋ページ／`title` 資料の題名・ファイル名・フォルダ名）。本文の見出しは、`detect_structure.py` の候補（`signals.json` の `body_headings`。ページと文字つき）から探せる。原典に名前が無いときだけ「目的語＋業務」で名付け、`name_ref` は書かない（業務マトリクス一覧に「LLM が命名」と出る）。
5b. **上の段（束ねる分類）は、原典に手がかり（フォルダ名・資料名・章の見出し）があるときだけ作る。** 手がかりを `name_ref` に書く。無ければ1段のままにする（もっともらしい大分類を作らない）。
6. 定常業務と、例外・不定期の業務（エラー対応・年次処理）は分ける。

書くこと:
- `rationale`: 何を単位に分けたか
- 確認事項（種別「分類」・effect「フローの範囲」。重要度は機械が高にする）: 分類の一覧を示し、「この分け方でよいか。別案として◯◯（部門別・資料別など）もある」と問う

### 共通

- 表紙・目次・白紙以外のページは、すべてどれかの分類の `pages` に入れる。入れないページは `unassigned_pages` に理由を書く。
- 2つの業務にまたがるページ（全体の流れの図など）は、両方に入れる。
- **1つの分類の材料は 4 万字（カードの文字数）まで。** `python3 scripts/pages.py plan-flows -w <作業フォルダ>` で見る。超える分類・25 ステップを超えそうな分類は、下位の分類（`F03-1`、`parent: "F03"`）に分ける。原典に節・項があれば、その切れ目で分ける。親の分類は、下位フローへのリンクだけのフローにする（材料は、下位に入れなかった概要のページだけ）。

`python3 scripts/check_flow.py -w <作業フォルダ> --stage structure` を FAIL 0 にする（フローがそろっているかは、この段階では見ない。フロー化の点検 `--stage flow` が見る）。

**利用者に見せる（確認点②）**: 縦軸（`python3 scripts/pages.py rows -w <作業フォルダ>` の出力: 大分類・中分類・分類名の根拠と、対象外にした項目・目次に無く足した分類）、ページ数、資料の結び付き、用語で確かめたいもの。**縦軸はここで確定する。**フロー化はこのあとに始める。利用者がその場にいない（自動で回している）ときは、確認事項に載せて先へ進む。
