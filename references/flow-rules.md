# as-is 業務フロー作成規約（正典）

読取・分類・フロー化・作図・確認事項の決まり。作業の前に全文を読む。機械チェック（`validate.py`・`check_extract.py`・`check_flow.py`・`check_layout.py`）はこの規約の一部を機械で見ているだけで、通っても規約を満たしたことにはならない。

書く JSON の形は `references/schemas.md`（正はスキーマ `assets/schemas/`）。**同じことは、いつも同じ項目に、同じ決め方で書く。** 人によって書く場所や決め方が違うと、あとの工程が拾えず、実行のたびに結果が変わる。迷いやすい所は、この規約に決め方を書いてある（1.14〜1.23）。ここに無い迷いは、自分で決めずに親へ報告する。

レビューで受けた指摘は、該当する節に1行ずつ足す（§7）。足すときは「何を・なぜ」を1行で書く。

## 0. 大原則

- 0.1 **原典に書いてあることだけを図にする。** 書いていないことは補わない。補わないとフローがつながらないときだけ「推定」として置き、必ず確認事項にする。もっともらしく埋めた図は、間違っていても誰も気づけない。
- 0.2 **すべてのノードに出典を付ける。** 資料・ページ・原文の引用の3点。出典を書けないノードは、原典に無いことを書いている。
- 0.3 **as-is だけを書く。** 改善案・あるべき姿・効率化の提案は書かない。原典に「〜する予定」「〜が望ましい」とあっても、現状の手順としては扱わず確認事項にする。
- 0.4 **分からないことは確認事項にする。** 黙って決めない。決めたことは「仮置きした内容」に書く。
- 0.5 **XML は手で書かない。** `flow.json` を書き、`build_drawio.py` で書き出す。図を直すときも `flow.json`（直しの一覧で作ったフローは、直しの一覧）を直す。
- 0.6 **番号は2種類ある。** データの鍵は「ファイルの番号」（`page`＝ファイル名 `pNNNN`）。人に見せるのは「ページに刷られた番号」（`printed_page`）。JSON の `page` には必ずファイルの番号を書く（目次を写した `toc_entries`・`toc_flow_list` の `page` だけは、目次に刷られた番号のまま）。図や一覧に出る番号は、機械が刷られた番号に引き直す。目次の番号・刷られた番号を `page` に書くと、出典が全部ずれる。
- 0.7 **数えること・そろえることは機械に任せる。** ノードの番号、確認事項の番号、目次の番号からページを引くこと、同じ表記を集めること、材料の大きさを測ること。LLM が数えると、実行のたびに変わる。

## 1. 読取（ページカード）

- 1.1 ページ画像を必ず見る。機械抽出の文字だけでカードを書かない。画像の中の文字・図の矢印・画面の項目・手書きの書き込みは、画像にしかない。
- 1.2 機械抽出は突き合わせに使う。画像で読んだ文字が機械抽出と食い違ったら、画像を見直す（読み違いか、機械抽出の順序の乱れか）。
- 1.3 部門名・役職・システム名・帳票名・画面名は、原文の表記のまま書く。「経理」と「経理部」、「上長」と「課長」を勝手にそろえない。
- 1.4 手順（steps）と分岐（decisions）には、原文の引用（quote）を付ける。**原文は写さず、場所を行の番号で指す**（`lines: [開始, 終了]`。番号は `pages.py lines` が見せる、機械抽出を文の単位に切った並び）。引用の文字は機械が入れる（`quotes.py fill`）。LLM が原文を写すと、表記ゆれ・言い換え・継ぎはぎが紛れ、直すたびに結果が変わる。行の番号で指せないもの（画像の中の文字）だけ、いままでどおり引用を写す（1.5）。前の版で作ったカードは、`quotes.py locate --rewrite` で行の番号に引き直す。
- 1.5 画像の中の文字を引用するときは `from_image: true` にし、読んだ文字を `figures[].texts` にも入れる（機械では照合できないので、後の原典照合レビューがここを見る）。
- 1.6 読めない箇所は推測で埋めず、`unreadable` に「どこが・なぜ」を書く。字が小さいページは `crop_page.py` で拡大してから読む。拡大しても読めなければ unreadable。
- 1.7 フロー図のページは、図をそのまま写す（`diagram`）。図のひし形は `decisions` にも書く。図の処理の箱は `steps` に重ねて書かない（フローの出典は、図の箱の id `g1` を引く。手順・分岐が1つも無い図だけのページでは、図の箱も網羅の点検の対象になる）。**箱の中に作業の文が書かれている図（見出し「1 申請」の下に「申請者は、申請書を作成して提出します。」）は、箱の見出しを `diagram` の `label` に、文を `steps` に書く**（文には担当・時期・帳票があり、フローの材料になる。見出しだけの箱は `steps` に書かない）。箱の文字・形（処理／判断／開始・終了／帳票）・レーン・線の向きと線の上の文字。矢じりが無い・線が途中で切れているなど、向きが決まらない線は `uncertain` に書く。
- 1.8 機械抽出にコネクタ（connectors）があるページは、矢印の本数を数えて突き合わせる。図形に貼り付いていない矢印（from / to が空）は機械では追えないので、画像で読む。
- 1.9 1ページに複数の手順があれば、すべて書く。「以下同様」「同上」「前ページと同じ」は、何と同じかを確かめて書く。
- 1.10 手順の主語（担当）が書かれていなければ、空にして `uncertain` に書く。前後のページから類推して入れない。ただし、同じ見出し・同じ番号つきの並びの中で、前の手順に主語があり、あとの手順に別の主語が出てこないときは、その主語を引き継ぐ（「① 経理部は…印刷する。② …電話で確認する。」の②は経理部）。見出しや並びが変わったら引き継がない。
- 1.11 表紙・目次・白紙も、種別を付けたカードを書く（全ページにカードがあることを機械が確かめる）。
- 1.12 プログラムのソース（マクロ・スクリプト・SQL・業務システムのソース）のページは、カードにしない。手順として読まず、アクティビティ図の側で読む（6 章）。マニュアルの手順が使うシステム・ツール（マクロ・クエリを含むブックやファイルの名前、ツールの名前）は、その手順の `system` に書く（帳票としてだけ書かない）。
- 1.13 他ページ・他資料への参照（「別紙3参照」「◯◯マニュアル p.12」）は `cross_refs` に写す。階層の判定と、資料の紐付けの候補に使う。
- 1.14 **ページの種別（`page_type`）は、下の表の上から順に当てはめ、最初に当たったものにする。** 手順や図があるページは、表や説明が一緒にあっても、手順・図を優先する。

  | ページにあるもの | `page_type` |
  | --- | --- |
  | 題名・版・日付だけ | `cover` |
  | 目次・索引 | `toc` |
  | マクロのソース | `code` |
  | 箱と矢印の図（業務の概要表が同じページにあってもよい。表は `figures` に `kind: table` で写す） | `flow_diagram` |
  | 番号つき・箇条書きの手順、または「No・担当・作業」の手順の表 | `procedure` |
  | 画面キャプチャと、その項目・操作の説明 | `screen` |
  | 帳票・様式の見本 | `form` |
  | 表が主（スケジュール・一覧・対応表）で、手順の文が無い | `table` |
  | 業務の全体像・位置づけの説明で、手順が無い | `overview` |
  | 用語・定義・条文・役割の説明・改訂履歴・参考 | `reference` |
  | 何も無い | `blank` |

- 1.15 **`printed_page` には、そのページに刷られたページ番号を、番号だけで書く**（「13」「3-2」「ii」。「- 13 -」「P.13」「13/20」「13 ページ」は、飾りを外して「13」）。刷られていなければ null。前後のページから数えて作らない。1ページずつ「画像を開く → 刷られた番号を書く → カードを書いて保存する」の順で進め、何ページ分もの画像を先に開いてから書かない（1つずれて書いてしまう）。
- 1.16 **補足（注記・※・なお書き・ただし書き・囲み・表の欄外・吹き出し）も読む。補足の中に「誰かが何かをする」が書かれていたら、本文の手順と同じく `steps` に書き、`origin: note` にする**（条件で流れが変わるなら `decisions`）。どの手順に掛かるかが原典から分かれば `applies_to` に書く。本文の中のかっこ書きは本文（`origin: body`）。作業を含まない補足（背景・定義・理由）は `notes` に書く。補足を全部フローに載せる必要はない。落としてはいけないのは、補足の中の作業。
- 1.17 「〜する」「〜してください」と書かれているが、担当が行う作業ではないもの（費用の負担・定義・一般的な注意・結果の説明）は `notes` に書き、`why_not_action` に理由を書く。推奨（「〜が望ましい」「できれば〜」）も手順にせず `notes` に書き、`uncertain` に「現状の手順として行われているか」を書く。例示（「例えば〜」）は、前の手順の説明なので手順にせず `notes` に書く（理由は「例示」）。例示にしか書かれていない作業は手順にする。
- 1.18 項目の id（`s1`・`d1`・`g1`・`n1`）は、カードの中で重ならないように上から振る。フローの出典がこの id を引くので、カードを直すときも、すでにある id は変えない（足すときは次の番号）。
- 1.19 ページの中の小見出しは、手順・分岐の `section` に書く。ページの見出しは `title`、章・節は `section_path`。ページの上下の柱（資料名・章名の繰り返し）は書かない（刷られた番号だけを `printed_page` に書く）。
- 1.20 担当が手順の文に無く、**同じページの表**（概要表・担当表）に書かれているときは、`actor` に入れてよい（その表を `figures` に写す）。別のページにしか無いときは、空にして `uncertain` に書く。
- 1.21 条件つきの作業（「不備がある場合は差し戻す」）は、`steps` に `condition` つきで書く。`decisions` に書くのは、原典が分かれ目として書いているもの（両側の行き先が書かれている・図にひし形がある・「〜か否か」）だけ。片側しか書かれていない条件を `decisions` にしない（フロー化のときに判断ノードにし、書かれていない側を推定にする）。
- 1.22 `uncertain` に書くのは、フローを描くときに決めなければならないこと（担当・順序・分岐の行き先・条件の境界・開始と終了）。1件＝1つの決められないこと。感想・改善案・原典の書きぶりへの指摘は書かない。
- 1.23 条文・規程は、「誰が・何を・する（しなければならない・ものとする）」の条を `steps` に書く（`no` に条番号）。目的・定義・適用範囲の条は `notes`。役割の定義（「経理責任者を置く」）は `notes`。日程表・スケジュール表（「上旬: 請求処理」）は `figures` に `kind: table`（`columns`・`rows`）で写し、表の中の作業名を `steps` にしない。
- 1.24 **手順は、原文の1文（箇条書き・番号つきなら1項目）を1つにする。** 1文に動作がいくつあっても分けない（「見積を取り、契約のあと、納品を確かめます。」は1手順）。分けるのは、文の途中で担当が変わるとき（「担当者が作成し、課長が承認する」）と、条件が一部にだけ掛かるときだけ。同じページを2回読ませると、ここがいちばん割れる（同じ 10 ページで、手順の数が合ったのは 6 ページ）。
- 1.25 非表示のスライド・シート（ページの一覧に「（非表示）」と出る）もカードを書く（非表示であることは、機械が資料の一覧から知る）。現行の手順とは限らないので、フローに入れるかは分類のときに決める（入れないなら `unassigned_pages` に理由。確認事項「資料の版」には機械が載せる）。
- 1.26 ページの頭の「概要」の表（目的・内容・タイミング・担当者など）の「内容」欄の文は、手順にしない: `notes` に書き、`why_not_action` に「概要の表の文。手順は、業務の流れ以下に書かれている」と書く。**ただし、その文に書かれた作業・分かれ目が、業務の流れ以下（同じページの図の箱・手順、続くページの見出し）のどこにも出てこないときは、その文を手順（分岐）にする**（フローの作業のノードは、カードの手順・分岐を出典に引く。補足にすると、原典に書かれた作業なのに、フローでは推定の扱いになる）。そのときは `uncertain` に「概要の表にだけ書かれている。業務の流れのどこに入るか」を書く。表の「担当者」「タイミング」は、手順の担当・フローのきっかけの根拠に使う。

## 2. 階層と業務分類

- 2.1 フローを作る前に、入力が階層構造かを判定する（`hierarchy.json`）。見るのは、フォルダの階層・ファイル名の番号・目次・見出し番号・PDF のしおり・PowerPoint のセクション・Excel のシート構成・資料間の参照。
- 2.2 判定は「あり／一部あり／なし」と根拠で書く。根拠どうしが食い違うとき（フォルダの分け方と目次の章立てが違う など）は、どちらを採ったかを書き、確認事項にする。
- 2.3 資料間の関係（上位→下位・別紙・根拠・参照・版違い・同一）は、根拠にした文（原文）とページを添える。根拠の無い関係は書かない。
- 2.4 **目次に業務フロー（業務）の一覧があれば、それに準拠する。** 名称・順序・番号を目次のままにする。まとめ直さない・分け直さない・言い換えない。
- 2.5 目次が複数の資料にあるときは、最上位の資料（全体マニュアル・業務一覧）の目次を軸にし、下位資料の目次はその下の階層にする。
- 2.6 目次に一覧が無いときだけ、LLM が分類する。分類の単位は「きっかけ（開始）から成果（終了）まで」がひとまとまりになる業務。部門別・資料別・システム別に切らない（担当の受け渡しが切れてしまう）。
- 2.7 LLM が分類したときは、分類の考え方・採らなかった別案を書き、種別「分類」の確認事項にして利用者に確かめる。
- 2.8 表紙・目次・白紙以外のすべてのページを、どれかの分類に割り当てる。割り当てないページ（改訂履歴・奥付・用語集 など）は理由を書く。
- 2.9 1つのページが2つの業務にまたがるときは、両方に割り当てる。
- 2.10 1つのフローが 25 ステップを超えるときは、下位フローに分けて親からリンクする（原典に節・項があれば、その切れ目で分ける）。きっかけが別々の手続きが1つの節に並んでいるとき（開始の直後に、どの場面かで分かれる）は、25 ステップ以下でも、原典の項ごとに下位フローへ分ける（レーンは1列なので、並んだ枝が縦に積まれ、線が何度も交わる）。分けたら、業務分類（`taxonomy.json`）と目次の業務一覧（`hierarchy.json` の `toc_flow_list`）に下位の分類を足す。親のリンクのノードの出典は、概要のページの1行（下位フローの手順と重ねない。3.18）。
- 2.11 版違いの資料は、どれが現行かを決めつけない。全部読んで、食い違いは確認事項にする。
- 2.12 **骨格は業務の木（業務領域 › 業務 › 手順）。資料は木にならない**（1つの様式を複数の業務が使う、規程が複数のマニュアルの根拠になる）ので、資料どうしを親子にして終わりにせず、**資料の節を業務の木に結び付ける**（`tree[].refs`）。上位資料が1行で書いた業務を下位資料が詳しくしているときは、下位資料の側を `rel: details` にし、根拠の文とページを書く。
- 2.13 全資料に役割（規程・全体マニュアル・手順書・別紙や様式・ツール）を付ける（`docs[].role`）。どの業務にも結び付けない資料は、対象外の理由を書く。
- 2.14 紐付けの種類は決まったものだけ: 資料の節→業務（書いている／詳しくしている）、資料→資料（上位・別紙・根拠・参照・版違い・同一）、業務→業務（続く）。新しい種類を作らない。語彙を増やすと、実行のたびに形が変わり、人が確かめきれなくなる。
- 2.15 紐付けの候補は機械が出す（`detect_structure.py`・`pages.py links`。別の業務を番号と名前で名指しした参照の文も「続く」の候補に出る）。1件ずつ根拠の文を読んで採否を決める（採るものの番号だけを `pages.py links --accept R1,S2` で渡す。根拠の文とページは機械が写す。見出しが目次の中で一意に一致するページは `pages.py orphans --accept` で機械が結び付ける）。**根拠の文を書けない紐付けは作らない。** 決められないものは確認事項（種別「階層」）。違うものを結ぶ誤りは、結ばない誤りより害が大きく、気づきにくい。
- 2.16 ある業務の成果を別の業務が受け取るとき（資料をまたぐ受け渡しを含む）は、業務どうしの「続く」（`sequence`）に、根拠の文とページを付けて書く。
- 2.17 担当・システム・帳票の名前は、用語の正本（`glossary.json`）で1つに決める。別の表記を寄せるのは、原典で同じものと確かめられたときだけ（根拠を書く）。確かめられなければ別の用語のままにして、確認事項（種別「用語」）。下書きは `pages.py terms --draft` が、寄せずに全部を別々の用語として書く。
- 2.18 目次に書かれたページ番号は、刷られた番号。ページの割当（`pages`）にはファイルの番号を書く。対応は `pages.py pagemap` が出す。自分で足し引きしない。割り当てたら、分類の先頭のページにその見出しがあることを確かめる（節が2ページ以上あると、1ページずれても目次の指すページは割当に入ったままになる。見出しがそろってずれていれば FAIL）。
- 2.19 1つの分類の材料（割り当てたページのカードの文字数）は 4 万字まで。超えると1つのエージェントで読み切れないので、原典の節・項の切れ目で下位の分類に分ける（`pages.py plan-flows`）。
- 2.20 **業務分類は、業務マトリクス一覧の縦軸（1行＝1フロー）になる。** 目次があれば、縦軸は最上位の資料の目次の項目のまま。目次の資料でない資料・目次の範囲に入らないページを、目次の項目に結び付けるのは、**根拠の文があるとき、または見出しが目次の中で一意に一致するとき**だけ（目次の資料でない資料は、根拠の文を必ず書く）。同じ名前の項目が目次に複数あるとき（章ごとに出てくる「記録の作成」など）は、見出しだけでは結び付けない。候補は `pages.py orphans` が出す。
- 2.21 目次に無い業務は、新しい分類として足す（`basis: llm`・番号なし。全体の `basis` は `mixed`）。置き場所は、属する上位の見出しの根拠があればその段の末尾、無ければ最上位の末尾（目次の並びを崩さない）。足した分類ごとに、その分類を指す確認事項（種別「分類」・`flow` に分類の id）を1件置く。全体で1件にまとめない（どの分類を足したのかが、利用者に見えなくなる）。**この確認事項は、機械が決まった形で作る**（「目次に無い「…」を、1つの業務分類として足しました。…」。LLM がその分類を指す問いを書けば、そちらを使う）。
- 2.22 フローを描かない目次の項目は、束ねる見出し（下にフローを描く分類がある）か、対象外（業務でない: 総則・体制の説明・予定表・用語集）のどちらか。対象外は `out_of_scope` に理由を書き、そのページを `unassigned_pages` に入れる。どちらでもない `make_flow: false` は FAIL。目次の項目は、どれも「フローを描く・下位フローに分けた・束ねる見出し・上位のフローに含む・対象外」のどれかになる（業務マトリクス一覧の「縦軸の根拠」に全件が出る）。
- 2.23 LLM が分類したときの名前は、原典の見出し・資料名の言葉のままにし、その場所を `name_ref` に書く（`heading` 本文の見出し／`title` 資料の題名・ファイル名・フォルダ名）。原典に名前が無いときだけ LLM が名付け、その分け方を確認事項で確かめる（名前だけを聞く問いにしない。5.8）。**上の段（束ねる分類）は、原典に手がかり（フォルダ名・資料名・章の見出し）があるときだけ作る。** 無ければ1段のままにする（もっともらしい大分類を作らない）。
- 2.24 目次に準拠した分類（名称・順序・番号・目次の場所・ページの割当）は、機械が下書きする（`pages.py taxonomy --draft`）。LLM が決めるのは、フローを描くか・対象外か、2つの分類にまたがるページ、目次に無い業務だけ。下書きの名称・順序・番号を書き換えない。

## 3. フロー化

- 3.1 ノードは「誰が・何を・どうする」の1作業。ラベルは「目的語＋動詞」（「注文書を受領する」）。**動詞で終える**（体言止めにしない。「…に連携」ではなく「…に連携する」。別のフローへ続く箱も「◯◯に進む」）。最後に、相手・物の名前を置くときは、かっこ書きにする（「メールを送る（Outlook）」）。機械が、動詞で終わらない名前を FAIL にする（末尾のかっこ書きは、除いて見る）。原典の言葉を使う。 `detail`（条件・時期・補足）は 120 字まで。図には、機械がかっこで包んで出す（動詞で終わる名前と、見分けられるように。自分では、かっこを付けない）。要点だけを書き、原文は出典の引用に任せる（長い補足は箱を縦に伸ばし、図が読めなくなる）。条件の一覧・金額の表・例の一覧のように、縮めると中身が読めなくなるもの（金額ごとの必要書類の表、例外として認める場合の一覧）は、`reference` に原典の言い回しで全部書く（図の箱には出ず、ノードにマウスを乗せたときの説明と出典対応表に出る）。`detail` には「必要書類は金額による（表）」のように、あることだけを書く。
- 3.2 レーンは原典に出てくる担当（部門・役職・システム・社外）。原典の呼び方のままにする。同じに見える2つの呼び方（「上長」と「課長」）は、同じと確かめられるまで別のレーンにするか、片方に寄せて確認事項にする（ノードに推定の印は付けない。3.15）。
- 3.3 順序は原典の順。**原典の順が一般的な流れと違っていても（支払のあとに承認、など）、原典のままにする**（よくある流れに並べ直さない。おかしいと思ったら、確認事項で聞く）。資料をまたぐ順序（資料 A の手順と資料 B の手順のどちらが先か）が書かれていなければ、推定＋確認事項にする。
- 3.4 判断ノードは、名前を問いの形（「〜か」）で書き、出口が2本以上・すべてにラベル。原典に片方しか書かれていなければ、もう片方は推定で置いて確認事項にする（「不備あり→差し戻す」だけ書かれていて「不備なし」の先が無い、など）。**書かれていない側のラベルと、判断の名前の「？」は、機械が決める**（`apply_edits.py`）: ラベルは、書かれた側の反対の語（ある↔ない・あり↔なし・する↔しない・以上↔未満・一致↔不一致 など。表に無ければ「その他」）。「？」で終わる名前は「〜か」にする。
- 3.5 条件で分かれるところは判断ノードにする。プロセスから線を2本出して済ませない。
- 3.6 開始と終了を置く。開始条件（きっかけ）と終了条件（成果）を `start_condition` / `end_condition` に書く。きっかけは、原典に無ければ空にして確認事項。終了条件は、原典に成果が書かれていなければ、原典の流れの最後の作業を「〜したとき」の形で書く（どの作業で終わるかが原典から決まらないときだけ、空にして確認事項）。**最後の作業からの終了条件は、機械が入れる**（`apply_edits.py`。直しの一覧の `end_condition` を空にしておく。終了に入る線が推定でない作業 1 つから来るときだけ。LLM が書くのは、原典に成果が書かれているときだけ）。開始条件の手がかり（最初の作業の条件・時期を書いた補足）は、下書きに出る。
- 3.7 すべてのノードが開始からたどれ、終了にたどり着くこと。行き止まり（差し戻したあと・エラーのあと）は、原典に続きが無ければ推定の終了を置いて確認事項にする。**分岐の先の「差し戻す」作業のあとは、機械が推定の終了と確認事項にする**（次の作業へは進ませない。差し戻しを受ける側の箱は足さない。原典に、差し戻したあとの手順が書かれていれば、`connect` でその手順へつなぐ）。
- 3.8 システムが自動で行う処理は `system` ノード（S-。「自動で」と書かれ、使うシステムが分かる手順は、機械が下書きでそのシステムのレーンに置く）。人がシステムを操作する作業は `process` で、どのシステムかは札（`systems`）に出る。札は、出典に引いた手順の `system` と、その手順の文に出てくるシステム名（用語の正本にあるもの）から、機械が付ける（`renumber.py`・`apply_edits.py`）。補足（`detail`）にシステム名を重ねて書かない。 プログラム（マクロ・スクリプト）が手元にあり、その起動点とマニュアルの手順を紐付けたとき（システム台帳）は、機械が、その手順を引く作業のすぐあとにシステム処理の箱（S-）を1つ置く（`activity` にアクティビティ図の番号。図では「▶ A-02-1」）。フローの側で、同じ処理の箱を足さない。プログラムの中身は、業務フローに描かない。
- 3.9 帳票・ファイル・データは `file` ノード（F-）にして、使うプロセスに付ける（参照するなら in、作るなら out）。
- 3.10 ノードの番号は P-001・S-001・F-001・D-001（判断）・SUB-001。書くときは仮の番号でよく、`renumber.py` が時系列の順に振り直す。
- 3.11 **カードの手順・分岐は、すべてフローに入れる。** ノードの出典に、もとにしたカードの項目の id を `item` で書く。入れない手順・分岐は `excluded_items` に理由を書く（ほかのフローで描く・資料間で食い違うので確認事項にした・同じ作業の重複、など）。どちらでもないものは FAIL。1つの手順に動作がいくつもあるときは、ノードを分けてよい（どのノードも同じ `item` を引く）。ページごと使わないとき（画面項目の説明だけ、用語の定義だけ）は `unused_pages` に理由を書く。
- 3.12 同じ作業が複数の資料に書かれているときは、1つのノードにまとめて出典を両方付ける。内容が食い違うとき: 担当・順序・作業の有無が違えば、まとめずに確認事項にする（種別「資料間の矛盾」。担当の違う作業をまとめたときは、機械がまとめ先の担当に置き、その問いを作る）。値（金額の基準・日付・件数）だけが違えば、確認事項にしない（答えても、図の形は変わらない。5.8）。箱は 1 つにして、補足に両方の値を書く（「翌月10日。規程では、毎月25日」）。もう一方の資料の手順は、まとめるか、対象外にして理由を書く。**書き方は機械が決まった形にする**（直しの一覧: `merge` の `values` に資料ごとの値を書くと、補足を「まとめ先の値。〈資料の題名〉では、〈値〉」で書く。`exclude` の `same_as`（同じ作業をほかの項目で入れた）・`flow`（ほかのフローで描く）で、理由を決まった形で書く）。
- 3.13 マニュアルの記述とプログラムの動きが食い違うとき（マニュアルは CSV で保存、プログラムは Excel で保存 など）・マニュアルに無い処理をプログラムがしているときは、どちらにも合わせず、確認事項（種別「プログラム」）にする。業務フローはマニュアルのとおり、アクティビティ図はプログラムのとおりに描く。
- 3.14 ほかの業務分類へ続くところは `subprocess` ノードにして、続き先のフローを `link_flow` に書く。リンクの出典は、続くことが書かれた文のあるページ（続き先の分類のページでもよい。下位フローでは、上位の分類のページ（節の概要のページなど）でもよい）。リンクのノードの補足に「手順は下位フローに描く」とは書かない（図に「→ 別ページ」と出る）。
- 3.15 推定で置いたノード・線は `inferred: true` にし、それを指す確認事項を必ず付ける。レーンだけを仮に決めたノードは、推定にしない（3.21）。**カードの手順・分岐を出典に引くノード（`sources[].item` がある）は、推定にしない**（作業は原典にある）。囲み・注記から起こした作業、「〜が重要です」「〜できます」と書かれていて現状行っているかが分からない作業、原典に順や時期が書かれていない作業も、ノードには印を付けず、前後の線を推定にして確認事項で聞く。原典に無いノード（場面で分ける判断 など。差し戻しを受ける側の作業は足さない: 3.7）だけを推定にし、その出典には `item` を書かない（ページと引用だけ）。**作業のノードの印は、機械が出典から付ける**（`renumber.py`: `item` を1つも引かない作業のノードが推定）。LLM が印を付けると、同じ種類のノードで有無が割れる。線の印は LLM が付ける。
- 3.16 出典の `page` はファイルの番号（カードの `page` と同じ）。刷られた番号や目次の番号を書かない。
- 3.17 補足の中の作業（カードの `origin: note` の手順）も、本文の手順と同じくノードにする。どの手順の前後かが原典から決まらなければ、推定で置いて確認事項にする。
- 3.18 上位の資料と下位の資料で粒度が違うとき（上位は1行、下位は手順）は、上位のフローに下位のフローへのリンク（`subprocess`）を置き、詳細は下位のフローだけに描く。**同じ手順を上位と下位の両方に描かない。** 粒度が同じで重なるときだけ、1つのノードに出典を両方付ける（3.12）。
- 3.19 レーン名・帳票名は、用語の正本（`glossary.json`）の名前を使う。正本に無い呼び方が原典にあったら、自分で足さずに親へ報告する。
- 3.20 「続く」（`hierarchy.json` の `sequence`）とされた業務のフローには、続き先へのリンク（`subprocess`）を置く。そのフローを下位フローに分けたときは、続く作業を描いた下位フローに置く（上位フローに重ねて置かない）。
- 3.21 手順の文に担当が無く（カードの `actor` が空）、どのレーンかが原典から1つに決まらないとき、レーンは仮に決める。ノードは推定（`inferred`）にしない（作業そのものは原典にある。推定の印は、原典に無いノード・線だけに使う）。代わりに、そのフローの中で「次の作業を行うのは A ですか、B ですか」の確認事項を**1件**書き、対象のノードを全部 `nodes` に並べる（図では、どのノードにも確認事項の番号が付く）。承認・確認・指示を受ける相手（「課長の承認を得てから発注します」の課長）のノードは、相手のレーンに置く（担当は原典にある。「X の承認を得る」だけの手順は、機械が下書きで X のレーンに置く。ほかの作業と 1 文になっていれば、`split` で分ける）。ノードの補足に「担当の記載なし」「原典の文に主語なし」とは書かない（問いに書いてあり、図では確認事項の番号で分かる）。
- 3.22 **処理時間（分）の数字を、LLM は作らない。** 業務マトリクス一覧の作業ごとの処理時間は、人が入れた値が正。人の値が無い所にだけ、機械が、仮の値を入れる。仮の値は、基準の表（ブックのシート「処理時間の基準」。動作の種類 × 量（小・中・大）の分）を引く式で、数字は表からだけ来る。LLM が決めるのは、表を引く鍵だけ: 人の作業の箱（`process`）ごとに、**動作の種類**（`action`）を、決まった 12 語から 1 つ選ぶ（入力する／作成する／確認する／承認する／提出・回付する／受け取る／出力する／連絡する／計算する／調べる／保管する／その他）。箱の名前の動詞が、何をする動きかで選ぶ（照合する・点検する → 確認する／登録する・記入する・システムで実行する → 入力する／回収する → 受け取る／差し戻す・送付する → 提出・回付する／電話で確かめる・依頼する・報告する → 連絡する／集計する → 計算する）。1 つの箱に 2 つの動きがあれば、時間のかかるほう。どれにも当たらなければ「その他」（仮の値は、表の「その他」の行の、決めの値。既定は、中で 5 分。語は、ほかの業務でも出てから足す）。判断・システム処理・別のフローへ続く箱は、機械が決める（判断は、決めの値で 2 分 — 読んで、どちらへ進むかを決める時間。前の作業に含めて数えるなら、表を 0 に直す。自動の処理は、人の時間でないので 0 分。別のフローは、行き先で数えるので 0 分 — 数を入れると、二重に数える）。**最初の出力から、すべての箱に時間が出る**（空のセルは無い。式のセルには、計算の結果も保存するので、計算をしない表示 — プレビュー・保護ビュー — でも、値が出る。基準の表の無いテンプレートには、既定のテンプレートから、基準の表・書式・処理時間の欄を補う）。**処理時間を出すのは、業務のフロー（業務マトリクス一覧）だけ。** プログラムの中身（アクティビティ図・プログラムのノード一覧）には出さない（人の時間でない。業務の見直しの前と後を比べるのは、業務のフロー）。**量**（`volume`）は、ふつう書かない: 機械が、同じページの手順（カードの s1・s2…）を 3 つ以上まとめた箱・見る帳票（`direction: in`）が 2 つ以上の箱を「大」、ほかを「中」にする（出典の数では数えない。同じ作業が、概要・図・詳しい手順の 3 か所に書かれているだけの箱が「大」になるため。作る帳票も数えない。1 つ見て 1 つ作るのは、ふつうの作業）。資料から量が言えるときだけ、理由つきで変える（「ボタンを押すだけ」→ 小／「全件を 1 件ずつ照合する」→ 大）。**「特大」**は、時間・日の単位でかかる作業に、LLM が、理由つきで付ける（機械は付けない）。資料から、そう読めるときだけ: 年・半期に 1 回、全体をまとめ上げる作業（年次の計画づくり・期末の書類一式）／全件を 1 つずつ扱う作業（全員分の精算・在庫の数え上げ）／期間をかけると書いてある作業。迷ったら付けない（「大」のまま）。理由の無い「特大」は FAIL。基準の表の「特大」の列は、とくに粗い目安で、業務マトリクスでは、まだ仮の値の「特大」のセルに色が付く（人が、先に時間を入れる所。数を打つと、消える）。理由は、時間のセルのコメントと「業務フローのノード一覧」に出る。動作の種類の無い箱は「その他」の行を引く（点検は WARN。古い作業フォルダを止めない）。人が入れた値・件数・基準の表の直しは、`build_matrix.py` が、書き出す前にブックから `times.json` に取り込み、書き出しで戻す（**ブックに書き込んだ時間を、書き出し直しで消さない**。いまあるブックを読めないときは、上書きせずに止まる）。同じ作業名の箱が 2 つ以上あるフローでは、値に、担当と直前の箱を控えておき、番号がずれても、担当 → 直前の箱の順に絞って、もとの作業に付け替える。作業名が変わった箱の値は、当てたまま WARN で見直しを促し、箱が無くなった値は、`times.json` に残して WARN で挙げる。合計は、その行の全作業の合計（分岐の両側を足す。ふつうの流れだけの合計は、枝に印を付ける決まりが無いので、出さない）。待ち時間・件数との掛け算は、扱わない（件数は、人が入れる欄だけを置く。処理時間の合計の左）。既定の表の数は、目安（裏付けのある数ではない）。使う側の実態に合わせて直す前提で、表にもそう書く。

## 4. 作図（draw.io）

- 4.1 スタイルは所定テンプレートのものだけを使う（`template_styles.json`）。色・線種・形を足さない。
- 4.2 レーンは列、時系列は上から下。レーンの並びは、やり取りの多い担当を隣にする。システムのレーンは右端。
- 4.3 **出典は、枠の外に出す。** 箱・ひし形のすぐ下・真ん中の線の右に、小さい灰色の字で「業務マニュアル p.3」（資料の題名とページ）と書く（1か所1行。「…」で切らない。幅を超える行は、折る）。枠の中には入れない（長い出典で、ひし形が縦に伸びる・字が切れる）。ひし形の中は、番号と条件だけ。条件の文は、機械が、ひし形の形に合わせて折る（上下の細い所ほど、行を短く。文節の切れ目らしい所で折り、行の頭に読点・閉じかっこを置かない）。ひし形は、文が収まるいちばん低い高さにする（テンプレートの高さが下限）。出典の分だけ、行は高く、列は広くなる（機械が、列ごとに、いちばん長い出典が収まる幅にする。レーンの幅は、テンプレートの幅が下限）。右へ出て下へ折れる線は、出典の右で折る。出典の字が、箱・線・ほかの出典と重なれば、配置の点検が FAIL にする。ページは資料に刷られた番号（PowerPoint はスライド番号、Excel はシート名とセル「請求管理「手順」シート C2」）。ファイルの何枚目かは出さない。番号の無いページは「表紙」「目次」のように種別で、資料全体に番号が無ければ先頭から数えた番号で出る（出典対応表の資料一覧にそう書かれる）。**資料は、題名で書く**（`hierarchy.json` の `docs[].title`。表紙の題名を写す。書いていなければ、表紙のカードの見出し → ファイル名から拡張子を外したもの。題名が重なる資料は、ファイル名を添える）。資料ID（M01）は、機械が読み込んだ順に振った番号で、担当者には通じないので、納品物（図・業務マトリクス一覧・確認事項一覧・出典対応表・照合シート）には出さない。点検の記録（チェック_*.txt）だけは ID で書く（作業フォルダのページのファイルを引くため）。資料のファイルの場所は、図の 1 ページ目と「資料一覧」で引ける。 表紙・裏表紙は、番号が文字として入っていても種別（「表紙」「裏表紙」）で書く（表紙の絵に隠れて、紙面では見えないことがある）。
- 4.4 推定は赤い破線。確認事項の番号（Q-012）をノードの右肩と、線のラベルに付ける。
- 4.5 1ページ目に全体構成（業務分類の階層・結び付く資料・業務どうしの「続く」・資料の一覧と役割と関係）を置き、各フローへリンクする。
- 4.6 書き出した図は PNG にして全ページ目で見る。線がノードを貫く・重なって見分けられない・文字があふれる、は `flow.json` のレーンの順・ノードの順・ラベルの長さを直して書き出し直す。
- 4.7 draw.io の図を手で直さない。直したら `check_flow.py` が JSON との不一致を FAIL にする。
- 4.8 判断から出る線のラベルは短く書く（「あり／なし」「5万円以上／未満」。12 字まで）。条件の中身は判断ノードの文言に書く。1つの判断の出口は4本まで（図は下・左・右にしか出せない。超えるときは判断を2段に分ける）。
- 4.9 **業務マトリクス一覧（xlsx）は、図と同じデータから機械で作る（`build_matrix.py`）。LLM は書かない・直さない。** 1行＝1フロー、列は作業を枝ごとに続けて並べたもの（作業の行のすぐ下に、作業ごとの処理時間（分）の行が付く。3.22）。縦軸の大分類・中分類は、分類の段を上から詰めて入れる（1 段なら大分類に名前・中分類は「—」。3 段以上は、中分類に下の段を「›」でつなぐ。大分類そのものは作らない — 2.23）。見出しは、業務の資料として通る言葉にする（開始条件・終了条件。印は `{きっかけ}`・`{成果}` のまま）。プログラム用のシート（プログラムのノード一覧・図にしない手続き・用語対応）は、中身が無ければ入れない。起動点の一覧は、アクティビティ図の1ページ目にだけ置く（既定の様式には入れない）。出典・確認事項の番号・推定の印は、図と同じものが出る。直すときは `flow.json`・`taxonomy.json` を直して、図と一緒に書き出し直す（手で直したブック・書き出し直していないブックは、`check_flow.py --stage matrix` が FAIL にする。人が入れる処理時間・件数・基準の表の数は別で、ブックが正。書き出し直しても残る）。表に収めるために作業名を縮めない・言い換えない（原典の言葉のまま。長ければ `detail` に移す決まりは図と同じ）。
- 4.10 出どころも行き先も違う線どうしが、同じ所を重なって走る・端どうしがつながって見える図は、出さない（`check_layout.py` が FAIL にする）。読む人が、別の箱へ進むと読むため。線の通り道は、機械が、ほかの線と重ならない所から選ぶ（同じ行き先の線は、合流してよい）。通り道が足りないときは、箱・分岐を減らすか、レーンの順・ノードの順を入れ替える。
- 4.11 **アクティビティ図は、分かれた道を横に並べる**（業務フローの図は、所定のテンプレートの配置のまま。レーンに1列）。機械が決める。図を手で動かさない。
  - ふつうの流れ（終了まで続く、長い方の道）は、まっすぐ下。条件に当たったときの側・エラーの側・途中で終わる側は、右の列。3つ以上に分かれる振り分けは、右へ順に並べる。
  - 条件に当たったときだけ行う短い処理（箱 3 つまで）は右の列に出し、当たらない側の線を、まっすぐ下に引く（箱を回り込む線をなくす）。
  - 分かれた道は、合流する箱の上で1本にまとまる。繰り返しは、中身を下に続け、戻る線だけを、その列の左に通す。
  - 途中で終わる所（「途中で終わる」「プログラムを止める」）は、抜ける所ごとに、すぐそばに終了の丸を置く（1つの丸へ、長い線を集めない）。
  - レーン（操作者／プログラム／外部）はそのまま。列は1レーンに 4 つまで（超える分は、いちばん右の列に縦に並ぶ）。
  - **安全網**: 横に並べたページが、配置の点検と同じ検査（箱の重なり・線が箱を貫く・線どうしの重なり）に1つでも当たれば、列を減らして描き直し、最後は縦一列に戻す（書き出しのときに、そのページの番号が出る）。
- 4.12 **納品物の様式は、テンプレートで決める。** 業務フロー・アクティビティ図（draw.io）と、業務マトリクス一覧・確認事項一覧（xlsx）の、欄と見た目は、`assets/` のテンプレートのもの。中身は、機械が同じデータから流し込む。LLM は、テンプレートにも、書き出した本にも書かない。お客様の様式に合わせるときは、テンプレートを差し替える（守る形と差し替え方は `template-spec.md`）。決まりを外れたテンプレートでは、書き出さない。

## 5. 確認事項

- 5.1 1件＝1つの問い。答えが「はい／いいえ」か、短い語で返せる形に書く（「〜はどうなっていますか」ではなく「〜は A ですか、B ですか」）。
- 5.2 何を仮置きしたかを書く。答えが来たとき、どこを直せばよいかが分かるようにする（対象のフロー・ノード・線）。
- 5.3 出典（どの資料の何ページを読んでそう思ったか）と、聞く相手（原典から分かる範囲で）を書く。
- 5.4 重要度は 高＝フローの範囲や、複数の箱・線が変わる／中＝箱 1 つ・線 1 本・担当 1 つが変わる（仮置きで描けている）／低＝図への付け足し（帳票・システムの札・開始条件・終了条件）が変わる。**重要度は機械が決める**（LLM は書かない。書いても使わない）: 答えで変わる所（effect）と指す箱の数から、担当 → 中、システム・帳票 → 低、フローの範囲 → 高（指すのが開始・終了だけなら低）、箱・順序・分岐 → 指す箱が 2 つ以上なら高・ほか（箱 1 つ・線 1 本）は中。LLM が決めるのは、問いの文と effect。
- 5.5 種別: 読取不能・記載なし・資料間の矛盾・資料間の順序・分類・階層・用語・システム・プログラム・資料の版。同じ資料の中の食い違い（概要の図と手順の文で順が違う、など）も「資料間の矛盾」にする。 「システム」は、どの作業でどのシステム・プログラムを使うか（紐付け）。「プログラム」は、プログラムの中身（マニュアルとの食い違い・実行時に決まる名前）。
- 5.6 同じ問いを重ねて出さない。1つのフローの中で同じ趣旨の問いが複数のノードに掛かるとき（担当の書かれていない作業が並ぶ、など）は、1件にまとめて対象を `nodes` に並べる。ノードごとに同じ文面の問いを並べない（答える人が同じことを何度も読むことになる）。別のフローと重なる問いは、親がそろえる。機械が作る問い（m-）と同じ所を指し、答えで変わる所（effect）も同じ問いを、直しの一覧に書かない（点検が WARN）。
- 5.7 文章で書く項目（質問・仮置き・理由・考え方・補足）の中に、ページ番号・ノードの番号・確認事項の id を書かない。資料を ID（M01）で呼ばない（題名で書く。4.3。箱の名前・開始条件・終了条件も同じ。点検が WARN）。ページは `sources`、対象は `node`・`nodes`・`edge` に書く。番号は機械が引き直し・振り直すので、文の中に書いた番号は古くなって納品物に残る。
- 5.8 **確認事項にするのは、答えによって図が変わる問いだけ。** 変わる所を、`effect` に 1 つ書く: `箱`（作業の有無）／`順序`（線・順）／`分岐`（条件の有無・行き先）／`担当`（レーン）／`システム・帳票`（使うシステムの札・紙・プログラムとの紐付け）／`フローの範囲`（分け方・階層・開始条件・終了条件・図にする範囲）。どれにも当たらない問いは、確認事項にしない: (1) 値だけを聞く問い（金額・期限・件数・宛先・保存先の名前が、いくつか・何か）、(2) 書かれていることが、いまも同じかの確かめ、(3) 名前・呼び方・表記だけが変わる問い（業務の名前はこれでよいか・プログラムの中の名前の読み方）。値は、原典のまま箱・補足に書く（資料どうしで値が違えば、両方を補足に書く。3.12）。名前の推定は、一覧（用語の対応）に色つきで出る。資料どうしで、箱・順・担当が食い違うときは、その食い違いを聞く（図が変わる）。機械が、`effect` の無い確認事項を FAIL に、値だけ・現況の確かめに見える言い回しを WARN にする。確認事項一覧には、「答えで変わる所」の列で出る。

## 6. プログラムの読取とアクティビティ図

入力にプログラム（マクロ付きの Excel・Access の書き出し・スクリプト・SQL・業務システムのソース）があるときの決まり。進め方は `code-guide.md`。

- 6.1 **プログラムは実行しない。** 文字として読むだけ。Office のファイルは、マクロを抜いた写しだけを開く。認証情報（接続文字列のパスワード・キー・トークン）は、ページを書く前に機械が伏せる。伏せる前の値を、どこにも書かない。閲覧のロックが掛かったマクロは、利用者に確かめてから読む。
- 6.2 層を分ける。業務フロー（誰が・何を）には、プログラムが動く所に箱を1つだけ置く。プログラムの中身（プログラムが・何を）は、アクティビティ図にだけ描く。**同じ処理を両方に描かない**（上位と下位で二重に描かない 3.18 と同じ考え）。
- 6.3 システムは、用語の正本のシステムを、すべてシステム台帳（`structure/systems.json`）に載せる。プログラムの無いシステムも載せる（一覧と札に出る）。
- 6.4 起動点（プログラムの外から始まる所: ボタン・イベント・自動実行・定時実行・ショートカット・スクリプトの本体）は、機械がプログラムから全部拾う。図にしないのは、理由が決まった4つ（中身が空／画面の表示の制御だけ／開発・試験用／ほかの起動点と同じ処理を呼ぶだけ）に当たるものだけ。理由が中身と合っているかは、機械が確かめる（中身が空なのに実行文がある・表示だけなのに入出力がある・呼ぶだけなのにほかの文がある → FAIL。開発・試験用は、中身からは決まらないので見ない）。
- 6.5 紐付け（起動点 ⇔ マニュアルの手順）の根拠は3種類だけ: 名指し（手順の文に、ボタン名・マクロ名・メッセージの文がある）／入出力の一致（手順の帳票名が、プログラムの読む・作るものの名前と一致する）／推定（根拠の文が無い。確認事項が付く）。名指し・入出力の一致は、その文字が両側にあることを機械が確かめる。**根拠の文字を作らない。** 根拠も見立ても無ければ、紐付けない（2.15 と同じ）。
- 6.6 紐付けるのは、その起動点を動かす作業（ボタンを押す・マクロを実行する・バッチを流す手順）。プログラムの出力を使うだけの作業には、紐付けない。
- 6.7 紐付けの結果は3つに分かれ、どれも一覧（アクティビティ図の1ページ目の起動点の一覧・システム一覧）に出る: 紐付いた起動点（業務フローに箱が出る）／業務フローに出てこない起動点（確認事項「どの業務で使っていますか」）／プログラムの無いシステム（札だけ）。
- 6.8 アクティビティ図は、起動点ごとに1枚。呼ばれる手続きは、呼ぶ所が1か所だけで箱が 8 個以下なら呼ぶ側の図に入れ、ほかは別の図にして、呼び出しの箱からリンクする（機械が決める）。1枚は 25 箱まで。超えるときは、畳める分岐を畳む → 1つの操作の前半と後半をまとめる → 同じ触る先への続く書き込みをまとめる、の順で減らす。それでも超えれば、超えたままにする（箱を減らすために、対象外を足さない）。図にする文が1つも無い手続き（異常終了の手続きなど）は、図にせず、呼ぶ側の呼び出しを対象外にする。
- 6.9 **骨組みは機械、名付けとまとめは LLM。** 分岐・繰り返し・呼び出し・入出力は、機械がソースから取り出す。LLM は、下書きに「直しの一覧」（名付ける・まとめる・分ける・畳む・対象外にする・図に戻す）だけを書く。図のデータ・XML は書かない。
- 6.10 **行の網羅**: プログラムの実行文は、どれも、どれかの箱か「対象外」に1回だけ入る（機械が確かめる）。対象外にできるのは、理由が決まった語（画面の更新の制御／変数の準備／ログ／後片付け／エラーの扱いの設定／書式・表示の調整／開発・試験用）に当たる文だけ。シート・ファイル・テーブルに書く文は、対象外にできない。「変数の準備」は、手続きの中だけで使う変数に、定数か、ほかの変数の値をそのまま入れるだけの文（機械が決める。右が引数なしの関数かもしれない名前のとき・左がモジュールの変数やプロパティのときは、残す。LLM が構造を読む言語では、木）と、最後の行・件数・長さ・今日の日時を取るだけの文・繰り返しの位置を進めるだけの文（VBA では機械が決める。1 つ進める文は、その変数をセルの行・列の番号にだけ使うとき。ほかの言語は、直しの一覧で足す）。書式だけの文（字・塗り・罫線・表示の形・列の幅）は、シートへの書き込みと数えず、VBA では機械が「書式・表示の調整」で対象外にする（業務の意味があれば、直しの一覧の include で図に戻す）。金額・数量・日付の計算、あとで表示する・書く件数を数える文、シートや画面の項目の値を読む文、戻り値・引数・レコードや画面の項目に入れる文は、当たらない。ログ・後片付け・画面の更新の制御・エラーの扱いの設定は、機械が決める。直しの一覧で足すのは、機械が見分けられなかった「取るだけの文」「書式・表示の調整」と、「開発・試験用」だけで、当たる文は対象外にする。
- 6.11 **分岐の網羅**: 分岐・繰り返しは、どれも、判断（か、繰り返す箱）として描くか、理由つきで畳む。**業務の条件（データの値・利用者の選択・件数・日付・金額のしきい値）は、畳まない。** 畳んでよいのは技術的な分岐だけで、理由は決まった語（保存先・ファイルの有無の確認／型や空の確認／エラー番号の振り分け／書式・表示の調整／再試行・待ち合わせ／配列・文字の加工）から選ぶ。中に、操作者とのやり取り・別の図の呼び出し・抜ける所がある分岐は、技術的でも畳まない（機械も、畳ませない）。それらが無い技術的な分岐は、箱の数に関わらず畳む。
- 6.12 **アクティビティ図を読むのは、業務部門の担当。** 箱・判断・出口・補足・図の名前は、業務の言葉で書く。担当の目に見える名前（シート・ファイル・テーブル・帳票・画面・ボタンの文字・メッセージ）は、ソースの文字のまま「」で書く。かぎかっこの中には、その箱が受け持つ行の文字列の中の文字か、その箱の入出力の名前だけを書く（機械が確かめる。補足も同じ）。ソースに書かれた数字（しきい値・税率）は、そのまま箱か補足に出す。
- 6.13 実行するときに決まるもの（変数のファイル名・組み立てた SQL）は、推測しない。機械が「＜変数名＞」「（実行時に決まる）」と書き、確認事項にする。
- 6.14 利用者にメッセージを出す・処理を止めるエラー処理は描く（エラーの設定の所に「このあとの処理でエラーが起きたか」の判断を置く）。エラーを無視する設定・後片付けだけのエラー処理は、対象外にする。プログラムごと終える文（VBA の `End`・`STOP RUN`・異常終了の呼び出し・`System.exit`）のあとは、呼んだ側に戻さず、「終了（プログラムを止める）」につなぐ。
- 6.15 コメントは、名付けの手がかりに使ってよい。処理と食い違えば、確認事項にする。コメントにしてある処理・どの起動点からも呼ばれていない手続きは、描かない（呼ばれていない手続きは、確認事項に出る）。
- 6.16 **as-is だけ。** 不具合の指摘・改善案・あるべき姿を、箱にも補足にも確認事項にも書かない。
- 6.17 構造の取り出し方（機械が構文から／機械が行の形から／LLM の読取）は、図と一覧に出す。LLM が構造を読んだ図は、原典照合で全部の箱を見る。機械が構文を読めない言語では、LLM が書くのは、ブロックの種類と行の範囲だけ（`code/<まとまり>.tree.json`）。機械が、範囲・入れ子・行の網羅・見出しの語・名前の所在を確かめ、1つでも合わなければ構造にしない。読む範囲（どの起動点から描くか）は、利用者と決める。読まないと決めたまとまりは、理由を書き、確認事項にする。
- 6.18 プログラムのページは、カード・業務分類・階層の資料の役割（`docs`）の対象にしない。ソースだけの資料は、業務の木でなく、システム台帳に結び付く。
- 6.19 Access は、書き出したテキスト（`access-export.md`）を読む。Access のファイルそのものは開かない。フォーム・レポートの起動点は、**定義でイベントに割り当ててあるものだけ**（コード・マクロ・関数の式・埋め込みマクロ）。割り当ての無い手続きは、起動点にせず、「どの起動点からも呼ばれていない手続き」として確認事項にする。起動点の名前には、ボタンの文字・項目に付いたラベルを、定義の文字のまま使う。
- 6.20 Access のマクロは、アクションの並びを手続きとして読む（構造の段は「行の形から」）。保存してあるクエリを動かす文には、そのクエリの SQL が読む・書くテーブルを付け、出典にクエリの定義の行を足す。集計の関数（DLookup・DCount ほか）の相手が、保存してあるクエリのときも同じ（テーブルと呼ばない）。リンクしたテーブルの接続先を決めるだけの文（`.Connect` に接続の文字を入れる）は、読み書きに数えない。接続の文字のうち、Access のリンクの形（`Text;DSN=…;DATABASE=…`）の DSN は、取り込みの定義の名前で、読む先ではない。書き出せなかったもの・書き出しから読み取れなかったもの（新しい形だけのマクロなど）は、推測で描かず、確認事項にする。テーブルは、定義（項目・型・リンク先）だけを持つ。行の中身は、書き出しにも入れない。
- 6.21 マニュアルが入力に無く、プログラムだけのときは、業務フローを作らない。アクティビティ図と、システム・起動点の一覧を出し、「どの業務の、どの作業で使うか」を、システムごとに1つの確認事項にする。
- 6.22 式の中で、ほかの手続き（関数）を呼んでいる文は、文そのものを箱に残し、呼び出しは、その前に置く（関数の結果をシートに書く文・メッセージを出す文・メニューを出す文が、呼び先の中身に置き換わって消えないように）。呼んだ結果を変数に入れる・足すだけの文は、呼び出しの箱1つにする（箱の名前に、何のために呼ぶかを書く）。値を取るだけのプロパティは、図に出さない。
- 6.23 まとめる（merge）のは、1つの操作の前半と後半だけ（写す → 貼る／選ぶ → 消す／開く → 読む）。分ける（split）のは、1つのまとまりに、触る先の違う書き込みが入っているときだけ。機械が対象外にした文を図に戻す（include）のは、そのプログラムの業務の出力そのもののときだけ。
- 6.24 条件の無い繰り返し（`Do … Loop`・`while (true)`）は、判断にしない。頭で抜ける道がソースに無いので、中の最後から中の頭へ戻る線で表し、終わるのは中の「抜ける」だけにする。
- 6.25 枠組みが、起動点の手続きの前に呼ぶ手続き（受け口の前に値を用意する宣言・前処理の宣言）は、図の先頭に、呼び出しとして入れる（木の起動点の `before`）。受け口の本体だけを描くと、その前の読み込みと、そこで起きる例外が、図から落ちる。起動点の名前（URL など）の前半が別の行にあるときは、つないだ名前を書く（`also`）。
- 6.26 別のシートを出す・選ぶ・隠す文は、読み書きが無くても、まとまりを切る境にする（別のシートの作業が、1つの箱に混ざらない）。写す先を引数に書く文は、先頭の1つが「書く」、その引数の中で読むセルは「読む」。
- 6.27 プログラムを止める所（異常終了の手続きの呼び出し・`End`・`STOP RUN`）は、「終了（プログラムを止める）」につなぐ。手続きの途中で呼んだ側に戻る「終了（途中で終わる）」と、分けて描く。
- 6.28 **プログラムの中だけの名前（変数・項目・手続き・モジュール・定数・部品の名前）は、箱に書かない。** 意味を業務の言葉に直して書く。言い換えは、用語の対応（`structure/code_terms.json`）に1回だけ書き、どの図でも同じ言葉を使う。根拠（コメント／定義／つづり＝推定／不明）を付ける。つづりから読んだ言葉は、推定として、一覧の「プログラムの用語対応」に色つきで出る（確認事項にはしない。名前が変わるだけで、図の形は変わらない。5.8）。意味が読めない名前は、推測せず、「不明」として載せ、もとの名前のまま「」で書く（確認事項にはしない。一覧に「不明」で出る。機械が、箱・補足・出口・図の名前に、プログラムの中の名前がそのまま出ていれば FAIL にする）。
- 6.29 もとのコードへの手がかりは、箱の右下（枠の外）の出典（資料・モジュール・行。機械が付ける。切らない）と、業務マトリクス一覧の「プログラムの用語対応」「プログラムのノード一覧」に置く。箱の中に、もとの名前を並べて書かない。繰り返す箱の、ソースの条件も、図に出さない（何について繰り返すかを、名前か補足に書く）。
- 6.30 **名前の無い箱が残る図は、納品物に入れない。** 書き出すと、題とページの名前に【下書き】と出て、1ページ目の一覧にも出る。全部に名前を付けるか、その図を出さないと利用者に伝える（一部の図だけを仕上げて、残りを下書きのまま同じファイルで渡さない）。
- 6.31 同じ共通の処理（別の図）を 3 回以上続けて呼ぶ並び（値を取る → 共通の処理に渡す、の繰り返し）は、25 箱を超える図に限り、1つの箱にまとめてよい。切れ目は、ソースのコメントの見出し。呼び出しが 3 回に満たない見出しは、となりの見出しと合わせる（間に分岐・繰り返しがあれば、合わせない）。箱には、呼ぶ先の図の番号と回数を、機械が付ける。行の網羅は、まとめた箱が、その並びの行をすべて受け持つことで保つ。
- 6.32 **共通の処理のうち、補助だけをする手続きは、図にしない。** 機械が候補を出す（その手続きと、そこから呼ぶ手続きのどれにも、入出力・操作者とのやり取り・プログラムの終了が無い）。図にしないのは、候補のうち、台帳（`folded_procedures`）に、決まった理由（探す・取り出す／寸法・位置・単位の計算／文字・日付の整形／保存先・名前の組み立て／ログの表示／型・空・エラーの種類の確かめ）を付けて書いたものだけ。**業務の計算・判定（金額・税・件数・期限・区分）をする手続きと、画面に見える動きをする手続きは、図にする**（6.11 と同じ線）。呼び出しは、呼ぶ側の図の、ふつうの箱になる（何のために呼ぶかを名付ける。ログの表示を呼ぶ行は、機械が対象外にする）。番号は詰めない。図にしない手続きと理由は、一覧（業務マトリクス一覧の「プログラムの図にしない手続き」）に出す。起動点の図は、必ず作る（6.4）。
- 6.33 **呼び出しの箱は、その流れで起きることを言う。** 呼ばれる側が、渡る値によって、することが変わるとき（番号が渡らなければ、読まずに空のものを返す、など）は、行き先の図の名前を、どちらの場合にも当てはまる言い方にする（「得意先を用意する（番号があれば読む）」。「読む」と言い切らない）。呼ぶ側で、どちらになるかがソースから決まるとき（受け口のアドレスに番号が無い・定数を渡している）は、呼び出しの箱に、その流れで起きることを名付ける（「空の得意先を用意する」。補足に、そう決まる理由）。決まらないときは、行き先の図の名前のまま。
- 6.34 **機械が付ける名前も、動詞で終える。** やり取りの箱は「「…」と、メッセージを出す」「「…」と、入力を求める」「フォーム「…」を開く」（見せる文字は、前に置く）。外部の箱は「メールを送る（Outlook）」「外部プログラムを動かす（…）」（相手の名前は、かっこ書き）。別のフローへ続く箱の既定の名前は「◯◯に進む」。判断は「〜か」（繰り返しの判断は、動詞で終えてもよい）。開始・終了と、紙（シート・ファイル・テーブル）は、物の名前のまま。
