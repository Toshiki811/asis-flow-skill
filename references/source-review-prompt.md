# 原典照合レビューの指示文（作り方を知らない別のエージェント用）

機械チェック FAIL 0 のあと、納品前に必ず通す最終工程。機械は「引用の文字が原典にあるか」しか見ない。**その引用が本当にそのノードの根拠になっているか、ページにあるのにフローに無い手順はないか、線のつなぎ方は原典どおりか**は、原典を見た人にしか分からない。作った本人は自分の読みを疑えないので、作り方を知らない別のエージェントに、原典とフローだけを渡して照合させる。

consulting-pptx-skill の「フレッシュアイ・レビュー」と同じ考え方（作り方を伏せる・採否表にする・全部は直さない）を、原典との照合に当てたもの。

## 使い方

1. フローごとに、`python3 scripts/make_compare.py -w <作業フォルダ>` が作る `out/照合シート_<フローID>.pdf` を用意する。出典ページが 12 を超えるフローは、レビュー担当が1回で読み切れるように `_1.pdf`・`_2.pdf`… に分かれる（`--max-pages` で変えられる。1本は 1〜数 MB。レビュー担当が開けないときは `--max-pages` を小さくして作り直す）。
2. 下の指示文を、**このスキルの名前・作り方・ページカードを一切伝えずに**、別のエージェント（Agent ツール、または新しいセッション）に渡す。照合シートの PDF 1本につき1エージェント。`{…}` は次のように置き換える。

   | 置き換える所 | 入れるもの |
   | --- | --- |
   | `{COMPARE_PDF}` | `<作業フォルダ>/out/照合シート_<フローID>.pdf`（分かれていれば `_1.pdf`・`_2.pdf`… を1本ずつ） |
   | `{PAGES_DIR}` | `<作業フォルダ>/pages/`（この下に資料ごとのフォルダ `M01/` があり、`pNNNN.png` が入っている） |
   | `{FLOW_JSON}` | `<作業フォルダ>/flows/<フローID>.flow.json` |
   | `{REVIEW_OUT}` | `<作業フォルダ>/reports/review_<フローID>.json`（分かれていれば `_1`・`_2`…）。**`review/` には書かせない**（`review/` は、親が採否を決めて書く採否表の場所。形が違うものを置くと、点検と進み具合が狂う） |

3. `python3 scripts/review.py draft -w <作業フォルダ>` で、レビュー担当の報告から採否表の下書き `review/<フローID>.review.json` を作る（判定と指摘は機械が写す。親は写さない。分けた PDF の分は1つにまとめる。報告の形が崩れていれば、どのファイルかを出して止まるので、その担当に直させる）。
   親は、指摘ごとに `decision`（採用／不採用／保留）と `action`（対応か、採らない理由）だけを書く。ほかの項目は書き換えない（点検が、報告と同じかを見る）。原典の読みが割れる指摘は、どちらかに決めずに確認事項に足す。
4. 採用分を反映する。直しの一覧で作ったフローは、直しの一覧に足して `apply_edits.py` をやり直す（番号は前の `flow.json` から引き継ぎ、足した箱には新しい番号が付く）。JSON をまるごと書いたフローは `flow.json` を直す（番号は変えない。`renumber.py` は、採否表のあるフローの番号を振り直さない）。そのあと工程7（書き出し）をやり直す。
5. `python3 scripts/check_flow.py -w <作業フォルダ> --stage review` を FAIL 0 にする: 採否表の無いフロー・採否か対応の無い指摘・報告と違う判定や指摘・採用したのに反映していない図（図のデータが採否表より古い）・**支持率（支持 ÷ 開始・終了を除く全ノード）が 95% 未満**。支持率が足りなければ、不支持・一部支持の多いフローを直して、照合し直す。
   `python3 scripts/build_reports.py -w <作業フォルダ>` が、採否表を `out/原典照合レビュー_採否表.md` にまとめ、支持率を出す。判定の無いノード・レビューをしていないフローがあれば、採否表の先頭に出る。
6. 何度も出る種類の指摘は、`flow-rules.md` に1行足す。

### 差分照合（照合のあとに図を直したとき）

採否表には、照合したときの図の写し（`reviewed`。箱ごとの種類・名前・レーン・補足・出典のページ・前後の線）が残る。照合のあとに図を直すと（採用した指摘の反映も含む）、点検（`--stage review`）が、写しと違う箱・足した箱を「照合したあとに変わった・足した箱」として FAIL にする。図全体を照合し直さず、その箱だけを照合し直す。

1. `python3 scripts/make_compare.py -w <作業フォルダ> --only <フローID> --nodes <点検が挙げた箱の番号>` で、`out/差分照合シート_<フローID>.pdf` を作る（1 ページ目に、照合し直す箱と、その名前・レーン・出典・前後の線。続けて、その箱の出典ページだけ）。
2. 上と同じく、作り方を知らない別のエージェントに渡す。`{COMPARE_PDF}` は差分照合シート、`{REVIEW_OUT}` は `<作業フォルダ>/reports/review_<フローID>_差分<N>.json`（N は 1、2…。前の報告を上書きしない）。指示文の最後に、次の 1 段落を足す:
   「この照合シートは、差分照合です。1 ページ目に挙げた箱だけを判定してください（`verdicts` は、その箱だけ）。ほかの箱は、前の照合で済んでいます。ページ側の判定（B）とつなぎの判定（C）は、挙げた箱と、その前後の線について行ってください。」
3. `python3 scripts/review.py draft -w <作業フォルダ> --only <フローID>`。差分照合の報告が判定した箱は、前の判定を置き換え、写しも、その箱だけ取り直す。新しい指摘には、採否と対応を書く。
4. 採用した指摘は、図に反映する（反映しないと、点検が「その指摘の報告を受けたときのまま」と FAIL にする）。反映して箱が変われば、また、その箱だけを照合し直す。

写しの無い前の版の採否表（この仕組みの前に作ったもの）は、点検が WARN にする。いまの図を照合済みと認めるとき・全体を照合し直したときは、利用者が決めて `python3 scripts/review.py snapshot -w <作業フォルダ> --only <フローID> --assume-current` で写しを作る（写した日が `reviewed.assumed` に残る）。

レビュー用エージェントに渡してよいもの: 照合シートの PDF、出典ページの画像（`pages/<資料ID>/pNNNN.png`）、`flows/<フローID>.flow.json`。
渡さないもの: ページカード、`flow-rules.md`、このスキルの説明。（渡すと、作った側と同じ読み方をしてしまう）
確認事項は、図の情報欄と `flow.json` に載っているので、レビュー担当に見えてよい（推定で置いた所の印と同じ扱い）。

親は、照合シートも出典の画像も開かない（フローが多いと文脈があふれる）。受け取るのは、レビュー担当が書いたファイルだけ。

### 採否表の形式

| # | フロー | ノード・ページ | 指摘（原文のまま） | 種別 | 採否 | 対応／理由 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | F03 | 経費精算チェックシート p.1 | 表の3行目「不備があれば申請者に差し戻す」の担当は経理部。フローでは P-004 が経理部で合っているが、差し戻し先の申請者の作業 P-005 は原典に無い | 不支持 | 不採用 | 推定として赤破線・Q-010 で確認済み |
| 2 | F03 | 支払処理手順 p.2 | ②は「口座情報の誤りは」と条件つき。P-010 の前に判断が要るのでは | 抜け | 採用 | D-003「口座情報の誤りか」を推定で足し、確認事項を追加 |

表に出るのは指摘（`findings`）だけ。ノードごとの判定（`verdicts`）は、件数と支持率にまとめて表の上に出る。種別は「一部支持」「不支持」「抜け（ページにあるのにフローに無い）」「つなぎ（順序・分岐・担当の誤り）」「表記」。採否は「採用」「不採用」「保留」。上の表は `out/原典照合レビュー_採否表.md` に出る形で、もとは `review/<フローID>.review.json`。

## 指示文（ここからコピー）

あなたは業務フロー図の検証担当です。業務マニュアルのページ（原典）と、それをもとに描かれた業務フローを照らし合わせ、**フローが原典どおりかどうか**を1か所ずつ判定してください。フローがどう作られたかは知らされません。推測する必要もありません。原典に書いてあるかどうかだけで判定します。

### 見るもの
- 照合シート `{COMPARE_PDF}`（1ページが原典の1ページに対応。右が原典のページ、左がフロー図と、そのページを根拠にしたノードの一覧。赤枠が該当ノード。「補足の中の作業」の印は、注記などから起こしたノード）。**Read で全ページを順に見てください。** 分冊（`_1`・`_2`…）のときは、渡された1冊に載っているページとノードだけを判定します。
- 原典のページ画像 `{PAGES_DIR}`（照合シートの右側で字が小さいときは、こちらを Read で開く）
- フローの定義 `{FLOW_JSON}`（ノード・線・レーン・各ノードの出典と引用）

ほかのファイルは読まないでください。

### やること

**A. ノードごとの判定（全ノード）**
各ノードについて、出典のページを見て次のどれかを付ける。
- **支持**: そのページに、そのノードの内容（誰が・何を・どうする）が書いてある
- **一部支持**: 書いてあるが、担当・対象・条件のどれかがページと違う、またはページに無いことが足されている
- **不支持**: そのページに、その内容が書いていない

「推定」と印の付いたノード（`inferred: true`）は、原典に無いことを承知で置いたもの。原典に無いこと自体は指摘しなくてよい。ただし、**原典に書いてあるのに推定になっている**場合と、**推定の置き方が原典と矛盾する**場合は指摘する。

確認事項（`questions`）が指しているノード（`node`・`nodes`）と線（`edge`）は、そこに書かれた点（担当が原典に書かれていない、など）を仮に決めたことを承知で置いたもの。**確認事項に書かれている点そのもの**は、指摘しなくてよく、判定も下げない。確認事項に書かれていない違いだけを指摘する。

**B. ページ側からの判定（全ページ）**
各ページを読み、**ページに書いてある作業・分岐・条件で、フローに無いもの**を挙げる。画像の中の文字、図の矢印、表の行も見る。
とくに、**注記（※）・なお書き・ただし書き・囲み・表の欄外・吹き出しの中に書かれた作業**（「〜すること」「〜してください」「〜を行う」）が抜けていないかを、1つずつ確かめる。本文でない所の作業は落ちやすい。
照合シートの最後のページに「カードにあるのに、フローに入れなかった手順・分岐（理由）」と「読取のときに、作業として扱わなかった補足（理由）」が載っている。その理由が原典に照らして妥当かも見る（載っているものを「抜け」として重ねて挙げない）。

**B'. ページ番号の判定（全ページ）**
照合シートの見出しに書かれたページ番号（例「経費精算マニュアル p.13」。資料の題名とページ）が、右の原典の画像に刷られているページ番号と同じかを確かめる。違えば「ページ違い」として挙げる。番号が刷られていないページは、見出しが「表紙」「目次」などになっている。Excel はシート名で書かれている。

**C. つなぎの判定**
- 順序: 線の向きは原典の順か。原典に順が書かれていないのに、決めて線を引いていないか。原典の順が一般的な流れと違っていても（支払のあとに承認、など）、原典の順が正しい。よくある流れに並べ直していたら「つなぎ」で挙げる
- 分岐: 判断ノードの条件と行き先は原典どおりか。原典の図にある矢印が抜けていないか
- 担当: ノードのレーンは、原典でその作業をする人と同じか。原典の呼び方（「上長」「課長」）と違う名前になっていないか
- 行き止まり・戻り: 差し戻し・エラー・再実行のあとの流れは原典どおりか
- 開始条件・終了条件: 図の情報欄の「開始:」「終了:」が、原典に書かれた時期・きっかけ・成果のとおりか（原典に無い時期・成果を書いていないか）。違えば「つなぎ」で挙げる（`target` は「開始条件」「終了条件」）

### 出力形式

結果を `{REVIEW_OUT}` に、次の形の JSON で書いてください（返事は件数だけを1行で）。

```json
{
  "verdicts": [{"node": "P-006", "verdict": "支持", "evidence": "「2. 経理部は、支払データを作成し、経理課長の確認を受ける。」"}],
  "findings": [{"kind": "抜け", "target": "支払処理手順 p.2", "text": "②は「口座情報の誤りは」と条件つき。P-010 の前に判断が要るのでは"}]
}
```

- `verdicts`: 開始・終了を除く全ノード。`verdict` は 支持／一部支持／不支持。`evidence` は原典の該当箇所の引用（不支持・一部支持は、何が違うかを1文で添える）
- `findings`: 指摘。`kind` は 一部支持／不支持／抜け（ページにあるのにフローに無い）／つなぎ（順序・分岐・担当の誤り）／表記（ページ違いを含む）。`target` はノード・線・ページ（**ページは照合シートの見出しの書き方で**。画像のファイル名 `pNNNN` の番号は、ページ番号と違うことがある）。`text` は何が違うかと、どう直すか

原典の引用は、ページから写してください（フローの定義に書いてある引用を写し返さない）。判定に迷う箇所は、迷った理由を書いて「一部支持」にしてください。指摘が無いノードも `verdicts` には載せます。
