# 中間データの形

**人・LLM・サブエージェントが書くもの**: ページカード・階層の判定・用語の正本・システム台帳・ブロックの木・業務分類・フローの直しの一覧・アクティビティ図の直しの一覧・用語の対応・報告・採否表。
**機械が書いて、読み戻すもの**: フロー（`flow.json`。既定は `apply_edits.py` が書く。まるごと書く方式では LLM）・アクティビティ図（`activity.json`。`activity.py` が書く）・確認事項の台帳・人が入れた処理時間・人が埋める欄に入れた値・列の対応・図の配置・棚卸し・機械抽出。人が値を入れて返す表のブック（業務マトリクス一覧・確認事項一覧）は、形をテンプレートと列の対応（`columns.json`）で決め、読み戻すときに確かめる。どちらも、下の表の形で書き、作った直後・読む所で形を確かめる（崩れていれば止まる）。
**機械だけが書いて読むもの**は、[内部の形式](#内部の形式機械だけが書いて読む)に一覧がある（形は作り直しとの一致で確かめる）。

**形はスキーマ（`assets/schemas/*.schema.json`）が正。** この文書の項目表は、スキーマから `python3 scripts/validate.py --doc` で作っている（手で直さない）。
スキーマに無い項目を足すと FAIL になる。書きたいことがどの項目にも当てはまらないときは、項目を作らずに親へ報告する（`hints`・`for_parent`）。同じ中身を人によって別の項目に書くと、あとの工程が拾えず、実行のたびに結果が変わる。
資料 ID（`M01`）・フロー ID（`F03`）・ノード番号（`P-003`）・Q 番号（`Q-001`）の書式は、共通の定義（`common.schema.json`）から引く。決まった語（種別・答えで変わる所・動作の種類・量・図にしない理由）も、スキーマが正（スクリプトは、スキーマから読む）。

書いたら自分で確かめる: `python3 scripts/validate.py -w <作業フォルダ> --kind card --only M01 --pages 13-24`（フローは `--kind flow --only F03`）。
実例は `evals/fixture_expected/`（架空の「経費精算」マニュアル一式を読んだ結果）。迷ったらそれを見る。

## 番号の2種類（ここを取り違えない）

| 番号 | どこにあるか | 使いみち |
| --- | --- | --- |
| **ファイルの番号**（`page`） | ファイル名 `pNNNN`。資料の先頭から数えた番号 | データの鍵。カード・分類・フローの `page` には、必ずこれを書く |
| **刷られた番号**（`printed_page`） | ページの紙面（「13」「3-2」。「- 13 -」は飾りを外して「13」と書く） | 人に見せる番号。図・出典対応表・確認事項一覧には、機械がこちらを引いて出す |

表紙を数えない資料では、2つが 1 ずれる（`p0014` に「13」と刷ってある）。`page` に刷られた番号を書くと、出典が全部1ページずれる。
目次に書かれた番号は刷られた番号なので、そのまま `page` に使わない。`python3 scripts/pages.py pagemap -w <作業フォルダ>` が「目次の番号 → ファイルの番号」を出す。足し引きは機械に任せる。
Excel にはページ番号が無い。出典はシート名（引用の位置が引ければセルも）で出る。`page` はシートごとのファイルの番号。

## ページカード `cards/<資料ID>/pNNNN.json`

1ページ1枚。全ページに書く（表紙・目次・白紙も）。1ページ読むごとに保存する。

```json
{
  "doc_id": "M01", "page": 5, "printed_page": null,
  "page_type": "procedure",
  "title": "2. 承認",
  "section_path": ["2. 承認"],
  "summary": "上長が照合し、金額で承認者が分かれる。不備は差し戻す。5万円以上は承認の前に見積書の添付を確認する（注記）。",
  "actors": ["上長", "課長", "部長", "申請者"], "systems": [], "documents": ["領収書", "見積書"],
  "steps": [
    {"id": "s1", "no": 1, "actor": "上長", "action": "申請内容と領収書を照合する", "system": "", "inputs": ["領収書"], "outputs": [],
     "condition": "", "section": "", "lines": [3, 3], "quote": "上長は、申請内容と領収書を照合する。", "from_image": false, "origin": "body"},
    {"id": "s5", "actor": "", "action": "見積書の添付を確認する", "system": "", "inputs": ["見積書"], "outputs": [],
     "condition": "5万円以上の申請。承認の前", "section": "", "quote": "5万円以上の申請は、承認の前に見積書の添付を確認すること。",
     "from_image": false, "origin": "note", "applies_to": "s3"}
  ],
  "decisions": [
    {"id": "d1", "question": "申請金額が5万円以上か",
     "branches": [{"label": "5万円未満", "to": "課長が承認"}, {"label": "5万円以上", "to": "部長が承認"}],
     "section": "", "quote": "申請金額が5万円未満の場合は課長が承認する。5万円以上の場合は部長が承認する。", "from_image": false, "origin": "body"}
  ],
  "diagram": {"nodes": [], "edges": []},
  "figures": [],
  "notes": [],
  "toc_entries": [], "cross_refs": [], "unreadable": [],
  "uncertain": [{"what": "見積書の添付を確認する担当", "why": "注記（※）に主語が無い"}]
}
```

引用（`quote`）は、行の番号（`lines`。`pages.py lines` が見せる番号）を書けば、機械が入れる（`quotes.py fill`。手で写さない）。手で書くのは、画像の中の文字（`from_image: true`）のときだけ。`summary`・`confidence` は書かなくてよい（機械は読まない）。

`s5` は注記（※）の中に書かれた作業。補足の中の作業は `steps` に `origin: note` で書く（フローのノードになる）。
作業を含まない補足は `notes` に書く。「〜する」と書かれているのに作業でないもの（費用の負担・定義・注意喚起）は、理由を `why_not_action` に書く:

```json
"notes": [{"id": "n1", "about": "振込手数料", "text": "振込手数料は会社が負担する。", "quote": "なお、振込手数料は会社が負担します。",
           "from_image": false, "why_not_action": "費用の負担先の定めで、担当が行う作業ではない"}]
```

## 階層の判定 `structure/hierarchy.json`

工程3で書き、工程5（全ページを読んだあと）で紐付けを確定する。

```json
{
  "is_hierarchical": "yes",
  "basis": ["folder", "toc", "cross_ref"],
  "rationale": "フォルダが「00_全体」「01_手順書」「02_規程」に分かれ、全体マニュアル「経費精算業務マニュアル」の目次に業務が3つ並ぶ。…",
  "tree": [
    {"id": "H1", "level": 1, "title": "経費精算業務", "kind": "domain", "source": "toc",
     "refs": [{"doc_id": "M01", "pages": [1, 2], "rel": "describes"}],
     "children": [
       {"id": "H1.3", "level": 2, "title": "支払処理", "kind": "process", "source": "toc",
        "refs": [{"doc_id": "M01", "pages": [6], "rel": "describes"},
                 {"doc_id": "M02", "pages": [1, 2], "rel": "details",
                  "evidence": "経理部は、承認済みの申請を下の画面で確認し、支払データを登録する。",
                  "sources": [{"doc_id": "M01", "page": 6}, {"doc_id": "M02", "page": 1}]}],
        "children": []}]}
  ],
  "docs": [{"doc_id": "M01", "role": "manual", "title": "経費精算業務マニュアル"}, {"doc_id": "M02", "role": "procedure", "title": "支払処理手順"},
           {"doc_id": "M04", "role": "regulation", "title": "経費精算規程"}],
  "doc_relations": [
    {"from": "M04", "to": "M01", "type": "basis_of", "evidence": "この規程の細則は、経費精算業務マニュアルに定める。",
     "sources": [{"doc_id": "M04", "page": 3}]}
  ],
  "sequence": [
    {"from": "H1.2", "to": "H1.3", "evidence": "経理部は、承認済みの申請を下の画面で確認し、支払データを登録する。",
     "sources": [{"doc_id": "M01", "page": 6}]}
  ],
  "toc_flow_list": {"found": true, "source": [{"doc_id": "M01", "pages": [2]}],
                    "entries": [{"number": "1", "title": "経費申請", "level": 1, "page": 3}]},
  "questions": []
}
```

資料どうしを親子にするだけでは、フローの親子に落とせない。**「上位資料のこの節を、この資料が詳しくしている」を、業務の木の `refs`（`rel: details`）に書く。**
紐付けの種類は、下の表にあるものだけ。新しい種類を作らない。根拠の文（原文）とページを書けない紐付けは作らない。

## 用語の正本 `glossary.json`

担当・システム・帳票の名前を1つに決める。フローのレーン名・帳票名は、ここの `name` から選ぶ（無い名前は FAIL）。
材料は `python3 scripts/pages.py terms -w <作業フォルダ>`（カードに出てくる表記と、同じものかもしれない組）。

```json
{
  "terms": [
    {"kind": "actor", "name": "経理部", "aliases": ["経理"], "evidence": "支払処理手順の表紙に「経理部（以下、経理）」とある"},
    {"kind": "actor", "name": "上長", "aliases": []},
    {"kind": "actor", "name": "課長", "aliases": []},
    {"kind": "document", "name": "領収書", "aliases": []}
  ],
  "questions": []
}
```

別の表記を `aliases` に寄せるのは、原典で同じものと確かめられたときだけ（根拠を `evidence` に）。「上長」と「課長」のように、同じかどうか原典から決まらないものは、別の用語のままにして確認事項（種別「用語」）にする。違うものを同じとして結ぶと、別の担当が1人に化け、あとから気づけない。

## システム台帳 `structure/systems.json`

システム（基幹・EUC・スクリプト）の一覧と、プログラムの起動点 ⇔ マニュアルの手順の紐付け。プログラム（マクロ付きのブック・ソースのファイル）が入力にあるときに書く。下書きは `python3 scripts/systems.py draft` が書く（用語の正本のシステムと、プログラムのまとまり）。進め方は `references/code-guide.md`。

```json
{
  "systems": [
    {"id": "SYS-01", "name": "販売管理システム", "kind": "core", "docs": []},
    {"id": "SYS-02", "name": "月次集計マクロ", "kind": "euc_excel", "docs": ["M05"]}
  ],
  "links": [
    {"entry": "M05.e1", "step": "M01.12.s3", "basis": "named", "evidence": "集計"},
    {"entry": "M05.e2", "step": "M01.14.s2", "basis": "inferred"}
  ],
  "excluded_entries": [{"entry": "M05.e4", "reason": "画面の表示の制御だけ"}],
  "questions": []
}
```

- 起動点（`M05.e1`）は機械が決める（`python3 scripts/systems.py entries`）。アクティビティ図の番号（`A-02-1`）も機械が振る（システムの番号＋そのシステムの中での連番）。
- 紐付けの根拠は3種類だけ。`named`・`io` は、`evidence` の文字が、手順の文とプログラムの側の両方にあることを機械が確かめる。根拠の文が無ければ `inferred`（確認事項は機械が作る）か、紐付けない（「業務フローに出てこない起動点」として確認事項になる）。
- 紐付けた手順を引く作業のすぐあとに、機械がシステム処理の箱（S-。`activity` にアクティビティ図の番号）を置く。フローの側で、同じ処理の箱を書かない。

## プログラムのブロックの木 `code/<まとまりの ID>.tree.json`

## 用語の対応 `structure/code_terms.json`

プログラムの中だけの名前（変数・項目・手続き・定数）と、アクティビティ図に書く業務の言葉の対応。LLM が書く。**1つの名前に、言葉は1つ**（どの図でも同じ言葉を使う）。

| `exclude` | `item`・`reason`（`same_as`・`flow`） | フローに入れない（`excluded_items` に理由つきで載る） | 同じ作業をほかの項目で入れたなら `same_as`、ほかのフローで描くなら `flow`（理由は機械が決まった形で書く）。ほかは `reason` |

| `disconnect` | `from`・`to` | 線を外す | 下書きにある線だけ |
| `link` | `flow`・`source`（`after`・`label`） | ほかの業務へ続くリンクを置く | `hierarchy.json` の `sequence` にある続き先は、機械が置く（位置を変えるときだけ書く） |

## 確認事項の書き方
