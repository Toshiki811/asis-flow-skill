# プログラム（EUC・スクリプト・ソース）の読取と、アクティビティ図の作り方

入力にプログラムがあるとき（マクロ付きの Excel、Access の書き出し、スクリプト、SQL、業務システムのソース）に使う。プログラムが無ければ、この工程は丸ごと飛ばす（システム一覧と札は、プログラムが無くても出る）。

決まりは `flow-rules.md` の 6 章、データの形は `schemas.md` の「システム台帳」「アクティビティ図の直しの一覧」。

## 3つの層と、出るもの

| 層 | 何を書くか | データ | 図・一覧 |
| --- | --- | --- | --- |
| 業務フロー | 誰が・何を。プログラムが動く所には、箱を1つだけ（S-。「▶ A-02-1」つき）。人が操作する箱には、システム名の札「［会計システム］」 | `flows/*.flow.json` | `業務フロー_as-is.drawio`、業務マトリクス一覧 |
| システム台帳 | どんなシステムがあるか。プログラムの起動点と、マニュアルの手順の紐付け | `structure/systems.json` | 業務マトリクス一覧の「システム一覧」「プログラムの図にしない手続き」、アクティビティ図の1ページ目（システムと起動点の一覧） |
| アクティビティ図 | プログラムが・何を。起動点（ボタン・イベント・バッチ）ごとに1枚 | `activities/*.activity.json` | `アクティビティ図.drawio`、業務マトリクス一覧の「プログラムのノード一覧」 |

同じ処理を、業務フローとアクティビティ図の両方に描かない。業務フローには箱1つ、中身はアクティビティ図。

## 安全（必ず守る）

- **プログラムは実行しない。** Office のファイルは、マクロを抜いた写しだけを開く。Access のファイルは Access で開かない。スクリプト・ソースは、文字として読むだけ（実行も、取り込みもしない）。
- **認証情報は、ページを書く前に機械が伏せる**（接続文字列のパスワード・キー・トークン → `＊＊＊`）。伏せた行があることは、棚卸しとページの先頭に出る。伏せる前の値を、ほかの場所（カード・確認事項・報告）に書かない。
- **閲覧のロックが掛かった VBA プロジェクトは、既定では読まない。** `render_pages.py` が知らせるので、読んでよいかを利用者に確かめる。よければ `--read-locked --force --only <資料ID>` で読む。
- 開くのにパスワードが要るファイルは読まない（保護を外した写しをもらう）。Access のテーブルは、定義（項目名・型）だけを読む。行の中身は読まない。

## 進め方

```bash
python3 scripts/inventory.py <入力> -w <WORK>          # 棚卸し。プログラムのソース・マクロあり・Access が、要約に出る
python3 scripts/render_pages.py -w <WORK>              # ソースは、1行＝1単位の文字のページになる（手続きの切れ目で切る。認証情報は伏せる）
python3 scripts/code_struct.py -w <WORK>               # 構造（手続き・木・呼び出し・入出力・起動点・図にする単位）を機械で取り出す → code/*.struct.json
#  「構造 LLM の読取」と出たまとまりは、ブロックの木 code/<ID>.tree.json を書いてから、もう一度（下の「構造を LLM が読む言語」）
python3 scripts/systems.py draft -w <WORK>             # システム台帳の下書き（用語の正本のシステム＋プログラムのまとまり）
python3 scripts/systems.py entries -w <WORK>           # 起動点の一覧（アクティビティ図の番号つき。共通の処理のうち、補助の候補に ★）
python3 scripts/systems.py links -w <WORK>             # 紐付けの候補（起動点 × マニュアルの手順）
#  → structure/systems.json を書く（下の「台帳の書き方」）
python3 scripts/check_flow.py -w <WORK> --stage systems
python3 scripts/activity.py list -w <WORK>             # 図にする単位（A-02-1 …）
python3 scripts/activity.py terms -w <WORK>            # プログラムの中の名前の候補（定義の行つき）
#  → structure/code_terms.json を書く（下の「用語の対応の書き方」）
python3 scripts/activity.py draft -w <WORK> --id A-02-1   # 下書きを、ソースの行つきで見る（その図に出てくる名前と、登録した言葉も出る）
#  → activities/A-02-1.edits.json を書く（下の「直しの一覧の書き方」）
python3 scripts/activity.py apply -w <WORK> --all      # 図のデータを作る（呼ばれる側から先に）
python3 scripts/check_flow.py -w <WORK> --stage activity
python3 scripts/renumber.py -w <WORK>                  # 業務フローの起動点の箱を、紐付けと図の名前に合わせて置き直す
python3 scripts/build_activity.py -w <WORK>            # out/アクティビティ図.drawio（PNG は check_layout.py）
```

順番: ページ読取（工程4）と用語の正本（工程5）のあと、フロー化（工程6）の前に、台帳とアクティビティ図を作る。台帳には、用語の正本のシステム名と、カードの手順が要る。フローは、台帳の紐付けを見て、起動点の箱を置く。

**マニュアルが無く、プログラムだけが入力のとき**は、業務フローを作らない（工程 3〜6 と、フローの原典照合はしない）。台帳には、紐付けを書かずにシステムと種類だけを書き、アクティビティ図と、システム・起動点の一覧を出す。`check_flow.py`・`status.py` は、マニュアルの工程を求めない。

**Access のファイル**は、書き出したテキストで受け取る（手順と、読めるもの・読めないものは `access-export.md`）。書き出したフォルダ1つが、1つのプログラムのまとまりになる。`python3 scripts/extract_access.py <フォルダ>` で、読めた中身を先に目で見る。

プログラムのページは、カードにしない（`pages.py batches` に出てこない）。業務分類にも割り当てない。階層の `docs` にも書かない（ソースだけの資料は、業務の木でなく、台帳に結び付く）。

## 機械が決めること・LLM が決めること

| 機械が決める | LLM が決める |
| --- | --- |
| 手続き・分岐・繰り返し・呼び出し・入出力・操作者とのやり取り | システムの種類（`kind`）と、プログラムの資料がどのシステムか（下書きを確かめる） |
| 起動点（ボタン・イベント・自動実行・定時実行・ショートカット・引数の無い公開の Sub） | 紐付け（候補の採否と、根拠） |
| 図にする単位と番号（`A-<システムの番号>-<連番>`）。呼ぶ所が1か所で箱 8 個以下の手続きは、呼ぶ側の図に入れる。補助の候補（入出力・やり取り・プログラムの終了が無い、共通の処理）を出す | 図にしない起動点（理由は決まった4つ）。図にしない手続き（補助。機械の候補から選ぶ。理由は決まった6つ） |
| 技術的と分かる文の対象外（画面の更新の制御・変数の準備・ログ・後片付け） | 箱・判断の名前、まとめ方、技術的な分岐の畳み、対象外（理由は決まった語） |
| 起動点の箱（S-）を置く場所、線、推定の印 | 機械が作らない確認事項（コメントと処理の食い違い・マニュアルとの食い違い。答えで図が変わるものだけ） |
| プログラムの中の名前の候補と、箱にその名前が出ていないかの点検 | 用語の対応（プログラムの中の名前 → 業務の言葉。根拠つき） |
| 図の配置（分岐の先を横に並べる・途中の終了を抜ける所ごとに置く・線の通り道） | |
| 決まった形の確認事項（下の表） | |

機械が作る確認事項（種別「システム」。どれも、答えで図が変わる問い＝紐付け・図にする範囲・紙・読めていない所）:

| いつ | 問い |
| --- | --- |
| 紐付けの無い起動点 | どの業務の、どの作業で使っていますか |
| 推定の紐付け | その作業で、このプログラムを使っていますか（フローの線に付く） |
| ボタン・ショートカットの割り当てが見つからないマクロ | どの操作で実行していますか |
| どの起動点からも呼ばれていない手続き | 図にする処理（どこかから動かしているもの）は、ありますか |
| 実行するときに決まる名前（ファイル・シート・テーブル） | 実際には何を指していますか |
| 閲覧のロックが掛かったマクロ | 中身を読んでよいですか |
| 読まないと決めたまとまり・読んだ範囲が一部だけのまとまり（LLM が構造を読む言語） | 図にする処理が、ほかにありますか |
| Access から書き出せなかったもの・書き出しから読み取れなかったもの（新しい形だけのマクロなど） | 中身を確かめる方法はありますか |
| マニュアルが入力に無い（プログラムのソースだけ） | 起動点は、どの業務の、どの作業で使っていますか（システムごとに1つにまとめて出す） |

名前・呼び方だけが変わる問い（つづりから読んだ言葉・「不明」にした名前）は、確認事項にしない。業務マトリクス一覧の「プログラムの用語対応」に、色つきで出る。

## 用語の対応の書き方（`structure/code_terms.json`）

**アクティビティ図を読むのは、業務部門の担当。** プログラムの中だけの名前（変数・項目・手続き・定数）は、箱に書かない。かわりに、**どの名前を、どの言葉で書いたか**を、ここに1回だけ書く。業務マトリクス一覧のシート「プログラムの用語対応」に出て、言葉からもとの名前を引ける。直しの一覧より**先に**書く（どの図でも、同じ名前を同じ言葉で書くため）。

`python3 scripts/activity.py terms -w <WORK>` が、候補（箱が受け持つ行に出てくる、文字列・コメントの外の名前）を、定義の行つきで並べる。載せるのは、**箱・判断・出口・図の名前に、その意味を書く名前**だけ。部品・枠組みの名前（`ClearContents`・`MsgBox`）は、載せずに、していることを書く。

| 項目 | 書くこと |
| --- | --- |
| `project` | プログラムのまとまり（`M02`） |
| `name` | もとの名前。ソースの文字のまま |
| `word` | 業務の言葉（名詞か、短い句）。図では、この言葉で書く |
| `basis` | 根拠。`comment` コメントに書いてある／`definition` 定義から読める（画面のラベル・定数の値・項目の説明・テーブルの列）／`spelling` 名前のつづりから読んだ（＝推定）／`unknown` 読めない。**定義の行（行末・すぐ上の行）にコメントがあれば `comment`、定数の定義なら `definition` を、機械が場所ごと入れる**（`activity.py` を実行したとき。書かなくてよい） |
| `source` | 根拠の場所（`module`・`line`）。機械が根拠を入れたときは、機械が書く。ほかの行（画面のラベル・項目の説明）を根拠にするときだけ書く。その行に、その名前があること（機械が確かめる） |
| `note` | 補足（省ける） |

- 1つの名前に、言葉は1つ。別の名前が同じ物を指すなら、同じ言葉にしてよい。
- 根拠は、強い方から選ぶ: コメント・定義があれば、それで書く（定義の行のコメント・定数の定義は、機械が根拠と場所を入れる。`basis` を書かない）。無ければ、つづりから読む（`saishu_gyo` → 「最後の行」）。定義の行にコメントがあるのに `spelling` と書くと、点検が WARN（コメントを読んで言葉を決める）。**つづりから読んだ言葉は、推定**（一覧の「プログラムの用語対応」に、色つきで出る。確認事項にはしない）。
- つづりからも読めない名前（`flg2`・`x1`）は、**推測しない**。`basis` を `unknown`、`word` を空にする。図には、もとの名前のまま「」で書く（一覧の「プログラムの用語対応」に、「不明」として色つきで出る。確認事項にはしない）。
- マニュアル・用語の正本（`glossary.json`）に、同じ物の呼び方があれば、その言葉を使う。
- 担当の目に見える名前（シート・ファイル・テーブル・ボタンの文字・メッセージ）は、載せない（言い換えないので）。


## 台帳の書き方（`structure/systems.json`）

1. `systems.py draft` の下書きを開く。システムは、用語の正本（`glossary.json` の `kind: system`）のものが全部載っている。
2. **システムの種類（`kind`）を埋める。** `core` 基幹・パッケージ／`euc_excel` EUC（Excel）／`euc_access` EUC（Access）／`script` スクリプト・バッチ／`external` 外部サービス／`other`。原典から決まらなければ `other` にする（確認事項にはしない。種類が変わっても、図は変わらない。flow-rules 5.8）。
3. **プログラムの資料（`docs`）を確かめる。** 下書きは、ファイル名・フォルダ名と、用語の正本のシステム名を見比べて入れている。マニュアルでの呼び方（「月次集計マクロ」）と、ファイル名（「月次集計.xlsm」）が違うときは、マニュアルの呼び方のシステムに `docs` を移す。マニュアルに出てこないプログラムは、ファイル名のシステムを `glossary.json` に足す（`kind: system`）。
4. **紐付け（`links`）を書く。** `systems.py links` の候補を、起動点ごとに見る。紐付けるのは、**その起動点を動かす作業**（ボタンを押す・マクロを実行する・バッチを流す手順）。プログラムの出力を使うだけの作業（できた集計表を確認する）は、紐付けない。

| 根拠 | いつ | `evidence` |
| --- | --- | --- |
| `named` 名指し | マニュアルの手順の文に、その起動点のボタン名・マクロ名・メッセージの文がある（起動点が1つだけのプログラムは、ファイル名でもよい） | 両方に出てくる文字（「集計」「Main」） |
| `io` 入出力の一致 | 手順の帳票名が、プログラムの読む・作るシート・ファイル・テーブルの名前と一致する | 帳票名（「請求一覧」） |
| `inferred` 推定 | 根拠の文は無いが、作業の内容から、その起動点を使うと読める | 書かない（確認事項は機械が作る） |

   根拠も見立ても無い起動点は、紐付けない（「業務フローに出てこない起動点」として、機械が確認事項にする）。**根拠の文字を作らない。** `named`・`io` の `evidence` は、機械が両側にあることを確かめる。
5. **図にしない起動点（`excluded_entries`）** は、理由が次の4つに当たるものだけ: 中身が空／画面の表示の制御だけ／開発・試験用／ほかの起動点と同じ処理を呼ぶだけ。当たらなければ、図にする。
6. **図にしない手続き（`folded_procedures`）**: `systems.py entries` で ★ の付いた共通の処理（補助の候補。その手続きと、そこから呼ぶ手続きのどれにも、シート・ファイル・テーブルの読み書き・操作者とのやり取り・プログラムの終了が無い）を、ソースで読む。**補助だけをしている**ものを、理由つきで書く（`{"procedure": "M01.modUtil.TrimName", "reason": "文字・日付の整形"}`）。書かなければ、図のまま。

| 理由 | 当たるもの |
| --- | --- |
| 探す・取り出す | 一覧・集まりから、名前や番号で1つを探して返す |
| 寸法・位置・単位の計算 | 画面の点・長さの単位・座標を計算して返す |
| 文字・日付の整形 | 文字を切り出す・置き換える・書式をそろえる |
| 保存先・名前の組み立て | フォルダ・ファイル・シートの名前を組み立てて返す |
| ログの表示 | 状態のコード・エラーの文字を、技術者向けに表示する |
| 型・空・エラーの種類の確かめ | 値の型・空かどうか・エラーの種類を見て、はい／いいえを返す |

   - **業務の計算・判定（金額・税・件数・期限・区分）をする手続きは、図にする。** 機械は、計算の中身を見分けない。読んで決める（業務の条件を畳まない、と同じ線）。
   - **画面に見える動きをする手続き**（一覧に行を足す・メニューを出す・表示を切り替える）も、図にする。画面の部品に書く文（リストに行を足す・ラベルや値を変える）のある手続きは、機械が候補から外す（VBA・Access のフォーム）。ほかの書き方（シートに図形を出す など）は候補に混ざるので、読んで決める。
   - 6つの理由に当たらなければ、図にする。迷ったら、図にする。起動点の手続きは、ここに書けない（図にしない起動点は、5 の `excluded_entries`）。
   - 図にしない手続きが呼ぶ共通の処理も、図にしないものにそろえる（片方だけは FAIL）。
   - 番号は詰めない（図にしない手続きの番号は、欠番になる。ほかの図の番号は変わらない）。前に作った図のデータ（`activities/<番号>.*.json`）は、消す。
   - 図にしない手続きと理由は、業務マトリクス一覧の「プログラムの図にしない手続き」に出る（候補だが図のままにしたものは出さない。数は、点検の INFO）。
7. `python3 scripts/check_flow.py -w <WORK> --stage systems` を FAIL 0 に。

## 直しの一覧の書き方（`activities/<番号>.edits.json`）

`activity.py draft --id <番号>` の下書きは、項目（キー・種類・行）と、ソースの行を並べたもの。直しの一覧には、次だけを書く。**呼ばれる側（共通の処理）から先に書く**（呼び出しの箱の名前に、呼ばれる側の図の名前が入る）。

- `name`: 図の名前（「目的語＋動詞」。業務フローの起動点の箱のラベルになる）と、`summary`（1〜2文）。
- `ops`:

| 直し | 書くこと | 決まり |
| --- | --- | --- |
| `name` 名付ける | `item`・`label`。判断・繰り返しは `branches`（出口のラベル。下書きの出口の順。else の無い分岐は、最後に「どれにも当たらない側」） | **全部の箱と判断に付ける**（付けないと点検が FAIL）。操作者とのやり取り・呼び出し・エラーの判断は、機械の名前のままでよい |
| `merge` まとめる | `items`（隣り合う「まとまり」を、並んでいる順に。機械が対象外にした文をはさむときは、それも入れる） | 1つの業務の言葉で言えるものだけ。間に分岐・繰り返し・呼び出しがあれば、まとめられない（同じ共通の処理を 3 回以上続けて呼ぶ並びだけは、呼び出しも `items` に入れて、まとめられる） |
| `split` 分ける | `item`・`at`（その行から新しい項目。キーは「手続き.その行」） | 1つのまとまりに、別々の仕事が入っているとき |
| `fold` 畳む | `item`（分岐・繰り返し）・`reason` | 理由は、決まった語から: 保存先・ファイルの有無の確認／型や空の確認／エラー番号の振り分け／書式・表示の調整／再試行・待ち合わせ／配列・文字の加工 |
| `exclude` 対象外 | `item`・`reason` | 理由は、決まった語から: 画面の更新の制御／変数の準備／ログ／後片付け／エラーの扱いの設定／書式・表示の調整／開発・試験用。**シート・ファイル・テーブルに書く文は、対象外にできない** |
| `include` 図に戻す | `item` | 機械が対象外にした文が、業務の上で意味を持つとき |

- `questions`: 機械が作らない問いだけ（下の「確認事項にすること」）。対象は `items`（箱になる項目のキー）。`effect`（答えで、図のどこが変わるか）を、必ず書く。

**する・しないの線**（同じ下書きを2人が直して、割れた所。「してよい」でなく、このとおりにする）:

- **対象外（`exclude`）を足すのは、次の3つだけ**。当たる文は、対象外にする（「してもよい」ではない）。**VBA では、機械がもう対象外にしている**（下書きに「※変数の準備」「※書式・表示の調整」と出る）。直しの一覧で足すのは、機械が見分けられなかった文と、構造を LLM が読む言語（木の `tech` に書く）だけ。業務の上で意味のある文だった（例: 要確認の行に色を付ける）ときは、`include` で図に戻す。
  - 「変数の準備」: 作業用の変数に、**最後の行・件数・長さ・今日の日時を取るだけ**の文（`最終行 = ws.Cells(…).End(xlUp).Row`・`n = UBound(a)`・`d = Date`・`LocalDate today = LocalDate.now();`）と、**繰り返しの位置を進めるだけ**の文（`r = r + 1`・`rs.MoveNext`・`i++;`）。機械は、1 つ進める文は、その変数をセルの行・列の番号にだけ使うとき（表示する・書く・ほかの変数に写すなら、業務の件数かもしれないので残す）に決める。手続きの中だけで使う変数に、定数や、ほかの変数の値を入れ直すだけの文も、機械が対象外にしている（構造を LLM が読む言語では、木の `tech`。付け忘れなら、木を直す）。モジュールの変数・プロパティ・戻り値・引数に入れる文は、手続きの外に値が残るので、機械は残している（足さない）。**金額・数量・日付の計算、あとで表示する・書く件数を数える文、シートや画面の項目の値を読む文、戻り値・引数に入れる文は、当たらない**（箱にする）。
  - 「書式・表示の調整」: 色・罫線・列幅・フォント・表示の形・選択の移動だけの文（VBA では、機械が、シートへの書き込みと数えずに対象外にする）。まとまりの途中にあるものは、分けてまで対象外にしない。
  - 「開発・試験用」: 試験用の表示・動作確認のための文。
  - ログ・後片付け・画面の更新の制御・エラーの扱いの設定は、機械が決める。機械が箱にした文に、これらの理由を足さない。箱を減らすために、対象外を足さない。
- **畳む（`fold`）**: 技術的な分岐（理由の語に当たるもの）で、**中に、操作者とのやり取り・別の図の呼び出し・抜ける所が無い**ものは、箱の数に関わらず畳む。中にそれらがある分岐は、技術的でも判断として描く（機械も、畳ませない）。データの値・利用者の選択で分かれる所は、畳まない。
- **まとめる（`merge`）**: 1つの操作の前半と後半だけ（写す → 貼る／選ぶ → 消す／開く → 読む）。それ以外は、機械のまとまりのまま。手続きをまたいでは、まとめられない。
- **同じ共通の処理を続けて呼ぶ並び**（値を取る → 共通の処理に渡す、を何度も繰り返す形。点検・集計・転記の並び）: 同じ共通の処理（別の図）を **3 回以上**続けて呼ぶ並びは、`merge` の `items` に、呼び出しと、その間のまとまりを並んでいる順に書いて、1つの箱にまとめられる（**25 箱を超えるときだけ**）。切れ目は、ソースのコメントの見出し。呼び出しが 3 回に満たない見出しは、**前の見出し**と合わせる（同じ共通の処理を呼ぶ見出しが前に無ければ — 並びの先頭なら — 後ろの見出しと。間に、分岐・繰り返し・やり取り・呼び出しの無い見出しがあれば、合わせない。そのままにする）。**25 箱を超える図では、下書き（`activity.py draft`）の終わりに、機械が、この決まりで切った「まとめの案」が出る**（呼ぶ先と回数・見出し・`items` の並び。はじめの呼び出しの前の「値を取る」まとまりから、終わりの呼び出しまで）。使うなら、`items` をそのまま `merge` に写し、名前を付ける。読んで、まとめないほうが分かりやすければ、使わなくてよい。箱の名前は、何を・何項目（「テーブルを 10 項目確かめ、結果を一覧に足す」）。補足に、はじめと終わりの項目（画面に出る名前）を書く。箱には、機械が「→ 別ページ A-01-8 …（10 回）」と付ける。呼ぶ側の図に入れた手続き・プログラムを止める手続きの呼び出しは、まとめられない。
- **分ける（`split`）**: 1つのまとまりに、触る先の違う書き込みが入っているときだけ。
- **図に戻す（`include`）**: 機械が対象外にした文が、そのプログラムの業務の出力そのもののときだけ（一覧を表示するのが目的のバッチの表示）。エラーの文字を出すログ・後片付け・フラグを立てる文は、戻さない。
- **25 箱を超えるとき**は、この順で減らす: (1) 上の決まりで畳める分岐を畳む (2) 前半と後半をまとめる (3) 同じ触る先への、続く書き込みのまとまりをまとめる (4) 同じ共通の処理を 3 回以上続けて呼ぶ並びを、見出しごとにまとめる（下書きの「まとめの案」）。それでも超えるときは、超えたままにする（点検は WARN）。箱を減らすために、対象外を足さない。
- **かぎかっこ**: 箱の名前と補足（`detail`）のかぎかっこの中は、**担当の目に見える名前**だけ。その箱が受け持つ行の、文字列の中の文字（メッセージ・ボタンの文字・シートやファイルの名前）か、その箱の入出力の名前（となりの箱の行にある名前は、書けない）。変数・項目・手続きの名前を「」で囲まない（用語の対応で「不明」にした名前だけは、もとの名前のまま「」で書く）。
- 呼び出しの箱は、対象外にできない。名前は、機械のままでよい（行き先の図の名前が入る。だから、行き先の図の名前を、手続きの名前のままにしない）。**呼んだ結果を変数に足す・入れる文**（`横のずれ = 横のずれ + 枠の幅(種類)`）の箱だけは、何のために呼ぶかを名前にする（「横のずれに、枠の幅を足す」）。
- **呼ばれる側が、渡る値によって、することが変わるとき**（番号が渡らなければ、読まずに空のものを返す、など）: 行き先の図の名前は、どちらの場合にも当てはまる言い方にする（「得意先を用意する（番号があれば読む）」。「読む」と言い切らない）。呼ぶ側で、どちらになるかがソースから決まるとき（受け口のアドレスに番号が無い・定数を渡している）は、呼び出しの箱に、**その流れで起きること**を名付ける（「空の得意先を用意する」。補足に、そう決まる理由を書く）。決まらないときは、行き先の図の名前のまま。
- **図にしない手続き（補助）を呼ぶ行**は、下書きに、ふつうの「まとまり」として出る（「補助の手続き … を呼ぶ」と、その手続きの中身が、下に出る）。**何のために呼ぶかを、業務の言葉で名付ける**（「閉じるコマンドの番号で、メニューの項目を探す」）。手続きの名前は書かない。呼んだ結果をすぐ使う、となりのまとまりとは、まとめてよい（取る → それを書く、の前半と後半）。理由が「ログの表示」の補助を呼ぶ行は、機械が対象外にする（名付けない）。
- **繰り返す箱**（中身が箱1つの繰り返し。図に「↻ 繰り返し」と出る）は、何について繰り返すかを、名前か補足に書く（「「請求一覧」の行ごとに、税額を書く」）。ソースの条件は、図に出ない。行き先が、図にする文の無い手続き（異常終了の手続きなど）の呼び出しは、機械が対象外にする。プログラムを止める手続きの呼び出しは、そこから「終了（プログラムを止める）」につながる。
- **条件の無い繰り返し**（`Do … Loop`・`while (true)`）は、下書きに「※条件が無い」と出る。判断にならない（中の最後から、中の頭へ戻る線になる。終わるのは、中の「抜ける」だけ）。名前も、出口の名前も付けない。
- **線が重なって読めないとき**（`check_layout.py` の FAIL「同じ所を重なって走る」）: 1枚の図に、線の通り道が足りていない。上の決まりで畳める分岐を畳み、前半と後半をまとめる。それでも出るときは、利用者に伝える（図を手で直さない）。

名付けの決まり（`flow-rules.md` 6 章）:

- **読むのは、業務部門の担当。** 箱・判断・出口・補足・図の名前と説明は、業務の言葉で「何を・どうする」と書く。プログラムを読める人にしか通じない言葉を使わない。
- **担当の目に見える名前は、ソースの文字のまま「」で書く。** シート・ファイル・テーブル・帳票・画面・ボタンの文字・メッセージ。言い換えない。
- **プログラムの中だけの名前は、箱に書かない。** 変数・項目・手続き・モジュール・定数・部品の名前（`saishu_gyo`・`KOKYAKU-ZAN`・`ClearContents`）。用語の対応の言葉で、意味を書く（「最後の行」「顧客の残高」）。部品の名前は、していることを書く（「「請求一覧」の中身を消す」）。「」で囲まない。機械が、箱・補足・出口・図の名前に、そのままの名前が出ていれば FAIL にする。
- **技術の用語も、そのまま書かない**（配列・可変長・状態コード・URL・パラメータ・例外）。何のためのものかを書く（「読み書きの結果のコード」「画面のアドレス」）か、担当の目に見える名前で指す（ファイル「売上明細.csv」）。
- **言い換えは、その変数に実際に入るもので書く。** はじめに別の物を入れる変数を、名前のつづりだけで言い換えない（`oya = buhin` で始まる変数を「親」と書かない。「いま見ている部品」）。補足には、箱の行がしていることを、落とさずに書く（足している物が 3 つあれば 3 つとも。式を入れるセルが 2 つあれば、それぞれの式）。
- 区分・状態を表す値（`'00'`・`9`）は、定義・コメントから意味が読めるときは、意味で書く（「正常に読めた」）。読めなければ、値のまま書く（確認事項にはしない。意味が分かっても、図の言葉が変わるだけ）。
- 意味が読めない名前は、推測しない。用語の対応に「不明」で載せ、もとの名前のまま「」で書く。
- **図の名前（`name`）も、業務の言葉**（「目的語＋動詞」）。手続きの名前を、題にしない。
- **箱の名前は、動詞で終える**（「…を読み込む」。体言止めにしない）。判断は、問いの形（「〜か」。繰り返しの判断は、動詞で終えてもよい）。最後に、相手・物の名前を置くなら、かっこ書き（「メールを送る（Outlook）」）。補足（`detail`）は、機械がかっこで包んで出すので、自分では、かっこを付けない。機械が、動詞で終わらない名前を FAIL にする。機械が付けた名前（「「…」と、メッセージを出す」など）も、この形になっている。
- 箱の右下（枠の外）の出典（資料・モジュール・行）は、機械が付ける。もとのコードは、そこと、用語の対応から引ける（箱に、もとの名前を並べて書かない）。
- **業務の条件は、畳まない。** データの値・利用者の選択・件数・日付・金額のしきい値で分かれる所は、判断として描く。ソースに書かれた数字（100 万円・8%）は、そのまま書く。畳んでよいのは、技術的な分岐だけ。
- 利用者にメッセージを出す・処理を止めるエラー処理は描く。
- 実行するときに決まるもの（変数のファイル名・組み立てた SQL）は、推測しない。機械が「＜変数名＞」「（実行時に決まる）」と書くので、そのまま使う。
- コメントは、名付けの手がかりに使ってよい。処理と食い違い、どちらが正しいかで箱・順・分岐が変わるときは、確認事項にする。
- **as-is だけ。** 不具合の指摘・改善案は書かない。

確認事項にすること（種別「プログラム」）: **答えで図が変わるものだけ**（`effect` に、変わる所を書く）。コメントと処理が食い違い、どちらが正しいかで箱・順・分岐が変わる所／マニュアルとプログラムの食い違い（マニュアルは CSV、プログラムは Excel で保存 など。紙が変わる）／ある場合に、プログラムが何もしない所で、人の作業があるか（箱が増える）。

確認事項にしないこと: しきい値・宛先・保存先の値（いくつか・いまも同じか。ソースの値のまま書く）／名前・区分の値の意味（用語の対応に「不明」で載せる）。答えても、図の形は変わらない。

## サブエージェントへの指示文（アクティビティ図）

図にする単位が多いとき（目安: 6 枚以上）は、組に分けて、サブエージェントに書かせる。組は機械が出す（`python3 scripts/activity.py list -w <WORK> --group 4`。呼ばれる側から先の順。上の組から順に渡すと、呼び出しの箱に、呼ばれる側の図の名前を使える）。原典照合の担当への組分けも、同じ組で。`{…}` を埋めて渡す。

```
あなたは、プログラムのアクティビティ図の「直しの一覧」を書く担当です。プログラムは実行しません。読むだけです。

対象: {番号の並び（例: A-02-4, A-02-1, A-02-2。共通の処理が先）}
作業フォルダ: {WORK}
スキル: {SKILL}

1. {SKILL}/references/code-guide.md の「直しの一覧の書き方」と、{SKILL}/references/flow-rules.md の 6 章を読む。
2. 番号ごとに、python3 {SKILL}/scripts/activity.py draft -w {WORK} --id <番号> で下書きを見る（ソースの行つき。終わりに、その図に出てくる
   プログラムの中の名前と、用語の対応 {WORK}/structure/code_terms.json に登録した言葉が出る）。
3. {WORK}/activities/<番号>.edits.json を書く（形は {SKILL}/references/schemas.md の「アクティビティ図の直しの一覧」）。
   全部の箱と判断に名前を付ける。読むのは、業務部門の担当。箱・判断・出口・補足・図の名前は、業務の言葉で書く。
   ・画面・シート・ファイル・テーブル・ボタンの文字・メッセージの名前は、ソースの文字のまま「」で書く。
   ・変数・項目・手続き・部品の名前は、書かない。用語の対応の言葉で、意味を書く。載っていない名前は、ソースのコメント・定義から読んで
     業務の言葉で書き、報告の terms に足す（用語の対応 code_terms.json は、親が書く。自分では書き換えない）。読めない名前は、推測せず、報告に書く。
   ・下書きに「補助の手続き … を呼ぶ」と出た項目は、何のために呼ぶかを、業務の言葉で名前にする（その手続きは、図にしない）。
   業務の条件は畳まない。as-is だけを書く。
4. python3 {SKILL}/scripts/activity.py apply -w {WORK} --id <番号> で図のデータを作る。誤りが出たら、直しの一覧を直す。
5. 全部終わったら、python3 {SKILL}/scripts/check_flow.py -w {WORK} --stage activity を実行し、担当した番号の FAIL を 0 にする。
6. 報告を {WORK}/reports/activity_{先頭の番号}.json に書く: {"activities": [番号…], "boxes": 箱の数, "excluded": 対象外にした数, "folded": 畳んだ数, "questions": 確認事項の数,
   "terms": [{"name": "もとの名前", "word": "業務の言葉（読めなければ空）", "basis": "spelling|unknown（定義の行のコメント・定数の定義から読んだなら書かない）"}], "notes": "迷った所"}
   書いたら python3 {SKILL}/scripts/validate.py --file report_activity {WORK}/reports/activity_{先頭の番号}.json で形を確かめる（根拠ごとに要る項目は、親が用語の対応に写したあと、check_flow.py --stage activity が見る）。

書かないこと: ソースに無い処理・名前。改善案。activity.json・flow.json・systems.json（機械と親が書く）。
```

親は、先に用語の対応（`structure/code_terms.json`）を書いてから、サブエージェントに渡す。全部そろったら、報告の `terms` を用語の対応に足し（同じ名前に違う言葉が来たら、1つに決めて、直しの一覧をそろえる）、`activity.py apply --all` → `renumber.py` → `build_activity.py` → `check_flow.py` → `check_layout.py` を回し、PNG を目で見る。**名前の無い箱が残る図は、題に【下書き】と出る。納品物に入れない**（全部に名前を付けるか、その図を出さないと利用者に伝える）。

## 揺れの測定（アクティビティ図）

同じプログラムから、図を2回作って比べる（作業フォルダを写し、片方の直しの一覧を消して、同じ指示文で書かせる）。

```bash
python3 scripts/diff_runs.py activities <作業フォルダA> <作業フォルダB> --min 0.9 --report <WORK>/out/揺れ_アクティビティ図.md
python3 scripts/code_struct.py --agree <木1> <木2>          # 構造を LLM が読む言語: ブロックの木の一致
```

箱は、受け持つソースの行の重なりで突き合わせる。揺れてよいのは、ラベルの言い回し。揺れてはいけないのは、箱の対応・まとめ方・対象外にした行・分岐の扱い（判断にしたか、畳んだか）。低い項目があれば、決まり（`flow-rules.md` の 6 章）に決め方を足して、もう一度測る。

## 原典照合（アクティビティ図）

業務フローと同じく、作り方を伝えない別のエージェントに、図とソースを突き合わせさせる（指示文は `code-review-prompt.md`）。構造を LLM が読んだ図（「構造の取り出し: LLM の読取」と図に出る）は、全部の箱を見させる。

## 構造を LLM が読む言語（Java・C#・COBOL ほか）

`code_struct.py` が「構造 LLM の読取」と出すまとまりは、機械が構文を読めない。LLM がソースを読んで、**ブロックの木** `code/<まとまりの ID>.tree.json` を書く（形は `schemas.md`）。機械は、その木を確かめて構造にする。そのあとの工程（台帳・アクティビティ図）は、ほかの言語と同じ。

```bash
python3 scripts/code_struct.py -w <WORK> --hints           # 手続きの見出しらしい行（読む範囲を決める手がかり。構造には使わない）
python3 scripts/pages.py lines -w <WORK> --only M01 --pages 1-3   # ソースを、行の番号つきで読む（番号は、モジュールの行の番号。木には、この番号を書く）
#  → code/M01.tree.json を書く
python3 scripts/code_struct.py -w <WORK>                   # 木を確かめて、構造にする（誤りは「※ 木の誤り」と出る）
python3 scripts/check_flow.py -w <WORK> --stage code
```

**先に、読む範囲を決める。** 業務システムのソースは、全部は描けない。`--hints` の一覧と、マニュアルが名指しする画面・バッチの名前を見て、起動点（入口）を選び、利用者に確かめる。木に書くのは、選んだ起動点と、そこからたどれる手続きだけでよい。読まないと決めたまとまりは、`{"project": "M05", "skip": "理由", "procedures": [], "entries": []}` と書く（確認事項に自動で載る）。

**書くのは、種類と行の範囲だけ。** 条件の文字・実行文の行・メッセージの文字・コメントの手がかりは、機械がソースから入れる。名前を付ける・まとめる・畳むのは、アクティビティ図の直しの一覧でする（ここではしない）。

| 種類 | いつ | 書くもの |
| --- | --- | --- |
| `seq` | 続く文のまとまり。切る所は、下の「まとまりの切り方」の4つだけ | `lines`。読む・書くものがあれば `io`。技術的な文だけなら `tech` |
| `if` | 条件での分岐。`try` の `catch` も、これ（`try` の中身はそのまま並べ、`catch` の行を条件にする） | `lines`、`branches`（`then`・`elseif`・`else`）。`elseif` には条件の行（`head`） |
| `select` | 値での振り分け（`switch`・`EVALUATE`） | `lines`、`branches`（`case` ごとに `head`。`default:`・`WHEN OTHER` は `else` で、行があるので `head` を書く） |
| `loop` | 繰り返し | `lines`、`body`。うしろに条件のある形（`do … while`）は `tail` |
| `call` | **木の中の手続き**の呼び出し | `lines`、`to`（「モジュール.手続き」）。木に無い呼び先（部品・枠組み・読まない範囲）は、`call` にせず `seq` |
| `interact` | 操作者に知らせる・聞く・画面を開く | `lines`、`how`。見せる文字が、行の最初の文字の定数でないときは `text` |
| `exit` | 戻る・抜ける・例外を投げる・プログラムを終える | `lines`、`what`（`proc`・`loop`・`continue`・`program`。`switch` の中の `break` は `select`） |

**揺れやすい所の決め方**（同じソースを2人が読んで、割れた所。このとおりに書く）:

- **まとまり（`seq`）の切り方**: 切るのは、(1) ほかの種類のブロックの所、(2) コメントだけの行の所、(3) 触る先（`io` の名前）が、別のものに変わる所、(4) 技術的な文（`tech`）と、そうでない文の境、の4つだけ。空の行では切らない。触る先の無い文は、前のまとまりに続ける。機械も、同じ決まりでつなぎ直す（(1)(2) は機械が自分で切る。(3)(4) は、書いた `io`・`tech` で決まる）。
- **技術的な文（`tech`）**: 1つの文ごとに決める。同じ `tech` の文が続けば1つのまとまり、違えば切る。
  - `ログ`: 標準出力・ログへの表示だけの文（COBOL の `DISPLAY`、`System.out.println`、`logger.info`、`console.log`）。エラーの文字を出す文でも同じ。業務の出力そのもの（一覧を刷るバッチの表示）は、アクティビティ図の直しの一覧の `include` で戻す。
  - `変数の準備`: 値を入れない宣言と、**作業用の変数**（COBOL の WORKING-STORAGE の項目・ローカルの変数）に、**定数**（数・文字・真偽・空）か、**ほかの変数の値をそのまま**入れるだけの文（`MOVE 0 TO WS-RESULT`・`MOVE 'Y' TO WS-EOF`・`INITIALIZE WS-AREA`・`MOVE IN-STATUS TO WS-STATUS`・`int n = 0;`）。定数だけの計算の形で入れる文（`ADD 8 TO ZERO GIVING WS-RESULT`）、繰り返しの位置を進めるだけの文（`ADD 1 TO WS-IDX`・`i++;`）、件数・長さ・今日の日付を取るだけの文（`LocalDate today = LocalDate.now();`）も同じ。業務の値の計算・あとで表示する件数を数える文・項目の値を取る文には付けない（`String name = order.getName();` は付けない）。ファイルのレコード・画面・戻り値・引数の項目に入れる文にも付けない（業務で決めた値・呼んだ側に返す値。`MOVE 100 TO OUT-TANKA`）。機械が構文を読む言語（VBA など）でも、同じ決め方で機械が付ける。
  - `後片付け`: ファイル・接続を閉じる、資源を放すだけの文（`CLOSE`・`close()`・`dispose()`）。
  - `画面の更新の制御`: 再描画・カーソル・警告の表示を切り替えるだけの文。
- **やり取り（`interact`）にするもの**: 操作者の画面に、文字を出す・入力を求める・画面を開く文。画面の枠組みを通して、次の画面で操作者に見せる文言・入力エラーを渡す文も、これ（Spring の `addFlashAttribute("message", "…")`・`rejectValue(…)`、ASP.NET の `ModelState.AddModelError(…)`。`how` は `msgbox`）。値を画面に渡すだけの文（`model.addAttribute("order", order)`）は `seq`。**バッチの標準出力への表示は `interact` にしない**（`seq`＋`tech: ログ`）。
- **1行が、2つの働きを兼ねるとき**（1行は、1つのブロックにしか入らない）:
  - `return 手続き(…)`（木の中の手続き）は `call` にして、`"leave": "proc"` を添える。`return リポジトリ.find(…)` のように読む・書くものがある `return` は、`seq`（`io` つき）にして `"leave": "proc"`。`exit` には `io` を付けられない。
  - `if`・`loop` の**条件の中で、木の中の手続きを呼ぶ**とき（`if (isDuplicate(order)) {`）は、その `if` に `"calls": ["モジュール.手続き"]` を書く（書かないと、呼び先が「たどれない手続き」になる）。
- **プログラムごと終える文**（`STOP RUN`・`System.exit(…)`・異常終了の呼び出し `CALL 'CEE3ABD'`）は、`exit` の `what: program`。呼んだ側には戻らない（図では、そこから「終了」につながる）。`GOBACK`・段落の終わりの `EXIT.`・`return`・`throw` は `proc`。
- **入出力（`io`）の名前**: その行にある文字のまま。COBOL の `WRITE レコード名` は、行にファイルの名前が無いので、ファイルの名前を書いて、`line` は `FD` の行を指す。`READ`・`OPEN` は、その行のファイルの名前。`CLOSE` には付けない。リポジトリ・DAO の変数越しの読み書き（`this.orders.save(order)`）は、種類は `テーブル`、名前は、その行にある変数の名前（`orders`）。木に無い外部の部品を呼ぶ文（`CALL 'DATECONV'`）は、`外部プログラム`・`out`。
- **手続きの範囲と名前**: 宣言の行から、最後の行（閉じかっこ・最後の文）まで。前に付くアノテーション（`@PostMapping(…)`）・うしろの区切りのコメントは入れない。COBOL の、段落の名前の無い先頭の処理は、`PROCEDURE DIVISION` という名前にする。何もしない文（`CONTINUE`）は、どのブロックにも入れなくてよい。
- **枠組みが、起動点の手続きの前に呼ぶ手続き**（受け口の前に値を用意する宣言 `@ModelAttribute`、前処理の宣言 `before_action` など。ソースの宣言から分かるものだけ）: その手続きも木に書き、起動点の `before` に、宣言の順で並べる（`"before": ["ItemController.java.findShop"]`）。図の先頭に、呼び出しとして入る。書かないと、受け口の前の読み込み・例外が、図から落ちる。入力の検査の設定だけの手続き（`@InitBinder`）は、書かない。
- **起動点の名前の前半が、別の行にあるとき**（クラスに付いた URL の前置き `@RequestMapping("/shop")` ＋ メソッドの `@PostMapping("/items/new")`）: つないだ名前（「/shop/items/new」）を書き、前置きの行を `also` に書く。前置きを落とした名前（「/items/new」）は、書かない。
- **起動点**: 画面や API の受け口は `trigger: entry`。根拠の行は、割り当ての行（`@PostMapping("/orders/new")`）。名前は「画面から「/orders/new」に送信（POST）」「バッチ「URIAGE01」を実行」のように書く（かぎかっこの中は、根拠の行か、ファイルの名前にある文字）。

機械が確かめること（1つでも合わなければ、構造にしない）:

- 行の範囲が、手続きの中にあり、入れ子が正しく、順に並び、重ならない。
- **行の網羅**: 手続きの中の行（空の行・注釈だけの行・かっこや `end` だけの行を除く）が、どれかのブロックに1回だけ入る。
- `if`・`select`・`loop` の先頭の行に、その種類の語がある（`if`・`switch`・`for`・`PERFORM` など）。`exit` の行・`leave` を添えた行に、抜ける語がある。
- `call` の呼び先が木にあり、その名前がその行にある。`calls` の名前が、条件の行にある。`interact` の `text` が、その行にある。`io` の名前が、指した行の文字にある（実行するときに決まる名前は「（実行時に決まる）」）。
- 起動点の名前のかぎかっこの中が、根拠の行か、ファイルの名前にある（`also` があれば、その行の文字と根拠の行の文字を、この順につないだものでもよい）。`before` の手続きが、木にある。

**同じソースを2回読んで、一致を測れる。** 別のエージェントに同じ範囲を読ませ、`python3 scripts/code_struct.py --agree <木1> <木2>` で、手続きとノード（種類と行の範囲）の一致を出す。隣り合うまとまりは、つないでから比べる（`tech` の違うものは、つながない）。流れを決めるノード（分岐・繰り返し・呼び出し・やり取り・抜ける）だけの一致も、別に出る。食い違った所は、ソースを見て決める。
