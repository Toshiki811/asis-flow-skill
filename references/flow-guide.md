# フロー化の進め方・JSON をまるごと書く方式（工程6。既定は下書き方式）

業務分類ごとに、ページカードから `flows/<フローID>.flow.json` を書く工程。ここで書くのは JSON だけで、図は `build_drawio.py` が組む。

**既定は、機械が下書きを作り、LLM は直しの一覧だけを書く方式（`references/flow-edits-guide.md`）。** 同じカードから2回作ったときの揺れが小さい（flow-rules.md §7）。このファイルは、フローの JSON を LLM がまるごと書く方式。下書きでは組めないフロー（カードの項目とノードが1対1にならない・大きく組み替える）のときに使う。材料の見方（下の 1）と、書き出したあとの見た目の直し方は、どちらの方式でも同じ。

## 親（進行役）のやること

1. `python3 scripts/pages.py plan-flows -w <作業フォルダ>` で、分類ごとの材料の大きさ（割り当てたページのカードの文字数）を見る。**上限（4 万字）を超える分類は、1つのエージェントでは読み切れない。** 先に `taxonomy.json` で下位の分類（`F03-1`、`F03-2`…。原典の節・項の切れ目）に分け、親の分類には下位フローへのリンクだけを描かせる。`check_flow.py --stage structure` が超過を FAIL にする。
2. `taxonomy.json` の `make_flow: true` の分類ごとに、サブエージェントを1つ起こして下の指示文を渡す。分類どうしは独立なので並べて進める。親はカードを読まない。サブエージェントを使えないときは、親が1分類ずつ同じ手順で書く。
3. そろったら、番号を振り直してから点検する:
   ```bash
   python3 scripts/renumber.py -w <作業フォルダ>
   python3 scripts/check_flow.py -w <作業フォルダ> --stage flow --report <作業フォルダ>/out/チェック_フロー.txt
   ```
   FAIL は、そのフローの担当に FAIL の行を添えて直させる（`--only F03` でそのフローの行だけ出る）。`renumber.py` は、番号・種別・線の端に形の違反があるフローを振り直さない（そのフローは、点検を通してからもう一度）。
4. WARN は1件ずつ見る。「同じ手順が2つのフローに描かれている」は上位と下位の重ね描き、「帳票を受け渡しているのに『続く』が無い」は受け渡しの抜けの疑い。
5. フローをまたぐ整合を親が見る（材料は報告 `reports/flow_*.json` の `for_parent`）: 続き先が互いに合っているか、用語の正本に無い呼び方をどうするか、同じ問いの確認事項が重なっていないか。用語を足す・寄せるときは `glossary.json` を直し、関係するフローを直させる。

## 指示文の `{…}` に入れるもの

`{WORK}`＝作業フォルダの絶対パス、`{SKILL}`＝このスキルのフォルダの絶対パス、`{FLOW_ID}`・`{FLOW_NAME}`＝`taxonomy.json` の分類の `id` と `name`（`F03`・`支払処理`）。

## サブエージェントへの指示文（ここからコピー。`{…}` を置き換える）

あなたは業務マニュアルの読取結果から、as-is（現状）の業務フローを1本、JSON で書く担当です。**原典に書いてあることだけをフローにしてください。** 書いていないことを補って流れを整えると、誤ったフローがそのまま納品されます。つながらないところは「推定」として置き、確認事項にします。

### 担当するフロー
- 作業フォルダ: `{WORK}`
- 業務分類: `{FLOW_ID}`「{FLOW_NAME}」（`{WORK}/taxonomy.json` の該当する分類を読む。`pages` が割り当てられたページ。番号はファイル名 `pNNNN` の番号）
- 書く先: `{WORK}/flows/{FLOW_ID}.flow.json`

### 最初に読むもの
- `{SKILL}/references/flow-rules.md` の §0・§3・§5（フロー化と確認事項の決まり）
- `{SKILL}/references/schemas.md` の「番号の2種類」「フロー」「確認事項の書き方」（**表に無い項目は足さない**）
- 実例: `{SKILL}/evals/fixture_expected/flows/F03.flow.json`

### 材料
- 割り当てられたページのカード `{WORK}/cards/<資料ID>/pNNNN.json`（手順・分岐・図・補足・曖昧な点）。**読む前に大きさを確かめる**: `python3 {SKILL}/scripts/pages.py plan-flows -w {WORK}` で自分の分類が「大きすぎる」と出たら、書かずに、節ごとの大きさをもとに分割案を報告する（`status: split_needed`）。
- カードだけで決められないとき（図の矢印の向き、手順の順、担当）は、ページ画像 `{WORK}/pages/<資料ID>/pNNNN.png` を Read で開いて確かめる。カードが原典と違っていたら、カードも直す（項目の id は変えない）。
- 担当・システム・帳票の名前は `{WORK}/glossary.json`（用語の正本）。資料の関係と、この業務がどの業務に続くかは `{WORK}/structure/hierarchy.json`（`tree` の `refs`・`doc_relations`・`sequence`）。

### 書き方
1. 割り当てられた全ページのカードを読み、手順を原典の順に並べる（原典の順が一般的な流れと違っていても、原典のまま。並べ直さない）。複数の資料に同じ作業があれば1つのノードにまとめ、出典を両方付ける。内容が食い違えば、まとめずに確認事項（種別「資料間の矛盾」）にする。
2. 担当（レーン）を並べる。**名前は用語の正本の `name` から選ぶ。** やり取りの多い担当を隣に、システムは右端に。正本に無い呼び方が原典にあったら、いちばん近い正本の名前で仮に置かず、報告の `for_parent` に書いて親に足してもらう。
3. ノードを置く。ラベルは原典の言葉で「目的語＋動詞」。**動詞で終える**（体言止め・「〜へ」にしない。判断は「〜か」）。条件・時期・補足は `detail` に（120 字まで。要点だけ。図には、機械がかっこで包んで出す）。条件の一覧・金額の表など、縮めると中身が読めなくなるものは `reference` に全部書く（図の箱には出ない）。1つの手順（カードの項目）に動作がいくつもあるときは、ノードを分けてよい（どのノードも同じ `item` を引く）。**ノードごとに出典を付ける**: 資料（`doc_id`）・ファイルの番号（`page`。刷られたページ番号ではない）・もとにしたカードの項目（`item`: s3・d1・g2）・原文の引用（`quote`。カードの `quote` から取る。言い換えない）。
4. **カードの手順・分岐は、補足の中の作業（`origin: note`）も含めて、すべてノードにする。** フローに入れないもの（ほかの分類で描く・資料間で食い違うので確認事項にした・同じ作業の重複）は、`excluded_items` に理由を書く。
5. 条件で分かれるところは判断ノードにし、出口のすべてにラベルを付ける（ラベルは 12 字まで。出口は4本まで）。原典に片方しか無ければ、もう片方は `inferred: true` で置き、確認事項にする。
6. 線を引く。原典に順が書かれていない線（資料をまたぐ順、補足の中の作業をどの手順の前後に置くか）は `inferred: true` にし、確認事項にする。
7. 開始と終了を置く。行き止まり（差し戻し・エラーのあと）は、原典に続きが無ければ推定の終了を置いて確認事項にする。
8. ほかの業務分類に続くところは `subprocess` ノードにして `link_flow` に相手のフロー id を書く。`hierarchy.json` の `sequence` で「続く」とされた先には、必ず置く。リンクの出典は、続くことが書かれた文（「第8章 購買を参照」）のあるページ。自分の分類のページに無ければ、続き先の分類のページを引いてよい。**上位の資料が1行で書き、下位の資料が詳しく書いている業務で、下位のフローが別にあるとき**は、こちらにはリンクだけを置き、詳細を重ねて描かない。
9. カードの `uncertain`・`unreadable` を1件ずつ見て、フローに関わるものは確認事項にする。**確認事項は、答えで図が変わるものだけ**（`effect` に、変わる所を 1 つ書く: 箱／順序／分岐／担当／システム・帳票／フローの範囲）。値だけを聞く問い（金額・期限はいくつか）・書かれていることが、いまも同じかの確かめ・名前だけの問いは、出さない（flow-rules 5.8）。資料どうしで値だけが違うときは、補足に両方の値を書く（3.12）。
10. 割り当てられたのに使わなかったページは、理由を `unused_pages` に書く（**自分の分類のページだけ。** ほかの分類のページは書かない）。
9b. **担当の書かれていない作業**（カードの `actor` が空で、レーンが原典から1つに決まらない）は、いちばん確からしいレーンに置き、`inferred` にはしない。フローの中で「次の作業を行うのは A ですか、B ですか」の確認事項を1件だけ書き、対象のノードを全部 `nodes` に並べる（`"nodes": ["P-003", "P-004", "P-007"]`。対象が1つなら `node`）。同じ趣旨の問いを、ノードごとに並べない（規約 3.21・5.6）。
9c. **ノードの推定の印（`inferred`）は書かなくてよい。機械が付ける**（`renumber.py`）: カードの手順・分岐を出典に引くノード（`item` がある）は推定でない、引かない作業のノードは推定。あなたが守るのは出典の書き方: 原典にある作業は、必ずカードの項目を `item` で引く。原典に無いノード（場面で分ける判断 など。差し戻しを受ける側の作業は足さない）の出典は、ページと引用だけを書き、`item` は書かない（推定になるので、そのノードを指す確認事項を書く）。囲み・注記の中の作業や、「〜が重要です」と書かれた作業は、作業そのものは原典にある（`item` を引く）。前後の線を推定にして確認事項で聞く。**線の推定の印は、あなたが付ける**（原典に順が書かれていない線）。出典の `quote` は書かなくてよい。`item` を書けば、機械がカードのその項目の引用を写す（`quotes.py fill`）。`item` の無い出典（リンクのノードなど）は、`lines` に行の番号を書く。
9d. **人の作業の箱（`process`）には、動作の種類（`action`）を 1 つ書く**（決まった 12 語から。選び方は flow-rules 3.22）。業務マトリクス一覧の、処理時間の仮の値を引く鍵になる。分の数字は、どこにも書かない。量（`volume`）は、資料から言えるときだけ、理由（`volume_reason`）つきで書く。「特大」（時間・日の単位でかかる作業）は、理由が無ければ FAIL。
9e. **決まりで決まる所は、機械が当てる**（`renumber.py`。書かなくてよい・書いても直される）: 確認事項の重要度（`severity`。effect と指す箱の数から。flow-rules 5.4）、判断の名前の「？」→「か」、分岐の書かれていない側のラベル「その他」→ 書かれた側の反対の語（「不備がある」→「不備がない」）、空の終了条件 → 終了に入る最後の作業の「〜したとき」（終了条件は、原典に成果が書かれているときだけ書く）。
10b. 文章で書く項目（確認事項の質問・仮置き、`detail`、理由）の中に、ページ番号・ノードの番号・確認事項の id を書かない。資料を ID（M01）で呼ばない（資料の題名で書く）。ページは `sources`、対象は `node`・`nodes`・`edge` に書く（番号は機械が引き直し・振り直すので、文の中の番号は古くなる）。
11. ノードの番号は仮でよい（あとで機械が振り直す）。ステップが 25 を超えても、それだけでは分けない（flow-rules 2.10）。節・項ごとに、きっかけが別の手続きが並んでいれば、切れ目を報告する（勝手に分類を増やさない。親が `taxonomy.json` を直す）。

### 終わったら
1. 番号を振り直し、自分のフローを確かめて FAIL を直す:
   ```bash
   python3 {SKILL}/scripts/quotes.py fill -w {WORK} --flow {FLOW_ID}       # 出典の引用を、カードから写す
   python3 {SKILL}/scripts/renumber.py -w {WORK} --only {FLOW_ID}
   python3 {SKILL}/scripts/validate.py -w {WORK} --kind flow --only {FLOW_ID}
   python3 {SKILL}/scripts/check_flow.py -w {WORK} --stage flow --only {FLOW_ID}
   ```
   `--only` を付けると、自分のフローの行だけが出る。行の頭がほかのフロー・分類の id の行（「F02: フローがまだ無い」など）は出ない。ほかの分類のページの心配はしなくてよい。
   「…がフローに無い」は、カードの手順・分岐がどのノードにも引かれていない。ノードの出典に `item` を足すか、`excluded_items` に理由を書く。「引用が出典のページに無く、… にある」は、`page` が1つずれている（刷られた番号で書いていないか）。
2. 報告を `{WORK}/reports/flow_{FLOW_ID}.json` に書き、`python3 {SKILL}/scripts/validate.py --file report_flow <そのファイル>` で形を確かめる（形は schemas.md の「報告と採否表」）。
3. 返事は1行だけ: ノードの数と確認事項の数。JSON の中身は貼らない。

## 書き出したあとの直し方

`build_drawio.py` → `check_layout.py` の PNG を見て、次のときは直して書き出し直す。直しの一覧で作ったフローは、直しの一覧を直して `apply_edits.py` をやり直す（`flow.json` を手で直すと、点検が FAIL にする）。JSON をまるごと書いたフローは、`flow.json` を直す。フローが多いときは、PNG を数本ずつ別のエージェントに見させ、親は指摘だけを受け取る（親が全部の画像を開かない）。

| 見た目 | JSON をまるごと書いたフロー | 直しの一覧で作ったフロー |
| --- | --- | --- |
| 線が遠くまで横切る・交わりが多い | `lanes` の順を入れ替える（やり取りの多い担当を隣に）。`renumber.py --lanes` で、機械に並べ直させてもよい | レーンは機械が並べる（決まり 4.2）。それでも読みにくければ、`lane_order` に並べたい順を書く |
| 戻りの線が長い | 戻り先に近い位置にノードが来るよう、`nodes` の順を見直す（行は線のつながりから決まる） | `move` で並べ替える |
| ノードの文字があふれる・縦に長い | `label` を短くし、補足を `detail` に。それでも長ければノードを分ける | `label`・`detail`。それでも長ければ `split` |
| 1ページが縦に長すぎる | 長いだけなら、そのまま 1 枚に描く（大きさだけでは分けない。決まり 2.10）。節・項ごとに、きっかけが別の手続きが並んでいれば、下位フローに分ける（`taxonomy.json` に分類を足し、親に `subprocess` を置く） | 同じ（下位フローは、分類を足し、`link` でつなぐ） |
| 分岐の主な流れが横に出て、例外がまっすぐ下に出る | `nodes` の中で、主な流れの先のノードを例外の先のノードより前に書く（同じレーンでは、先に書いたノードが判断のすぐ下の行に入り、まっすぐ下の線になる） | `move` で、主な流れの先の作業を、例外の先の作業より前にする |

原典照合レビュー（工程8）を始めたあとは、番号を振り直さない（採否表のノード番号とずれる。`renumber.py` は、採否表のあるフローの番号だけを自動で飛ばし、推定の印・札・決まりで決まる所は当てる）。
