# フロー化の進め方（工程6。既定の方式: 機械が下書き、LLM が直しの一覧）

フローを、LLM に JSON でまるごと書かせる代わりに、**機械がカードから下書きを作り、LLM は直すところだけを「直しの一覧」に書く**やり方。
同じカードからは同じ下書きになるので、2回作っても、ラベル・線・帳票・決まった形の確認事項が揃う。揺れが残るのは、LLM が決める所
（まとめ方・担当の違う作業の分け方・資料をまたぐ順・ラベルの短縮・原典の中身についての問い）だけになる。
`flow.json` から先（点検・図・業務マトリクス一覧・原典照合）は、どちらの方式でも同じ。下書きでは組めないフロー（カードの項目とノードが1対1にならない・大きく組み替える）だけ、`references/flow-guide.md`（JSON をまるごと書く方式）で作る。

## 親（進行役）のやること

1. 材料の大きさを見て分類を分けるところまでは、`references/flow-guide.md` の 1 と同じ。
   カードに行の番号（`lines`）が無いときは、先に `python3 scripts/quotes.py locate -w <作業フォルダ> --rewrite`（いまの引用から、行の番号を機械で引く。下書きは、行の番号で分岐の位置と箇条書きの切れ目を決める）。
2. `make_flow: true` の分類ごとに、サブエージェントを1つ起こして下の指示文を渡す。小さい分類は、1体に数本まとめてよい。
3. そろったら `python3 scripts/run.py -w <作業フォルダ>`（引用・番号の入れ直し → 点検 → 書き出し）。FAIL は、そのフローの担当に、直しの一覧を直させる。
4. 原典照合のあとの直しも、直しの一覧に足して `apply_edits.py` をやり直す（`flow.json` を手で直すと、次に `apply_edits.py` を実行したときに消える）。

## 指示文の `{…}` に入れるもの

`{WORK}`＝作業フォルダの絶対パス、`{SKILL}`＝このスキルのフォルダの絶対パス、`{FLOW_ID}`・`{FLOW_NAME}`＝`taxonomy.json` の分類の `id` と `name`。

## サブエージェントへの指示文（ここからコピー。`{…}` を置き換える）

あなたは、機械が作った業務フローの下書きを見て、直すところを「直しの一覧」（JSON）に書く担当です。フロー（`flow.json`）そのものは書きません。機械が、下書きにあなたの直しを当てて作ります。**原典に書いてあることだけを、直しの根拠にしてください。** 書いていないことを補って流れを整えると、誤ったフローがそのまま納品されます。直すところが無ければ、直しは空のままで構いません。

### 担当するフロー
- 作業フォルダ: `{WORK}`
- 業務分類: `{FLOW_ID}`「{FLOW_NAME}」
- 書く先: `{WORK}/flows/{FLOW_ID}.edits.json`（`flow.json` は書かない・直さない）

### 最初に読むもの
- `{SKILL}/references/flow-rules.md` の §0・§3・§5（フロー化と確認事項の決まり）
- `{SKILL}/references/schemas.md` の「直しの一覧」（書く形と、直しの種類。**表に無い項目・種類は使えない**）
- 下書き: `python3 {SKILL}/scripts/draft_flow.py -w {WORK} --flow {FLOW_ID}`

### 材料
- 下書き（上のコマンドの出力）。カードの手順・分岐が、1項目＝1ノードで、ページの順に並んでいる。項目は、キー（`M01.35.s3`）で指す。
- 割り当てられたページのカード `{WORK}/cards/<資料ID>/pNNNN.json`（下書きに出ない `notes`・`figures`・`uncertain`・`unreadable` を見る）。
- カードだけで決められないとき（手順の順、担当）は、ページ画像 `{WORK}/pages/<資料ID>/pNNNN.png` を Read で開いて確かめる。
- 担当・帳票の名前は `{WORK}/glossary.json`（用語の正本）。この業務がどの業務に続くかは `{WORK}/structure/hierarchy.json` の `sequence`。

### 下書きが、すでにやってあること（直しに書かない）
- ラベルは、カードの文そのまま。帳票は、カードの「参照」「作る」から付けてある。線は、並びの順につないである。
- 概要のページの手順は、詳しいページの、同じ番号の見出しの手順にまとめてある（「まとめた候補」）。
- 推定の印（番号の無い箇条書きの順・資料をまたぐ順・補足の中の作業の前後・分岐の書かれていない側）と、それを聞く確認事項。
- 担当の書かれていない作業を聞く確認事項（1件）。終了条件が空のとき、終了に入る最後の作業からの「〜したとき」（決まらなければ確認事項）。開始条件が空のときの確認事項。確認事項の重要度（決まり 5.4）。開始と終了。使わなかったページの理由。`hierarchy.json` の `sequence` にある続き先へのリンク。

### 直し方（上から順に見る）
1. **まとめる**: 「まとめた候補」が合っているかを見る。違っていれば `unmerge`。まとめた概要の側の文に、詳しい側に無い作業・確認が書かれていれば（概要「入力し、計算を行う」／詳細「入力する」）、まとめたままにせず、`unmerge` して別のノードにするか、`detail` に書く。同じ作業が、別のページ・別の資料にもう一度書かれていれば `merge`（担当・順序・作業の有無が食い違うときは、まとめずに `questions` に種別「資料間の矛盾」で書く。値（金額の基準・日付・件数）だけが違うときは、まとめて `values` に資料ごとの値を書く: 補足は機械が決まった形で書く。flow-rules 3.12）。重複は `exclude` の `same_as`（同じ作業として入れた項目）、ほかの分類のフローで描く手順は `exclude` の `flow`（理由は機械が決まった形で書く）。どちらでもなければ `reason` を書く。
2. **並び**: 下書きは、ページの順・カードの順。原典の順と違うところだけ `move`。**原典に書かれた順を、一般的な流れに合わせて入れ替えない。**
3. **レーン**: 担当の書かれていない手順（下書きの `[担当なし]`）を置くレーンを、`default_lane` に1つ書く（概要の表の「担当者」など、原典からいちばん確からしい担当）。1つの手順の文に、別の担当の作業が書かれているとき（「部長に報告し、指示を受ける」「課長の承認を得る」）は、`split` で担当ごとの作業に分ける。**分けるのは、担当が変わるときだけ**（同じ担当の作業は、文に動作がいくつあっても1つのノードのまま）。レーンの並びは機械が決める（開始の担当が左端・システムが右端、残りは線がまたぐレーンの数が少ない順。決まり 4.2）。お客様の組織の順に合わせたいときだけ、`lane_order` に左から並べたい順に書く。
4. **分岐**: カードの分岐は、行き先の手順へつないである。原典に書かれていない側は、書かれた側の反対の語（「不備がある」→「不備がない」。表に無ければ「その他」）のラベルで、その手順を飛ばして次へ進む線になっている（推定。ラベルは機械が付ける）。行き先（次へ・終了・ほかの手順）を `branch` で直す（`label` は、反対の語で意味が通らないときだけ書く）。分岐の先の「差し戻す」作業のあとは、機械が推定の終了と確認事項にする（差し戻しを受ける側の箱は足さない）。カードが分岐にしていない条件つきの手順（下書きの「条件:」）が、行う・行わないの分かれ目なら `decide`（時期・きっかけの条件は、分岐にしない）。
5. **線**: 差し戻して前の手順に戻る・エラーのあとで合流する、のように、並びの順でない線は `connect`。要らない線は `disconnect`。
6. **ラベル**: **30 字を超えるラベル**と、**動詞で終わっていないラベル**（体言止め。判断で「〜か」になっていないもの）を、`label` で直す（原典の語で「目的語＋動詞」）。分岐の線のラベルは 12 字まで（`branches`）。そのほかのラベルは、カードの文のままにする（言い換えない）。
7. **補足**: 条件・時期の要点を `detail`（120 字まで）に（図には、機械がかっこで包んで出す。自分では、かっこを付けない）。縮めると読めなくなる一覧・表は `reference` に。下書きの補足（条件）で足りていれば書かない。使うシステムの名前は書かない（手順の `system` から、機械が箱に札「［会計システム］」を付ける）。下書きに「⇒ この作業のすぐあとに、機械がシステム処理の箱を置く」と出ている手順には、プログラムの起動点が紐付いている。その処理の箱を `add` で足さない（機械が、アクティビティ図の番号つきで置く）。
8. **帳票**: 同じ書類が、概要と詳細で呼び方だけ違って2つ付いているとき（「集計表」と「月次の集計表」）は、詳しいページの呼び方を残して、もう一方を `drop_file`。同じ帳票が続けて出て図が読みにくいときも `drop_file`。
9. **続く業務**: `sequence` にある続き先は機械が置く。置く位置を変える・原典にほかの続き先が書かれているときだけ `link`。
10. **確認事項**: 機械が作るもの（上の「すでにやってあること」）は書かない。カードの `uncertain`・`unreadable` を1件ずつ見て、**原典の中身についての問いのうち、答えで図が変わるもの**（担当・順序・作業の有無・分岐の行き先・使う帳票やシステムが、原典から決まらない・資料どうしで食い違う）だけを `questions` に書く。`effect` に、変わる所を 1 つ書く（箱／順序／分岐／担当／システム・帳票／フローの範囲）。値だけを聞く問い（期日・金額の基準はいくつか）・いまも同じかの確かめ・名前だけの問いは、書かない（資料どうしで値だけが違うときは、`detail` に両方の値を書く）。対象は、項目のキーで指す。
11. `start_condition`（きっかけ）・`end_condition`（成果）を書く。きっかけは、原典に書かれたもの（概要の表の「タイミング」など）。無ければ空にする。成果は、原典に書かれているときだけ書く。書かれていなければ空にする（機械が、終了に入る最後の作業から「〜したとき」を入れる。最後の作業が 1 つに決まらなければ、確認事項を作る）。下書きの先頭に、開始条件の手がかりと、機械が入れる終了条件の案が出る。
12. **動作の種類**: 人の作業の箱（下書きの「手順」のうち、システムのレーンに置かないもの）すべてに、動作の種類を 1 つ、決まった 12 語から選んで `time` で書く（入力する／作成する／確認する／承認する／提出・回付する／受け取る／出力する／連絡する／計算する／調べる／保管する／その他）。箱の名前の動詞が、何をする動きかで選ぶ（照合する・点検する → 確認する／登録する・記入する・システムで実行する・システムの画面で伝票を作る → 入力する／回収する → 受け取る／差し戻す・送付する → 提出・回付する／電話で確かめる・依頼する → 連絡する）。使うシステムの札がある箱で「作成する」を選ぶと、点検が WARN（画面で作るなら「入力する」。紙・ファイルを一から作るなら、そのまま）。1 つの箱に 2 つの動きがあれば、時間のかかるほう＝基準の表で、同じ量の分が大きいほう（flow-rules 3.22）。どれにも当たらなければ「その他」。`add`（作業）・`split` の箱には、その場で `action` を書く。**分の数字は、どこにも書かない**（業務マトリクス一覧の処理時間の仮の値は、機械が、基準の表から引く）。量（`volume`）は、ふつう書かない（機械が、同じページの手順を 3 つ以上まとめた箱・見る帳票が 2 つ以上の箱を「大」、ほかを「中」にする）。資料から量が言えるときだけ、理由（`reason`）つきで、小・大・特大に変える（「ボタンを押すだけ」→ 小）。**特大**は、資料から、時間・日の単位でかかると読める作業にだけ付ける（年・半期に 1 回、全体をまとめ上げる／全件を 1 つずつ扱う／期間をかけると書いてある）。理由には、資料の、そう読める所を書く。迷ったら付けない。下書きに、量の案（ボタンを押す・実行する → 小）と、特大の手がかりの語（年 1 回・決算・全員 など）が出る（付けるかどうかと理由は、資料を読んで決める）。
13. 文章で書く項目（確認事項・補足・理由）の中に、ページ番号・キー・ノードの番号を書かない。資料を ID（M01）で呼ばない（担当者には通じない。資料の題名で書く）。

### 終わったら
1. 直しを当てて、フローを確かめる:
   ```bash
   python3 {SKILL}/scripts/apply_edits.py -w {WORK} --flow {FLOW_ID}
   python3 {SKILL}/scripts/validate.py -w {WORK} --kind flow --only {FLOW_ID}
   python3 {SKILL}/scripts/check_flow.py -w {WORK} --stage flow --only {FLOW_ID}
   ```
   「直しの一覧に誤り」と FAIL は、**直しの一覧を直して** `apply_edits.py` をやり直す（`flow.json` を手で直さない）。WARN「ラベルが長い」は `label` で短くする。WARN「動作の種類（action）の無い作業」は、`time` で付ける。
2. 報告を `{WORK}/reports/flow_{FLOW_ID}.json` に書き、`python3 {SKILL}/scripts/validate.py --file report_flow <そのファイル>` で形を確かめる（形は schemas.md の「報告と採否表」）。
3. 返事は1行だけ: ノードの数と確認事項の数。JSON の中身は貼らない。
